# 需求对齐与决策记录（Grill with Docs）

本 Skill 用于在 PRD 编写、原型验证、进入开发前，对需求进行结构化对齐，把隐含的假设显性化，并记录关键决策。

---

## 适用场景

1. **PRD 编写前**：对齐模块范围、目标用户、核心场景
2. **原型验证中**：通过原型反向拷问 PRD，发现遗漏或矛盾
3. **进入开发前**：确认 PRD 已 ready，关键决策已书面化
4. **开发中遇到 PRD 缺口**：快速判断是就地决策还是走 CR 流程

---

## 使用原则

- **对事不对人**：追问的是文档和方案，不是质疑提出者
- **证据优先**：每个结论都要有 PRD、原型、标准或技术预研报告支撑
- **适可而止**：对齐到"可以进入下一步"即可，不要追求无限完美
- **必须记录**：所有关键决策必须写入 `docs/04-execution-records/module-XX/design-decisions.md`

---

## 追问框架

### 1. 范围边界

- 本模块要解决什么问题？不解决什么问题？
- MVP 必须做哪些？明确不做的有哪些？
- 未来版本（v0.2/v0.3/v1.0）会扩展哪些功能？

### 2. 用户与场景

- 目标用户是谁？（运维、开发、管理员、领导）
- 核心用户故事是什么？
- 最频繁的操作路径是什么？
- 异常路径和边界情况有哪些？

### 3. 数据与模型

- 核心实体有哪些？（Resource、Strategy、Job、Config 等）
- 实体之间的关系是什么？
- 数据来源是什么？（手工录入、CMDB 同步、自动发现）
- 数据量级多大？（千级、万级、百万级）

### 4. API 与集成

- 需要哪些 API？
- 与 Prometheus / Blackbox / Alertmanager 的边界在哪里？
- 是否需要修改 upstream？如果必须修改，走扩展点还是 patch？
- 配置下发是 push 还是 pull？

### 5. 权限与安全

- 哪些操作需要鉴权？
- 哪些数据是敏感的？
- 文件上传（Excel、YAML）如何校验？
- 配置下发如何防止误操作？

### 6. UI/UX

- 核心页面有哪些？页面之间如何跳转？
- 表单字段哪些是必填？校验规则是什么？
- 列表默认排序和分页策略是什么？
- 操作成功/失败如何反馈？

### 7. 验收标准

- 什么情况下可以认为本模块 MVP 完成？
- 必须通过的测试有哪些？
- 性能或稳定性要求是什么？

## 输出格式

对齐结果必须写入：

```
docs/04-execution-records/module-XX/design-decisions.md
```

文件格式：

```markdown

- 日期：2026-08-02
- 参与 Agent：prototype-designer、orchestrator
- 触发原因：PRD 编写前需求对齐

## 关键决策

### 决策 1：xxx

- 问题：xxx
- 结论：xxx
- 依据：PRD §3.2 / 原型页面 X / 技术预研报告
- 影响范围：数据模型、API、前端页面

### 决策 2：xxx
```

## 阻断规则

以下情况必须停止，要求补充材料或上报 Orchestrator：

1. 关键决策没有书面结论
2. 模块边界与 `02_Product_Roadmap.md` 明显冲突
3. 涉及 Prometheus 等开源组件能力不确定，但尚未做技术预研
4. 安全控制点（鉴权、配置下发、上传）未明确
5. 验收标准缺失或不可验证

---

## 与原型验证的关系

`grill-with-docs` 和原型验证是互补的：

- **grill-with-docs**：通过结构化追问暴露逻辑缺口
- **原型验证**：通过可视化页面暴露交互缺口

推荐流程：

```
初步对齐（grill-with-docs）
    │
    ▼
编写/更新 PRD
    │
    ▼
生成原型
    │
    ▼
原型评审 + 深度对齐（grill-with-docs）
    │
    ▼
PRD 定稿（ready）
```

---

## 与 Orchestrator 的关系

Orchestrator 在以下时机调用本 Skill：

1. 用户需求不清晰时
2. prototype-designer 报告 PRD 关键决策不明确时
3. 进入开发前做最后确认时
4. 开发中发现 PRD 缺口需要快速决策时

---

## 常见借口与反驳

| 借口 | 反驳 |
|------|------|
| "需求已经很清楚了，不用再 grill" | 清楚是对人而言，对 AI 和后续开发者往往是隐含的。关键决策必须书面化 |
| "先出原型再对齐" | 原型是验证工具，但对齐应贯穿 PRD 编写和原型验证全过程 |
| "这个决策以后再说" | 影响当前模块闭环的决策必须在当前阶段确定，否则无法派生 Plan |
| "对齐结果记在心里就行" | 所有关键决策必须写入 design-decisions.md，否则无法追溯 |
