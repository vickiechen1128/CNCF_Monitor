# 需求规格说明书（SRS）编写规范

本 Skill 面向**需求方**。核心原则：**场景优先，功能后置**——需求方只讲“场景 + 验收”，能力抽象与实现交给技术方。目标是写出能被技术方**演示**、被需求方**用感受验证**的输入，而不是一份功能清单。

---

## 1. 适用场景

- 把原始业务需求转成可开发的 SRS。
- 需求方与技术方对齐“要解决什么场景”。
- 需求方在开发中确认/修正场景理解。

---

## 2. 核心原则

1. **场景是需求方的第一语言**：谁、在什么情境、要完成什么任务、怎么算成功。
2. **功能后置**：不先列功能/页面/接口，不写“常见功能”补全。
3. **能力抽象不是需求方的义务**：复用、扩展、新建能力是技术方的事，SRS 不要求填 CAP。
4. **面向结果验收**：验收写“结果对不对”，不写“按钮在哪、字段叫什么”。
5. **写非目标**：明确不做什么、不为单个项目定制什么。

---

## 3. 场景引导（对话框架）

描述每个需求时，依次澄清并记录：

| 维度 | 必问 |
|------|------|
| 谁 | 使用者的角色 |
| 情境 | 什么情况下触发 |
| 任务 | 要完成什么任务（动词 + 对象） |
| 成功标准 | 什么结果算“做成了” |
| 前置条件 | 需要什么已就绪的状态 |
| 操作步骤 | 用户怎么走（面向结果，不是面向组件） |
| 非目标 | 明确不做什么 |

**禁止**：把“任务”写成“功能”。例如：

```text
❌ 功能式：做一个资源 CRUD，支持导入导出、标签、关系
✅ 场景式：运维要登记一台新主机并让它进入采集（SCN-01）
```

---

## 4. SRS 结构

> 模板：`docs/02-product-requirements/Modules/SRS/_TEMPLATE.md`。

建议固定以下章节，编号稳定：

```text
1. 文档信息与变更记录
2. 背景、目标与非目标
3. 业务场景（SCN-xx）
4. 功能需求（FR，由场景派生）
5. 非功能需求（NFR）
6. 概念数据（只写实体，不写表/字段）
7. 约束、假设与依赖
8. 验收标准（面向结果）
9. 变更影响
附录 A：实现追溯见 Scenario Link
```

### 4.1 业务场景（第一公民）

每个场景一个稳定 ID：

```markdown
### SCN-01：新网域接入监控
- 谁：运维
- 情境：新上线一个采集节点/网域
- 任务：完成纳管、看到节点在线、确认配置已下发
- 成功标准：节点在线、目标状态正确、无需手工改配置
- 前置：已登记网域
- 操作步骤：1. 纳管 2. 安装 agent 3. 等待心跳 4. 查看配置
- 验收：节点 online；config 版本 +1；配置产物正确
```

### 4.2 功能需求 FR

FR 由场景派生，每条标注来源场景：

```markdown
#### FR-01：网域纳管（源自 SCN-01）
- 能力意图：把已登记网域纳入监控
- 验收：纳管后节点可注册、配置可下发
```

不写 API 路径、数据库表、页面组件、字段枚举。

### 4.3 验收标准

面向用户结果，不是面向功能：

```text
✅ 验收：新节点在 N 秒内出现在在线列表，配置版本 +1
❌ 验收：列表页有“新建”按钮，表单包含 name/ip 字段
```

---

## 5. 禁止项

- 不写 API 路径、字段、错误码（在 HLD + 契约）。
- 不写数据库表/索引（概念实体可以写）。
- 不写页面组件/交互细节（演示阶段由技术方走查）。
- 不写“功能清单/常见功能补全”。
- 不写客户名/项目名/一次性字段进核心语义。
- 不要求填 CAP / 能力映射（那是技术方的事）。

---

## 6. 质量检查清单

- [ ] 每个场景有：谁/情境/任务/成功标准/验收
- [ ] 每个 FR 都能追溯到某个 SCN
- [ ] 验收是面向结果，不是面向按钮/字段
- [ ] 非目标明确（不做什么、不为单项目定制什么）
- [ ] 没有出现 API/表/页面/组件细节
- [ ] 没有出现“功能清单式”描述

---

## 7. 与 hld-design 的交接

- SRS 交给技术方后，技术方用 `hld-design` 做“场景 → 实现”映射与演示脚本。
- 双方唯一链接点是 `Module_XX_Scenario_Link.md`（场景 ↔ 设计 ↔ 演示 ↔ 验收）。
- 需求方在每次场景演示后更新“需求方反馈”列，不直接改 HLD。
