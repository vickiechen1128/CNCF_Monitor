# 安全审查规范

本 Skill 是 security-reviewer 的专项检查基线。审查协议、输入包、triage 顺序、输出模板与复审交接统一遵循 `code-review`；本 Skill 只补充安全专项维度、深读重点与严重级别。

---

## 1. 安全审查的特殊性

- 密钥、SSRF、注入模式等可以通过 grep 预检，但**鉴权、越权、业务逻辑安全必须由 LLM 深读判断**。
- 不得为了降本把安全审查空心化为“只读预检结果”。
- 安全审查覆盖前后端 + 部署 + patch，基数比单端代码审查大；但仍遵守 `code-review` 的软预算与留痕要求。
- 安全结论只有 `PASS` / `FAIL`；存在任一 CRITICAL / HIGH ⇒ FAIL。

---

## 2. 审查范围

- `platform/` 后端代码
- `ui-custom/web/` 前端代码
- `deploy/` 部署配置（如存在）
- `patches/prometheus/` patch
- 本次 `feat/module-XX` 相对 `develop` 的变更 diff

禁止深审 `docs/`、`upstream/`；目录越界本身按安全 / 隔离问题记录。

---

## 3. 安全预检输入

Orchestrator 必须提供：

- 变更文件清单 + 每文件 1–3 行安全控制点摘要
- 预检结果：
  - 密钥 / token / 密码 / 连接串扫描
  - URL scheme / host 校验（SSRF）
  - SQL / 命令 / 模板 / NoSQL 注入模式扫描
  - 文件上传类型 / 大小 / 路径校验
  - 目录隔离检查
- 高风险预标注：鉴权、越权、配置下发、资源导入、Patch 安全
- 已验证清单（信任边界）：抽查 1–2 处，不重新全量验证
- 契约快照：核对新增 / 修改接口的鉴权与权限字段
- PRD 相关章节、task-sequence（缺失不阻断）

预检未命中不等于安全；鉴权 / 越权 / 业务逻辑必须深读。

---

## 4. 后端安全检查

- [ ] SQL 注入：使用参数化查询或 ORM；禁止拼接用户输入
- [ ] 命令注入：不把用户输入拼进 shell / exec
- [ ] NoSQL / 模板注入：查询与模板参数化
- [ ] 路径遍历：校验用户提供的文件路径，限制在允许根目录内
- [ ] 敏感信息：日志、错误信息、响应中不暴露密钥 / 密码 / token / 连接串
- [ ] 上传文件：限制类型、大小、数量；校验内容与扩展名；存储路径不可预测
- [ ] 配置下发：接口必须鉴权；参数校验；写入前备份 / 校验；审计日志
- [ ] 鉴权：所有写接口必须认证；管理接口必须授权
- [ ] 越权：水平越权（租户 / 资源归属）与垂直越权（角色 / 权限）都要检查
- [ ] 多租户隔离：查询与写入必须带租户边界，不能只靠前端过滤
- [ ] SSRF：URL 仅允许 `http` / `https`，host 非空，代理目标走允许列表
- [ ] 反序列化：YAML / JSON / Excel 解析不可触发任意对象构造或命令执行
- [ ] 审计：核心写操作（配置下发、资源导入、用户 / 租户变更）有审计记录

---

## 5. 前端安全检查

- [ ] XSS：不把用户输入直接插入 `dangerouslySetInnerHTML` / DOM
- [ ] CSRF：使用 SameSite Cookie 或 CSRF Token
- [ ] 敏感信息：前端代码 / 构建产物 / localStorage 不硬编码密钥、token、连接串
- [ ] 权限控制：前端隐藏不等于后端授权；敏感操作必须后端鉴权
- [ ] URL 跳转：开放重定向校验目标
- [ ] 上传：前端限制类型 / 大小只是体验，不能替代后端校验
- [ ] 依赖：不引入来源不明的包 / CDN 脚本

---

## 6. 配置下发与 Patch 安全

MetricCenter 会向 Prometheus 写入配置，必须确保：

1. 只有授权用户可以下发配置。
2. 下发的配置经过 schema / 语义校验，避免破坏 Prometheus 运行。
3. 配置变更记录审计日志。
4. 配置文件写入路径固定、可预测范围受限，禁止路径遍历。
5. 下发失败可回滚 / 保留旧配置。

Patch 安全：

- [ ] patch 是否引入新的网络监听、文件写入、命令执行入口
- [ ] patch 是否绕过原有鉴权 / TLS / 校验
- [ ] patch 是否最小化，是否附带 README 与验证方法
- [ ] 是否直接修改 `upstream/` 而未生成 patch（CRITICAL）
- [ ] patch 是否影响 upstream 原有安全测试；影响时是否标注

---

## 7. 部署安全

- [ ] 不提交 `.env`、密钥、证书私钥到 Git
- [ ] 容器以非 root 用户运行
- [ ] 最小化镜像权限与暴露端口
- [ ] 生产配置不默认开启调试 / pprof / 无鉴权管理接口
- [ ] 日志不落敏感信息

---

## 8. 深读重点（不能只看预检）

必须完整深读以下区域：

1. 新增 / 修改的鉴权中间件、权限判断、租户过滤
2. 配置下发 / 资源导入 / 文件上传的完整调用链
3. URL 解析、反向代理、Webhook、远程读取等出站请求
4. Patch 对启动参数、监听端口、文件系统、命令执行的影响
5. 任何“前端隐藏 / 仅靠参数校验”的权限设计

---

## 9. 严重级别（安全专项）

| 级别 | 判定标准 | 示例 |
|------|----------|------|
| **CRITICAL** | 可直接导致未授权访问、数据泄露、远程代码执行、配置被篡改 | 核心写接口未鉴权、SQL / 命令注入、硬编码生产密钥、配置下发无鉴权、直接改 upstream 未生成 patch |
| **HIGH** | 高概率被利用或扩大攻击面 | SSRF 未校验 scheme/host、上传未校验类型/大小/路径、水平 / 垂直越权、patch 新增网络/文件/命令入口、敏感信息进入日志 |
| **MEDIUM** | 需要特定条件或影响有限 | 安全控制点与原型业务意图不符、缺少审计日志、错误信息泄露内部路径、弱校验 |
| **LOW** | 加固建议 | 安全响应头、依赖版本提示、注释中的安全说明缺失 |

特殊规则（与历史审查口径一致）：

- 配置下发 / 资源导入等核心接口未鉴权 ⇒ **CRITICAL**
- 所有 `/api/v2/platform/*` 写接口未鉴权 ⇒ **CRITICAL**
- SQL / 命令 / NoSQL 注入 ⇒ **CRITICAL**
- 直接修改 `upstream/prometheus/` 且未生成 patch ⇒ **CRITICAL**
- URL 解析 / 反向代理未校验 scheme 与 host ⇒ **HIGH**（SSRF）
- 用户上传文件未校验类型 / 大小 / 路径 ⇒ **HIGH**
- 硬编码密钥、密码、token、数据库连接串 ⇒ **HIGH**
- patch 引入新的网络监听、文件写入或命令执行入口 ⇒ **HIGH**
- 安全控制点与原型业务意图明显不符 ⇒ **MEDIUM**

---

## 10. 输出与交接

输出模板使用 `code-review` §8，标题改为「安全审查结果」，总体结论使用 `PASS` / `FAIL`。

- **CRITICAL / HIGH**：必须修复后才能进入 Git Guardian 阶段。
- **MEDIUM / LOW**：记录遗留风险，或让 Developer 快速修复。
- **无问题**：输出 PASS。
- 修复后复审复用同一 Reviewer 会话，只核对修复点与回归；通过即 PASS。
