## 1. 讨论起点：一个 UI 开关引发的架构追问

### 1.1 初始问题

module-09 原型的全局 Header 上有一个「单网域 / 多网域」模式切换开关（`multi_site_enabled`）。用户指出：

> 核心模块里只有 module09 的顶层 banner 上有网域切换开关，点击其他模块它又不存在，让用户误以为这是一个全局的概念。

这个观察的实质是：**一个租户级行政能力开关被放在了具有全局语义的视觉位置上**，造成认知断裂。此前决策 25 已确立「禁止全局顶栏弱提示」（避免「有的模块受控、有的不受控」），banner 开关是同一类问题的更强形式（不是提示，是切换）。

### 1.2 第一轮方案：数据驱动替代模式开关

讨论后形成的第一版结论（后落档为**决策 31**）：

- banner 开关移除；`Tenant.multi_site_enabled` 退化为 M06 租户级「是否允许多网域」的行政能力开关；
- 「网域管理」入口常驻（`default` 域预置且始终存在，页面不空洞）；
- 「Agent 状态」等入口按数据驱动渐进呈现；
- 以「网域纳管 → Agent 上线」作为其他功能网域筛选生效的前置引导（onboarding 漏斗）。

## 2. 用户的第一次修正：常驻不等于无差别展示

用户随即指出第一轮方案的漏洞：

> 单域情况下用户不用获取 Agent 的 Token，那对应的列字段就需要按条件进行调整；用户不用去查看 Agent 进程的状态，即 Agent 状态对用户没有作用。

这引出一个重要原则：**「入口常驻」必须以「页面对当前用户有实际内容」为前提**。一个永远空态的常驻页面比隐藏更差。由此修正为：

- 字段条件化：Token / Agent 类型 / 最后心跳 / 安装指引等字段仅对有 Agent 通道的网域展示；
- 「Agent 状态」入口的显示条件从「多网域开关」改为「是否存在 EdgeAgent 实例」——**数据驱动的渐进呈现**，而非模式驱动。

## 3. 关键追问：单网域真的不需要 Edge Sync Agent 吗

用户提出了本次讨论最关键的问题：

> 现在定义的 Edge Sync Agent 可以包含配置轮询、vmagent 包、blackbox 包。在什么用户场景下，单域是需要 vmagent 包、blackbox 包？是否是分布式部署的情况下，虽然网络域是同一个，但是技术上可以有分布式的采集节点？如果这个用户场景在企业级是常见的，原先说的「按域类型分层：管理域本地文件集 + /-/reload，边缘域 zip 包 + Agent 拉取」必要性就降低了。

### 3.1 场景论证：单网域分布式采集真实存在且企业级常见

经讨论确认，同一网域（无网络隔离、路由可达）内仍要分布式采集的典型驱动：

| 驱动 | 说明 |
|------|------|
| **规模分片** | 中心单点采集器抓不动全部 target，按业务线/集群分摊到多个 vmagent，remote write 回中心——VictoriaMetrics 官方推荐的标准扩容姿势 |
| **采集 HA** | 关键 Job 双节点采集去重，防采集器单点造成监控盲区 |
| **拨测探针位置语义** | blackbox 探测结果与探针物理位置强相关（不同网段/机房探测同一 URL 结果不同），同域也需要多探测点 |
| **多 K8s 集群** | 每集群一个 vmagent 是社区惯例，同网域也这么部署 |

这些场景的共同点：**中心无法直接写这些节点的磁盘、也无法 SIGHUP 它们**——本地文件集通道天然不适用。

### 3.2 推论：分层轴选错了

由此得出（后落档为**决策 32**）：原方案按 `domain_type`（management/edge）分层的轴选错了。**网域是网络/行政分组概念，下发通道是部署拓扑概念，两者不能绑定**。正确的模型：

> 下发通道绑定到**采集节点位置**而非网域类型。每个网域 1..N 个采集节点，节点通道只有两种：`local`（与中心同机/同 Pod，中心可写盘 + reload）和 `agent_pull`（远端节点，心跳拉包）。原「default 域本地文件集」只是 `N=1 且 local` 的退化情形。

### 3.3 同时识别出的决策联动

讨论中还发现两个决策相互牵制：**如果 default 域默认改走 agent_pull，那么第 2 节刚砍掉的 Token 和 Agent 状态页在单域下又都变得必需**。因此结论是不能让「中心域也走 Agent 通道」成为默认——它只能是可选项。这直接为下一轮的 MVP 边界确认埋下伏笔。

## 4. MVP 边界确认：明确拒绝过度设计

用户权衡后拍板（落档为**决策 33**）：

> 「同一网域内多个采集节点 / 混合通道」是很复杂的问题，MVP 侧用户也没有提出这个需求，只是作为企业级产品的演化，现在考虑是过度设计；引导用户从 local 切换 agent_pull 的模式也没有对应的场景，放到 v0.4+。

**MVP 边界**：

- 一个网域同一时刻只有一种下发通道、对应一个逻辑采集组；
- `channel` 按网域固定：`default` 固定 `local`，其他网域固定 `agent_pull`；
- 不提供通道切换入口（编辑表单通道只读）；
- 单网域分布式采集整体推迟 v0.4+。

### 4.1 随之记录的 v0.4+ 演化影响备忘

为保证未来评审时可检索，讨论中识别出的影响面被完整存档（决策 33 备忘）：

1. **M09 下发粒度**：`ConfigDeployment` 从网域粒度细化到节点粒度；心跳 / WAL / `config_sync_status` 按节点聚合；混合通道时同一份 `ConfigVersion` 需同时走两条路径，需一致性策略；UI 保持网域筛选 + 节点下钻。
2. **M01 采集 Job**：同域多节点默认重复执行同一 Job 产生重复序列，必须引入节点级分片（`hashmod` / 目标拆分）或 Job→节点绑定或 HA 主备去重；`scope=edge` 规则下发到多节点时需决定逐节点求值还是选主求值。
3. **external_labels**：仅靠 `network_domain` 无法区分同域不同节点的数据——分片场景需要 `shard`/`node` 标签，HA 场景需要 `replica`/`cluster` 标签供中心去重；`network_domain` 维度的查询/权限/聚合不变。
4. **通道切换**：`local` ↔ `agent_pull` 切换需定义历史 `ConfigVersion` / `ConfigDeployment` 处理策略与在途变更处理方式。

## 5. 极端场景推演：要不要「网域主控节点」或「每域一套产品」

用户进一步推演：如果将来不同网域内都出现多采集节点，是否应升级为「网域主控节点 + 中心控制各域主控」的多层采集模型？还是因网络链路/时延等硬限制，更建议用户在不同网域各部署一套产品？

### 5.1 先区分需求的两种真实驱动

「网域内多节点」背后有两种不同驱动，最优解不同：

- **驱动一：规模 / HA / 探测位置（同域内网互通，节点可直连中心）**——网络无硬限制，问题纯粹是控制面管理粒度；
- **驱动二：网络约束（隔离网域内只有一台机器有出站权限）**——这才是层级模型唯一真正硬性的理由。

### 5.2 业界参照：扁平方案是二十年验证的答案

- **VictoriaMetrics 标准姿势**：每个集群/节点一个 vmagent，各自 remote write 到中心 VM，配置由中心（或 GitOps）统一下发——**没有中间层**；
- **Prometheus 层级 federation**：早年存在，后基本废弃，原因是层级控制面的版本一致性、部分失败、中间层 HA 问题太痛，社区最终选择 remote write + 全局查询层（Thanos/Mimir/VM）的扁平方案；
- **Zabbix proxy**：层级模型能工作的参照，但代价是 proxy 成为有状态中间层——版本同步、故障域、升级编排全部翻倍；
- **OTel Collector + OpAMP**：中心直管大量 agent，同样是扁平模型。

### 5.3 对两个候选方案的评估

**「网域主控节点」层级控制面——否决。** 理由：

- 网络时延不是真正障碍（配置拉取准实时容忍、指标有 WAL 续传兜底）；真正的硬性难度在**有状态层级控制面本身**：两级版本一致性、跨层回滚语义、主控故障域、脑裂、升级编排——这是软件复杂度问题，业界已证明扁平方案更优；
- 驱动二（单出口约束）可以用**透明 relay**（nginx / vmagent relay / egress gateway）解决：配置包和心跳都是轻量流量，relay 无状态、挂了重启即可，**不需要为此造有状态的网域主控**。

**「每个网域部署一套完整产品」——仅空气隔离场景成立。** 每域一套完整 MetricCenter 意味着多套控制面、多套审批流、多套用户/租户/CMDB 对接、无统一视图，直接违背产品核心价值（统一指标中心）。仅在**完全物理隔离、443 出站都不通**的空气隔离环境合理——而现有设计已留路：离线 zip 配置包 + checksum 校验，理论上可离线介质摆渡，边缘只需轻量运行时（Edge Sync Agent + vmagent 一体化包），**连这个极端场景都不需要完整控制面下沉**。

### 5.4 演化路线结论

- **MVP ~ v0.3**：维持域级单通道（决策 33）；
- **v0.4+ 遇到规模需求**：扁平化细化——`CollectionNode` 实体（归属网域），中心直接管节点配置与状态，配 M01 Job 分片与 external_labels 节点标签；
- **遇到单出口约束**：增加「域 egress relay」部署形态（透明转发，无控制逻辑），不动控制面；
- **遇到空气隔离**：离线包摆渡 + 边缘轻量运行时，不部署完整控制面。

产品核心逻辑从头到尾只有一条线：「**中心生成 → 按节点分发 → 心跳回执**」，规模和网络约束都是在这条线上加部署形态，而不是加层级。

## 6. 最终思辨：网域概念该不该降级？

讨论最后一轮回到根本问题：既然业界否定层级、主张扁平节点化，M09 的网域级控制模型是不是站不住脚？网域是否应降级为纯逻辑概念/操作上下文，未来设计全面切换到节点级？

### 6.1 结论：网域和节点回答的是两个不同的问题

- **网域回答「边界」问题**：网络隔离边界、租户归属（1 租户 : N 网域）、CMDB 云区域映射、Token/鉴权边界、出站地址（`center_endpoint` / `remote_write_url`）、`external_labels` 注入、查询侧数据隔离——**天然域级**，不随节点数变化；
- **节点回答「拓扑」问题**：采集进程跑在哪台机器、配置分片给谁、心跳/WAL/同步状态按谁统计——**天然节点级**。

关键洞察：**即使在 VM 的扁平模型里，配置也不是全局一份发给所有 vmagent，而是按集群分组生成、按实例分发**（集群 ≈ 网域，vmagent ≈ 节点）。「域级生成 + 节点级分发」恰恰就是业界标准姿势。扁平化反对的是中间插入有状态控制层，而 M09 的中心直管模式本来就没有这个中间层。

### 6.2 当前设计其实已经半节点化

- 数据模型中 `EdgeAgent` 实例本来就是「一个边缘节点的部署单元」，心跳、WAL、`config_sync_status` 都是节点级上报；
- Agent 状态页已是「网域聚合 + 展开节点明细」两级结构；
- **真正还停在域级的只有配置打包（一个网域一份 ConfigVersion）**。

因此未来从域级到节点级的演化是**增量而非颠覆**：配置生成从「每域一份」变为「域基线 + 节点分片」，`ConfigVersion` / `ConfigDeployment` 增加节点维度，其余（Token、纳管、标签、查询隔离）不动。

### 6.3 两个角度的权衡

- **用户引导角度——网域不该降级**：运维的心智模型就是网络区域（政务内网/外网、DMZ、生产/办公），网域作为操作上下文是正确的产品抽象（决策 25 已定分层）。把节点提到用户主视角会让每个运维背负部署拓扑细节，认知负担反而上升。正确姿势：**用户面向网域，节点作为状态/诊断的下钻维度**（现有 UI 结构已如此）。
- **技术限制角度——该节点化的别硬留在域级**：同域多节点却只有一份配置、聚合心跳掩盖单点故障，才是真正该被技术侧质疑的「域级过度抽象」。要防的是这个，而不是「域概念存在」。

### 6.4 最终设计原则

> **「域生成、节点分发、域聚合展示」**
>
> 1. 配置按网域生成（边界、标签、Job 归属都是域级）；
> 2. 分发与状态观测细化到节点（v0.4+：节点级 `channel` / `ConfigDeployment` / 分片）；
> 3. 用户界面以网域为主上下文，节点只做展开明细和诊断。

这条原则同时回答两端顾虑：对用户，网域仍是稳定的一等公民；对技术，分发粒度可随时细化到节点而不动概念模型。
