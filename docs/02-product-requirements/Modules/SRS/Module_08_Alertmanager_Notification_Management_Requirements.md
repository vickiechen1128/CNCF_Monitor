## 1. 文档目的

本文档用**便于人理解的语言**记录 M08 模块的业务需求、功能需求与非功能需求。它站在产品经理和运维工程师的视角，说明「告警如何通知、通知给谁、如何收敛、如何静默」，并为后续概要设计、详细设计、开发、测试提供依据。

本文档不直接定义 API 字段级别的技术契约（历史技术 PRD 已覆盖），而是回答：**在去掉整份配置文件挂载逃生门、新增内部 Reload 子模块后，这个模块必须具备哪些能力、做到什么程度算合格**。

## 2. 业务背景

### 2.1 M08 的定位

当监控系统产生大量告警时，运维团队面临「告警风暴」——重要告警被淹没、通知渠道分散、临时变更时无法快速静音。M08 把 Alertmanager 的路由、静默、抑制、通知渠道与模板能力产品化，让运维工程师无需手写 YAML 即可完成告警收敛与通知管理。

### 2.2 去掉「直接挂载配置文件的逃生门」

原 M08 历史上曾支持整份 `alertmanager.yml` 上传/粘贴、历史版本「重新挂载」、手写/平台管理模式切换等逃生门。这些能力会导致：

- `route` / `receiver` 段出现「手写 + 平台生成」双作者，配置口径冲突；
- 历史手写 receiver、未引用渠道混入产物，导致校验与对账混乱；
- 用户绕过平台表单后，平台无法保证配置安全与版本一致。

因此，本模块**彻底取消整份配置文件挂载逃生门**：`alertmanager.yml` 的唯一作者是平台，由后端根据路由规则树、抑制规则、被引用渠道统一生成；告警配置页只读展示，不再提供导入/手写/重新挂载入口。

### 2.3 新增内部 Reload 子模块

 historically，M08 生成配置后依赖外部模块（M09）完成下发与 reload。在新架构下，M08 需要具备**内部的配置应用与 Reload 能力**：

- 在路由/抑制等配置保存并校验通过后，由 M08 内部子模块直接将 `alertmanager.yml` 原子写入配置路径，并触发 Alertmanager reload；
- 校验 reload 结果，记录 reload 历史；
- reload 失败时自动回退到上一生效配置并再次 reload，保障 Alertmanager 可用性；
- 同时向合并后的 M09 配置同步服务写入配置快照，用于版本留痕与未来边缘分发。

### 2.4 与合并后 M09 的关系

- M08 是 `alertmanager.yml` 的**内容 Owner**；
- M08 内部 Reload 子模块负责**中心 Alertmanager 的即时应用**；
- M09（合并后）的简化配置同步服务负责**配置快照持久化与面向采集节点的配置包管理**；M08 将生效的 `alertmanager.yml` 同步给 M09 用于留痕与统一配置视图。

### 2.5 一句话定位

> M08 回答的问题是：**「告警产生后，如何按规则通知、如何临时静默、如何抑制风暴，并确保配置变更安全生效」**。

## 3. 核心概念

### 3.1 `alertmanager.yml` 平台生成产物

- `alertmanager.yml` 不是用户手写文件，而是平台根据路由规则、抑制规则、通知渠道生成的产物；
- 生成后必须经过 `amtool check-config` 校验；
- `receivers` 段只物化被路由树引用的渠道，名称固定为 `notify-<渠道ID>`，未引用渠道不进入产物。

### 3.2 `route` 段唯一作者 = 平台

- 路由规则在「路由规则」页以树形表单维护；
- 前端只提交 `{base_checksum, route_tree}`，后端统一生成 YAML；
- 不存在手写/导入/模式切换等入口。

### 3.3 通知渠道与通知模板

- **通知渠道**：飞书/钉钉/企业微信/自定义 Webhook；渠道无启停字段；IM 类必须绑定模板；Webhook 禁止模板；删除被引用渠道返回 409；
- **通知模板**：Go template 可变实体，不进入 `alertmanager.yml`；内置模板只读，自定义模板可增删改；被渠道绑定后禁止删除。

### 3.4 静默 vs 抑制

- **静默（Silence）**：临时手动屏蔽通知，调用 Alertmanager v2 API 即时生效，属于运行时状态；
- **抑制（Inhibition）**：规则驱动的自动收敛，例如网域离线时抑制该域内次生告警；与路由规则共用同一生成器与 reload 链路。

### 3.5 告警事件单一事实源

- 以 `alert_events` 事件表作为「当前告警」与「历史告警」的唯一事实源；
- 事件由 Alertmanager webhook 留痕 + 分钟级对账写入；
- Prometheus `/api/v1/alerts` 规则求值态与 AM `/api/v2/alerts` 通知状态四态降级为参考/兼容数据源。

### 3.6 内部 Reload 子模块

- M08 内置的「配置应用 + Reload」能力；
- 负责原子写配置、触发 reload、验证结果、记录日志、失败回退；
- 不依赖外部人工确认，但保留只读历史用于排障。

## 4. 目标用户与使用场景

### 4.1 目标用户

| 用户角色 | 关注点 | 典型操作 |
|----------|--------|----------|
| 运维工程师 | 通知渠道、静默、当前告警 | 配置渠道、创建静默、查看告警 |
| 运维架构师 | 路由规则、抑制规则、告警风暴 | 配置路由树、预置抑制规则 |
| 值班工程师 | 告警是否通知、是否被静默 | 查看当前/历史告警、导出 CSV |

### 4.2 典型使用场景

#### 场景 1：配置告警通知渠道

- **角色**：运维工程师
- **触发**：平台首次部署，需要把告警发到飞书/钉钉
- **目标**：创建通知渠道并绑定模板
- **成功标准**：告警触发后指定渠道收到格式正确的通知

#### 场景 2：配置告警路由规则

- **角色**：运维架构师
- **触发**：不同团队需要按 severity/team/network_domain 分流告警
- **目标**：在路由规则页编辑树形规则
- **成功标准**：后端生成合法 `alertmanager.yml`，内部 Reload 子模块成功应用，告警按规则路由

#### 场景 3：临时静默已知故障

- **角色**：运维工程师
- **触发**：计划内数据库迁移
- **目标**：创建静默规则
- **成功标准**：静默期间匹配告警不再通知，过期自动恢复

#### 场景 4：抑制告警风暴

- **角色**：运维架构师
- **触发**：某网域整体离线，大量 `up=0` 告警爆发
- **目标**：启用/配置抑制规则
- **成功标准**：只保留根因告警，次生告警被抑制

#### 场景 5：查看当前告警与历史告警

- **角色**：值班工程师
- **触发**：告警触发后确认状态
- **目标**：查看告警是否仍在发生、是否被静默/抑制、何时恢复
- **成功标准**：当前告警/历史告警同源展示，支持筛选与导出 CSV

## 5. 功能需求

### 5.1 Alertmanager 配置管理

#### FR-01：默认配置 Seed

- 数据库初始化时若不存在已生效配置，幂等写入默认 `alertmanager.yml`；
- 默认配置包含根路由、`default` 空接收人、全局参数。

#### FR-02：路由规则生成

- 「路由规则」页以树形表单维护路由；
- 前端提交 `{base_checksum, route_tree}`；
- 后端校验结构、matcher、时长、接收人可达性；
- 生成 `route` 段并整份重建 `alertmanager.yml`（`global` + `route` + 保留当前抑制规则 + 被引用渠道的 receivers）。

#### FR-03：抑制规则集成

- 「告警抑制」页独立维护 `inhibit_rules`；
- 保存时与路由共用同一生成器，生成整份 `alertmanager.yml`；
- 显式空数组表示清空抑制规则；
- 保存时不得覆盖路由段。

#### FR-04：`amtool` 校验

- 任何保存动作生成 YAML 后，必须执行 `amtool check-config` 等价校验；
- 校验失败不落库、不 reload，返回行级错误；
- 校验通过后写入 `AlertmanagerConfigSnapshot` 并标记为当前版本。

#### FR-05：告警配置页只读

- 「告警配置」页只读展示当前生效 `alertmanager.yml` 与历史版本；
- 不提供整份导入、手写、重新挂载、模式切换入口。

#### FR-06：只读配置历史

- 保留最近生效的 `alertmanager.yml` 历史版本，用于排障与审计；
- 历史版本只读展示，不支持回滚或恢复为当前版本。

#### FR-07：内部 Reload 子模块（新增）

- 配置校验通过后，由 M08 内部子模块执行以下动作：
  1. 将新的 `alertmanager.yml` 原子写入配置路径（temp + rename）；
  2. 触发 Alertmanager reload（`POST /-/reload` 或 `SIGHUP`）；
  3. 等待并验证 reload 结果（健康检查 / reload 指标 / 配置加载状态）；
  4. 记录 `AlertmanagerReloadLog`（时间、操作人、配置版本、状态、失败原因）；
  5. 若 reload 失败，自动将上一生效配置回写并再次 reload，保障 AM 可用性。
- reload 子模块可被 M08 自身调用，也可接收 M09 配置同步服务的触发。

#### FR-08：配置快照同步到 M09

- 生效的 `alertmanager.yml` 及其校验和同步写入 M09 配置同步服务；
- 用于统一配置视图、版本留痕与未来边缘 Alertmanager 分发。

### 5.2 通知渠道与通知模板

#### FR-09：通知渠道管理

- 支持飞书、钉钉、企业微信、自定义 Webhook 的增删改查；
- Webhook 地址做 SSRF 校验（默认拒绝私网/环回/link-local/云元数据，可显式放行内网）；
- 渠道无 `enabled` 字段；
- 删除被路由引用的渠道返回 409 并提示引用位置。

#### FR-10：通知模板管理

- 按渠道类型分 Tab；
- 内置模板只读、可复制；自定义模板可新建/编辑/复制/删除；
- 模板为可变实体，不进入 `alertmanager.yml`；
- 被渠道绑定的模板禁止删除。

#### FR-11：接收人物化

- `receivers` 仅物化 `default`（空接收人）与被当前路由树引用的渠道 `notify-<渠道ID>`；
- 未引用渠道不生成 receiver；
- 通知渲染桥按渠道 ID 实时读取模板与渠道参数。

#### FR-12：通知渲染桥

> API 版本口径（D38）：`/api/v1/webhooks/*` 为语义路径，实施期统一挂载 `/api/v3/platform/*` 前缀，权威路径以 api-contract-snapshot-v3 为准。

- `POST /api/v1/webhooks/notify?id=<渠道ID>`：按渠道类型渲染并发送通知；
- IM 类按模板渲染并加签；自定义 Webhook 原样转发告警内容；
- 无内部令牌，仅接受渠道 ID。

### 5.3 路由规则管理

#### FR-13：树形路由编辑

- 支持新增/编辑/删除路由节点；
- 支持标签匹配条件（`severity=critical`、`team=sre`、`network_domain_id=xxx` 等）；
- 支持指定接收人、分组键、等待/间隔/重复时间、`continue`、启用状态；
- 根路由锁定不可删除。

#### FR-14：乐观锁校验

- 保存时提交 `base_checksum`；
- 若服务端当前版本校验和不一致，返回 409 提示配置已过期，需刷新后重试。

#### FR-15：接收人候选集

- 路由表单中接收人下拉候选 = `default` ∪ 全部已创建渠道 `notify-<渠道ID>`；
- 保存时只物化被引用的渠道。

### 5.4 静默管理

#### FR-16：静默规则 CRUD

- 创建/列表/删除 Alertmanager 静默规则；
- 调用 Alertmanager v2 API 即时生效，不进配置 reload 链路；
- 支持按标签匹配、起止时间、原因说明。

#### FR-17：静默网域作用域过滤

- 创建静默规则时，matcher 中的 `network_domain_id` 必须落在当前用户被授权网域集合内；
- 越权网域静默请求被拒绝。

### 5.5 告警抑制规则

#### FR-18：独立抑制规则页面

- 提供「告警抑制」独立页面；
- 支持新增/编辑/删除/启停通用抑制规则；
- 规则字段：`source_matchers`、`target_matchers`、`equal`、`enabled`。

#### FR-19：预置抑制场景

- 预置「网域离线时抑制该域内 `inhibitable=true` 次生告警」规则；
- 用户可启停、调整参数，但不可删除系统预置规则。

#### FR-20：抑制保存不覆盖路由

- 保存抑制规则时，整份重建 `alertmanager.yml` 但保留当前路由段；
- 路由保存与抑制保存分配置段 pending 提示（`route_changed` / `inhibit_rules_changed`）。

### 5.6 告警事件留痕与对账

#### FR-21：内置 Webhook 留痕

- 平台为每个 receiver（含 `default`）追加内置 webhook `POST /api/v1/webhooks/alerts`；
- 对 Alertmanager 永远返回 2xx；
- 由平台生成，不可删除。

#### FR-22：分钟级对账

- 定时拉取 Alertmanager 活跃告警与 uptime；
- 补插漏记、关闭消失行、对齐静默/抑制状态；
- 按 `fingerprint + starts_at` 去重（`occurrence_key`）。

#### FR-23：当前告警

- 告警状态页默认页签展示事件表未结三态：告警中 / 静默中 / 抑制中；
- 支持按网域/告警名/实例/状态筛选与分页；
- 首页告警卡右栏同源展示。

#### FR-24：历史告警

- 独立页面展示告警发生历史；
- 一行 = 一次告警发生，七态（告警中 / 静默中 / 抑制中 / 已恢复 / 静默期间结束 / 抑制期间结束 / 已结束但恢复时间未知）；
- 支持按网域/告警名/实例/状态/描述/时间范围筛选，并导出 CSV。

#### FR-25：实例名回填

- 告警列表「实例名」按告警标签 `resource_id` 回连 M07/M01 资源表回填；
- 「采集地址」列展示 Prometheus `instance` 标签值；
- 缺失时显示 `-`。

### 5.7 通知状态代理（兼容保留）

#### FR-26：AM 通知状态代理

- 保留 Alertmanager `/api/v2/alerts` 代理；
- 返回 active / silenced / inhibited / unprocessed 四态；
- 事件表对账内部消费，前端不再作为主视图。

## 6. 非功能需求

### 6.1 配置安全与一致性

#### NFR-01：`route` 段唯一作者

- 任何场景下不允许手写 `route` 段进入生效配置；
- 平台生成的 `alertmanager.yml` 是 `route` 的唯一来源。

#### NFR-02：取消整份配置文件挂载逃生门

- 删除整份 YAML 上传/粘贴、历史版本重新挂载、手写/平台模式切换、`route-setting` 端点；
- 告警配置页只读，路由规则页是唯一的 `route` 编辑入口。

#### NFR-03：内部 Reload 原子性与安全性

- 写配置路径使用 temp + rename，避免中间态文件；
- reload 失败必须回退到上一生效配置并再次 reload；
- reload 记录持久化，包含配置版本、时间、结果、错误信息。

#### NFR-04：配置历史只读

- `AlertmanagerConfigSnapshot` 与 `AlertmanagerReloadLog` 只读；
- 不提供回滚或恢复到历史版本的接口。

#### NFR-05：校验即守门

- 任何进入 reload 的配置必须先通过 `amtool check-config`；
- 校验失败不得触发 reload，不得覆盖当前生效文件。

### 6.2 数据隔离与安全

#### NFR-06：静默/抑制作用域隔离

- 静默规则创建时强制校验 `network_domain` 标签属于用户授权集合；
- 抑制规则中的网域 matcher 同样受授权集合约束。

#### NFR-07：SSRF 防护

- Webhook URL 默认禁止访问私网、环回、link-local、云元数据地址；
- 提供显式开关放行内网，但需管理员权限。

#### NFR-08：敏感信息保护

- 渠道密钥/加签密钥加密存储；
- 接口与日志不返回明文密钥。

### 6.3 性能与可用性

#### NFR-09：告警事件保留策略

- `alert_events` 保留 180 天；
- 未结行永不自动清理；
- 已结束行按保留策略清理。

#### NFR-10：对账与 reload 性能

- 分钟级对账任务单次执行 ≤ 30 秒；
- reload 操作在配置保存后 5 秒内完成（含验证）。

#### NFR-11：用户语言一致性

- 用户界面统一使用「路由规则 / 静默 / 抑制 / 通知渠道 / 通知模板 / 当前告警 / 历史告警」等业务语言；
- 技术术语（`inhibit_rules`、`route_tree`、`receiver` 等）仅出现在折叠区、代码注释或接口文档。

#### NFR-12：错误提示可执行

- `amtool` 校验失败、reload 失败、渠道被引用、静默越权等错误须给出下一步操作指引。

## 7. 数据模型概述

### 7.1 核心实体

| 实体 | 说明 | 关键属性 |
|------|------|----------|
| Route | 路由规则树节点 | 父节点、名称、matcher、接收人、分组、时间参数、启用状态 |
| InhibitionRule | 抑制规则 | 名称、source_matchers、target_matchers、equal、enabled |
| NotifyChannel | 通知渠道 | 名称、类型、webhook_url、密钥、默认模板、被引用次数 |
| NotifyTemplate | 通知模板 | 名称、渠道类型、内容、是否内置、绑定渠道数 |
| AlertmanagerConfigSnapshot | 配置快照 | 内容、校验和、生成时间、是否当前版本 |
| AlertmanagerReloadLog | Reload 记录 | 配置版本、时间、操作人、状态、失败原因 |
| Silence | 静默规则（运行时） | ID、matcher、起止时间、原因、创建人、状态 |
| AlertEvent | 告警事件 | fingerprint、occurrence_key、状态、触发/恢复/关闭时间、标签、资源名 |

### 7.2 核心关系

- **Route 树**：自引用树形结构，根路由唯一；
- **NotifyChannel → NotifyTemplate**：IM 渠道必须绑定一个模板；
- **Route → NotifyChannel**：通过 `receiver` 字段引用；
- **AlertmanagerConfigSnapshot → AlertmanagerReloadLog**：一次配置版本可对应多次 reload 尝试；
- **AlertEvent**：由 webhook + 对账写入，与 Silence/InhibitionRule 状态联动。

## 8. 关键流程

### 8.1 路由/抑制保存与内部 Reload 流程

1. 用户在「路由规则」或「告警抑制」页编辑并保存。
2. 后端校验 `base_checksum` 乐观锁。
3. 后端生成整份 `alertmanager.yml`。
4. 执行 `amtool check-config` 校验。
5. 校验失败：返回行级错误，流程终止。
6. 校验成功：
   - 写入新的 `AlertmanagerConfigSnapshot` 并标记为当前版本；
   - 调用内部 Reload 子模块；
   - 原子写入配置文件；
   - 触发 Alertmanager reload；
   - 验证 reload 结果；
   - 记录 `AlertmanagerReloadLog`；
   - 若失败，自动回退上一配置并再次 reload。
7. 将生效配置快照同步到 M09 配置同步服务。

### 8.2 通知渠道/模板变更流程

1. 用户创建/编辑/删除渠道或模板。
2. 渠道变更后，仅影响被路由引用的 receiver 物化结果；
3. 模板变更即时生效，不产生 M09 变更单；
4. 若渠道被路由引用，删除请求返回 409。

### 8.3 静默管理流程

1. 用户创建静默规则，填写 matcher、起止时间、原因。
2. 服务端校验 matcher 中的网域在授权集合内。
3. 调用 Alertmanager v2 API 创建静默规则。
4. 静默即时生效，不进配置 reload 链路。
5. 用户可列表/删除正在生效的静默规则。

### 8.4 告警事件写入与对账流程

1. Alertmanager 将通知发送到平台内置 webhook `POST /api/v1/webhooks/alerts`。
2. 平台解析并写入 `AlertEvent`。
3. 分钟级对账任务拉取 AM 活跃告警：
   - 补插漏记；
   - 关闭已消失行；
   - 对齐静默/抑制状态。
4. 当前告警/历史告警页面从 `AlertEvent` 读取。

### 8.5 告警查询流程

1. 用户访问「当前告警」或「历史告警」页面。
2. 后端按用户授权网域过滤。
3. 返回事件表数据，并按规则求值/通知状态补充参考信息。
4. 历史告警支持按当前筛选导出 CSV。

## 9. 验收标准

### 9.1 功能验收

- [ ] 「告警配置」页只读展示当前生效 `alertmanager.yml`，无导入/手写/重新挂载/模式开关入口。
- [ ] 「路由规则」页可编辑树形路由，保存时由后端生成 YAML，不暴露手写入口。
- [ ] 路由保存支持 `base_checksum` 乐观锁校验，过期返回 409。
- [ ] `alertmanager.yml` 生成后必须经过 `amtool check-config` 校验；失败不落库、不 reload。
- [ ] 内部 Reload 子模块实现原子写配置、触发 reload、验证结果、记录日志；失败时自动回退上一配置。
- [ ] 生效配置快照同步到 M09 配置同步服务。
- [ ] 通知渠道支持飞书/钉钉/企业微信/自定义 Webhook 的 CRUD；Webhook URL 做 SSRF 校验。
- [ ] IM 渠道必须绑定模板；Webhook 禁止模板；被路由引用的渠道不可删除。
- [ ] 通知模板为可变实体，不进入 `alertmanager.yml`；被绑定模板不可删除。
- [ ] 静默规则通过 AM v2 API 即时生效；创建时校验网域授权。
- [ ] 抑制规则独立页面维护，与路由保存共用生成器但不互相覆盖。
- [ ] 预置「网域离线抑制次生告警」规则，用户可启停/调整。
- [ ] 告警事件由 webhook 留痕 + 分钟级对账写入 `alertEvent`。
- [ ] 当前告警展示事件表未结三态（告警中 / 静默中 / 抑制中）。
- [ ] 历史告警支持七态展示、多维度筛选、CSV 导出。
- [ ] 告警列表实例名按 `resource_id` 回连资源表回填。

### 9.2 非功能验收

- [ ] 不存在整份 `alertmanager.yml` 上传/粘贴/重新挂载的接口或入口。
- [ ] `route` 段唯一来源是平台生成的路由规则树。
- [ ] reload 操作使用原子写，失败可回退，5 秒内完成（含验证）。
- [ ] 配置历史与 reload 日志只读，不支持回滚。
- [ ] 渠道密钥加密存储，不在接口/日志中泄露。
- [ ] 静默/抑制规则严格按用户授权网域作用域过滤。
- [ ] `alert_events` 保留 180 天，未结行不清理。
- [ ] 用户界面统一使用业务语言，错误提示给出可执行指引。

## 10. 依赖与风险

### 10.1 模块依赖

| 依赖方 | 依赖内容 | 说明 |
|--------|----------|------|
| Module 09（合并后） | 配置快照留痕与查询代理 | M08 将生效的 `alertmanager.yml` 快照同步给 M09 仅用于留痕与统一配置视图，不扇出边缘（D31）；规则求值态参考数据由 M09 查询面代理（原 M02 已并入） |
| Module 06 | 网域授权数据 | 静默/抑制规则需要校验用户授权网域 |
| Module 07 / M01 | 资源台账与规则 | 告警列表实例名回填依赖 M07/M01；告警规则内容不归 M08 |
| Alertmanager 二进制 | amtool / reload / v2 API | 本模块依赖 AM 提供校验、reload、静默、通知状态查询能力 |

### 10.2 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 去掉文件挂载逃生门后，高级用户无法手写复杂配置 | 部分复杂路由场景无法满足 | 在路由规则页逐步增强表单能力（分组、正则、子路由、continue 等） |
| 内部 Reload 子模块失败且回退也失败 | Alertmanager 不可用 | 增加告警/健康检查；保留上一生效配置备份；reload 失败通知管理员 |
| 路由与抑制保存并发冲突 | 配置丢失或覆盖 | `base_checksum` 乐观锁；保存前校验当前版本 |
| 告警事件对账延迟 | 当前告警状态不准确 | 分钟级对账 + webhook 留痕双保险；对账失败可观测 |
| 历史 PRD 中已删除的逃生门接口仍有代码残留 | 安全与口径风险 | 重写 SRS 后同步清理相关 API 端点、模型、页面 |
