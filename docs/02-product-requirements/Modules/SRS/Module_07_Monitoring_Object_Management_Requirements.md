## 1. 文档目的

本文档用**便于人理解的语言**记录 M07 模块的业务需求、功能需求与非功能需求。它站在产品经理和运维经理的视角，说明「我们需要监控谁」「这些对象如何组织」「治理手段是什么」，并为后续概要设计、详细设计、开发、测试提供依据。

本文档不直接定义 API 字段级别的技术契约（历史技术 PRD 已覆盖），而是回答：**这个模块为什么存在、要解决什么问题、必须具备哪些能力、做到什么程度算合格**。

## 2. 业务背景

### 2.1 我们在监控谁

MetricCenter 的监控对象是线上各类 IT 资源。在真实运维环境中，这些资源的信息分散在：

- CMDB（如腾讯蓝鲸）
- 供应商交付的 Excel 清单
- 各应用团队自行维护的台账
- 口头交接或临时登记

结果是：同一台机器有多个名字、应用归属 missing、标签口径不统一，导致后续采集配置、告警分组、业务看板都无从对齐。

**M07 的定位**：建立 MetricCenter 内部的「监控对象台账」（即线上 CMDB），作为平台的数据基座。先定义清楚有哪些对象、它们属于谁、该打什么标签，再让采集策略（M01）和配置下发（M09）基于这份统一台账工作。

### 2.2 一句话定位

> M07 回答的问题是：**「我们在监控谁」**。

它不负责「怎么采」「怎么告警」「怎么下发配置」，只负责「监控对象本身的数据对不对、归属清不清楚、标签受不受控」。

## 3. 核心概念

### 3.1 监控对象（CI）类型

本模块管理六类监控对象：

| 类型 | 例子 | 一句话说明 |
|------|------|-----------|
| 主机 | Linux/Windows 服务器、虚拟机 | 运行 OS 与 Exporter 的实体 |
| 数据库 | MySQL、Redis、Oracle、PostgreSQL | 以数据存储/查询为主语义的实例 |
| 中间件 | Kafka、Elasticsearch、Nginx、Zookeeper | 消息、网关、搜索、协调类组件 |
| 应用服务 | 接口包装系统、数据目录系统 | 平台下的子系统/服务 |
| 接口服务 | `/api/v1/authorize`、`/api/v2/query` | 应用服务对外暴露的数据类 API 端点 |
| 其他监控对象 | K8s 集群级端点、网络设备、GPU、自定义 HTTP 端点 | 当前未大规模使用、预留扩展的兜底类型 |

### 3.2 平台、应用服务、接口服务的关系

这是本模块最关键的业务定义。

#### 平台（Platform）

- **业务含义**：一个需要整体进行等保、安测、统一运维的业务平台。例如「公共数据授权运营平台」。
- **组织定位（第一原则）**：平台是**运维组织架构的根节点**——运维组织按「**平台 → 应用运维团队 → 应用**」划分：先有平台，再由平台下的应用运维团队做组织保障，平台由「该有的若干个应用」聚合而成。因此**应用不是孤立、可随意定义的实体**，而是平台的组织单元。
- **管理主体**：平台团队（运维工程师/运维架构师）自维护。平台由哪些应用组成，由平台团队自己定义。
- **在监控中的价值**：
  - **组织归属与告警分发**：平台是**第一维度**——告警发生后先归属到平台（对应哪个平台的运维团队），再下钻到应用/实例；
  - **管理视角聚合**：管理层看「某个平台整体健不健康」。两者是不同用途，不可互相替代。

#### 应用服务（Application）

- **业务含义**：平台下的子系统或服务。例如平台上的「接口包装系统」「数据目录系统」。
- **归属约束（硬性）**：应用**必须归属于至少一个平台**，且**恰有一个主平台**。系统不接受「无平台归属的应用」——登记应用时即须选定所属平台（首个即主平台），存量/编辑场景也不允许把应用的平台归属清空。
- **管理主体**：应用团队或供应商。一个平台可由多个应用团队或供应商分别开发和部署各自的应用服务。
- **运维组织保障**：
  - 一线运维工程师：发现告警、初步定位。
  - 二线应用运维工程师：负责深入排查和处理问题。
- **在监控中的价值**：故障定位时，先落到「哪个应用服务」，再下钻到具体实例或接口。

#### 接口服务（Interface Service）

- **业务含义**：应用服务承载的、对外暴露的数据类 API 端点。例如「接口包装系统」对外提供的 `/api/v1/authorize`。
- **核心用途**：用于 blackbox 拨测，验证接口可用性。
- **在监控中的价值**：反映业务接口的可用性，是业务可用性监控的直接载体。

#### 关系总结

```
平台（运维组织根节点 / 等保·安测·统一运维视角）
  └── 应用服务 N 个（平台的组织单元；由平台团队定义，应用团队/供应商部署）
        └── 接口服务 M 个（应用服务对外暴露的数据 API，用于拨测）
```

> **约束方向**：组成关系自下而上不可断裂——接口服务必须归属应用服务，应用服务必须归属平台。反向（平台可无应用）在组织上成立（新平台尚未上线应用），正向（应用无平台）**不成立**。

### 3.3 受控标签

为了在多团队、多供应商、多应用的场景下保证监控数据口径一致，本模块引入**受控标签**机制：

- **类型级标签**：通过「标签模板」按资源类型定义映射规则，例如「主机的 `app_code` 字段 → `app` label」。所有该类型实例自动生效。
- **实例级标签**：仅对业务类型资源（应用服务 / 接口服务）开放自定义标签入口；静态资源（主机 / 数据库 / 中间件 / 其他监控对象）只读展示，避免在 CMDB 治理侧之外二次打标造成口径混乱。
- **来源标注**：每条标签都标注来源（system / user / cmdb），让用户看得见「这个标签从哪来」。

### 3.4 字典生命周期

平台、应用、业务三本字典是监控标签取值的权威。编码一旦被资源或应用归属引用，就会进入历史指标与告警序列，因此字典不是普通配置，而是**需要治理的编码资产**。

字典条目的生命周期有四种状态：

| 状态 | 含义 | 是否可选 | 说明 |
|------|------|----------|------|
| 启用 | 正常可用 | 是 | 可被新增 / 编辑资源引用 |
| 停用 | 暂停新增引用 | 否 | 存量引用保留，历史数据不受影响 |
| 已合并 | 编码作为别名保留 | 否 | 引用已迁移到目标编码，源编码不再可选 |
| 已撤销 | 编码永久失效 | 否 | 仅零引用条目可撤销，编码不释放、不复用 |

两条硬性规则：

1. **编码一经引用，永不物理删除、永不复用**——避免同一编码在不同时期指向不同对象，导致历史时序语义漂移。
2. **零引用可撤销，有引用只能停用或合并**——从未投入使用的错建条目可以清理；已经进入监控数据的编码必须保留可追溯性。

> 系统不预置任何业务字典，包括历史上的 `infra` 兜底条目。所有字典由运维按实际组织与业务登记。

### 3.5 资源能力属性与通用扩展属性

资源除了「身份」与「归属」之外，还有一类**描述它具备什么能力**的事实——例如一台主机是否带 NPU、是否带 GPU、是否有本地磁盘阵列。这类属性不参与标签治理，但对「用什么采集器采」至关重要：M01 需要按这些属性判断某个资源属于哪种监控对象类型。

本模块把它们分成两层承载，**固定字段负责常见能力、通用扩展属性负责长尾能力**：

| 层次 | 承载方式 | 适用场景 | 举例 |
|------|----------|----------|------|
| **常见能力（一等字段）** | 资源表上的固定布尔字段 | 取值稳定、需要筛选 / 导入 / 建索引的高频能力 | 主机 `has_npu`、`has_gpu` |
| **长尾能力（通用扩展属性）** | `ResourceAttribute`（资源 × key × value） | 种类不可预知、由用户按需扩展的能力或规格 | `dpu_model`、`smart_nic`、`gpu_memory_gb` |

三条边界：

1. **能力属性只描述事实，不描述采集策略**。资源表只回答「这台机器有没有 NPU」，不回答「用什么 exporter 采、多久采一次」——后者属于 M01。
2. **M07 不感知 `monitor_type`**。本模块不存监控对象类型，也不做类型推导；类型定义与推导规则由 M01 维护，M07 只提供可被规则读取的属性字段。
3. **扩展属性不是标签**。`ResourceAttribute` 用于判定「这是什么资源」，不同于 `ResourceLabel`（用于时序数据的维度聚合）；两者互不替代，也不互相写入。

## 4. 目标用户与使用场景

### 4.1 目标用户

| 用户角色 | 关注点 | 典型操作 |
|----------|--------|----------|
| 运维经理 | 监控覆盖率、资源归属是否清晰 | 查看资源列表、统计未监控资源 |
| 运维工程师 | 批量录入资源、维护标签 | Excel 导入、手动登记、编辑标签模板 |
| 应用运维工程师 | 应用服务与接口服务的可用性 | 登记应用服务、登记拨测接口 |
| 运维工程师 / 运维架构师（字典自维护） | 平台 / 应用 / 业务三者自维护 | 登记维护平台字典、应用字典、业务分组，维护应用↔平台归属 |
| 平台管理员 | 字典审计与纠错 | 查看引用数、处理错建/重码条目的停用、合并与撤销，**不承担日常维护、不预置业务字典** |
| 运维架构师 | 标签治理、数据一致性 | 定义标签模板、审计标签来源 |

### 4.2 典型使用场景

#### 场景 1：新平台上线，批量录入资源

- **角色**：运维工程师
- **触发**：供应商交付 300 台主机、50 个 MySQL 实例、10 个应用服务
- **目标**：一次性录入平台监控对象
- **成功标准**：
  - 按类型导入成功
  - 资源可按平台/应用/业务筛选
  - 导入错误有明确行号、字段、原因提示

#### 场景 2：新应用上线，登记应用与接口服务

- **角色**：应用运维工程师
- **触发**：新应用上线，需要配置拨测与指标采集
- **目标**：建立应用服务与拨测接口的台账
- **成功标准**：
  - 应用服务挂到平台下
  - 接口服务挂到应用下
  - Blackbox 拨测任务可从接口服务列表中选取目标

#### 场景 3：统一业务标签口径

- **角色**：运维架构师
- **触发**：各应用团队自行埋点，标签命名不统一
- **目标**：通过标签模板强制统一关键标签
- **成功标准**：
  - 新建采集 Job 时自动带出 `app`、`biz`、`env`、`platform` 等标签
  - 查询可按业务维度聚合

#### 场景 4：发现未监控资源

- **角色**：运维经理
- **触发**：例行检查监控覆盖率
- **目标**：发现监控缺口
- **成功标准**：
  - 资源列表可筛选「未监控」和「已下发未采到」
  - 三态 badge（采集中 / 已下发未采到 / 未监控）清晰可辨

## 5. 功能需求

### 5.1 资源台账管理

#### FR-01：六类资源台账维护

- 系统必须支持维护主机、数据库、中间件、应用服务、接口服务、其他监控对象六类资源。
- 业务归属不是资源登记的前置条件：主机 / 数据库 / 中间件 / 应用服务可留空（后续补录或批量改归属），接口服务必填，其他监控对象与应用归属二选一；空值不注入 `biz` 标签。
- 每类资源有独立的列表页（Tab 切换）。
- 支持新增、编辑、删除、查看详情。
- 支持按关键字、网域、平台、应用、业务、运行状态、采集状态筛选。

#### FR-02：应用服务与接口服务差异化登记

- 应用服务登记字段：服务名、健康检查 URL、协议、指标端点、端口、负责人、运维人员、上线时间、所属平台/应用/业务等。
- 接口服务登记字段：接口名、接口 URL、所属应用服务、业务、环境等。
- 健康检查 URL 是 blackbox 拨测的目标地址，必须必填且格式正确。
- 同一应用服务可登记多个接口服务。

#### FR-03：运行状态维护

- 资源运行状态包括：运行中、已停止、维护中。
- 已停止的资源在下一配置生成周期从采集目标中移除。
- 状态变更需记录审计日志。

#### FR-04：采集状态感知

- 资源列表需展示采集状态三态：采集中、已下发未采到、未监控。
- 「已下发未采到」需高亮提示。
- 采集状态数据由 M01（选中关系）和 M09（健康度聚合接口，原 M02 已并入）提供，M07 只读消费。

#### FR-05：删除与引用保护

- 删除资源前需二次确认。
- 若资源被采集 Job 引用，允许软删放行，但需回显引用 Job 数量并提供跳转入口。
- 删除后同步回收引用 Job 中的该资源。

#### FR-06：其他监控对象兜底登记

- 为 K8s 集群级端点、网络设备、GPU、自定义 HTTP 端点等提供统一登记入口。
- 用户只需填写目标名称、端点地址、端点类型，无需理解 Exporter 术语。
- 容器 / Pod / K8s 节点等动态发现产物不在本模块登记。

### 5.2 平台、应用、业务字典管理

#### FR-07：平台字典维护

- 由运维工程师 / 运维架构师自助维护平台编码、平台名称、描述、状态。
- 平台编码创建后不可修改；停用不删除，不提供物理删除入口。
- 平台是**运维组织的第一划分维度**：既是资源的归属维度，也是告警组织归属与分发的第一维度。
- 停用平台后禁止新资源 / 新应用引用，存量关联保留历史值。
- 平台列表展示实时引用数（资源数 + 应用平台关联数）；引用数为零的条目可撤销，有引用的条目只能停用或合并，详见 §5.7。

#### FR-08：应用字典维护

- 由运维工程师 / 运维架构师自助维护应用编码、应用名称、描述、状态，以及**应用↔平台归属**。
- 应用编码创建后不可修改；停用不删除，不提供物理删除入口。
- 应用与平台支持多对多关联：一个应用可属于多个平台，一个平台可包含多个应用。
- **硬性约束（必须由服务端强制，不能只靠界面校验）**：
  - 每个应用**至少归属一个平台**——登记应用时即须选定所属平台（可多选），删除应用与最后一个平台的关联被拒绝；
  - 每个应用**恰有一个主平台**——首个关联由系统自动置为主平台，同一应用至多一个主平台；
  - **转移主平台须显式操作**——删除主平台关联前，必须先把其他平台设为主平台；系统不做「自动提升」，避免静默改变告警派单归属。
- 应用编辑抽屉只保留**一个「关联平台」多选字段**：已选平台以标签展示，标签左侧星标标识主平台，点击星标即可切换主平台；只选一个平台时自动成为主平台。
- 应用列表展示实时引用数（引用该应用的资源数）；引用数为零的条目可撤销，有引用的条目只能停用或合并，详见 §5.7。

#### FR-09：业务分组字典维护

- 由运维工程师 / 运维架构师自助维护业务编码、业务名称、描述、状态。
- 业务编码创建后不可修改。
- 停用业务后禁止新资源引用，存量资源保留历史值。
- **系统不预置任何业务字典**：全新部署时业务字典为空，不存在 `infra` 或其他兜底条目；资源登记不依赖业务字典先存在，业务可留空后补，表单内提供快捷登记入口。
- 资源登记时业务归属按类型分化：主机 / 数据库 / 中间件 / 应用服务可留空；接口服务必填；其他监控对象与应用归属二选一。
- 业务列表展示实时引用数（引用该业务的资源数）；引用数为零的条目可撤销，有引用的条目只能停用或合并，详见 §5.7。

#### FR-10：平台-应用-资源级联关系

- 资源登记表单支持先选平台、再选应用（按平台过滤应用列表）。
- 应用服务资源必须关联应用；因应用必归属平台，应用服务资源的平台归属**可稳定派生**，无需重复填写。
- 接口服务资源通过所属应用间接关联平台，同上。
- 静态资源（主机 / 数据库 / 中间件 / 其他监控对象）的应用归属可能不唯一或为空，故其平台归属**须显式填写**（可留空，留空时按所属应用主平台兜底）。

### 5.3 标签模板与受控标签

#### FR-11：标签模板管理

- 按资源类型定义「资源字段 → Prometheus Label」的映射规则。
- 六类资源各预置一套默认模板。
- 支持基于默认模板克隆创建自定义模板。
- 支持编辑、删除自定义模板；默认模板只读。

#### FR-12：映射批量编辑

- 标签模板映射支持表格批量编辑。
- 用户在本地草稿中连续新增/修改/删除多行映射，最后统一保存。
- 保存时进行整组校验：目标标签不能冲突、不能覆盖 Prometheus 内置 label。

#### FR-13：标签来源与冲突管理

- 标签来源分为 system（来自模板）、user（手动添加）、cmdb（外部 CMDB 同步）。
- 同 key 冲突时优先级：cmdb > user > system。
- system 标签为系统保护标签，用户不可覆盖。

#### FR-14：实例级自定义标签

- 仅应用服务和接口服务资源支持手动添加/编辑/删除 user 标签。
- 静态资源（主机、数据库、中间件、其他监控对象）的标签只读展示。
- 用户添加的标签 key 若与模板映射目标冲突，需提示用户前往标签模板管理修改。

#### FR-15：模板引用影响感知

- 标签模板详情页展示：关联实例数量、被引用采集 Job 数量。
- 模板修改后，引用该模板的 Job 显示「模板已变更，待确认」提示。
- 每次模板/映射变更落只读修改快照（操作人、时间、旧值、新值）。

### 5.4 Excel 批量导入

#### FR-16：固定列模板下载

- 按资源类型提供固定列 Excel 模板。
- 模板内置「取值说明 sheet」，列出网域、业务、环境等列的合法值。

#### FR-17：Excel 导入与校验

- 支持上传 Excel 并导入到对应资源类型。
- 支持 `create_only`（仅新增，重复报错）和 `upsert`（重复则更新）两种模式。
- 校验必填字段、IP 格式、端口范围、URL 格式、环境枚举、字典存在性等。
- 返回导入结果：总数、成功数、更新数、失败数、失败明细（行号/字段/值/原因）。

#### FR-18：状态映射

- Excel 中的中文状态（运行中 / 已停止 / 维护中）自动映射为内部枚举（online / offline / maintenance）。
- 未匹配状态默认映射为 offline。

#### FR-19：字典声明 sheet

- 导入文件支持内联「业务声明」「应用声明」「平台声明」sheet。
- 导入时可随批次原子创建新字典条目。
- 声明条目只增不覆盖，与资源落库在同一事务内完成。

### 5.5 查询与展示

#### FR-20：资源列表展示

- 按资源类型 Tab 切换列表。
- 默认展示列按类型固定，例如主机列表展示主机名、IP、操作系统、网域、业务、运行状态、采集状态等。
- 支持列显隐配置，偏好按资源类型分区记忆。

#### FR-21：多维度筛选

- 资源列表支持按平台、应用、业务、网域、运行状态、采集状态筛选。
- 筛选条件必须由后端按全量结果生效，分页总数随筛选条件变化。

#### FR-22：资源详情展示

- 详情页展示资源字段、平台/应用/业务归属、标签列表、适用模板、采集状态。
- 标签列表按来源分组展示，并标注来源。

### 5.6 归属编码的聚合消费契约

#### FR-23：平台 / 应用 / 业务三维聚合

本模块维护的三个归属编码（`platform_code` / `app_code` / `biz_code`）经标签模板映射为 `platform` / `app` / `biz` 三个监控标签，随采集注入到每条指标与告警序列。因此：

- 告警面板**必须**支持按这三种维度聚合展示与分析（平台 / 应用 / 业务的健康度、告警量、趋势）；
- **平台维是告警组织归属与分发的第一维度**（先回答「哪个平台」，再下钻应用 / 实例），不作为「可选过滤器」降级处理；
- 业务维是横切维度（回答「为谁服务」），与应用维正交，二者不可互相派生；
- 资源类型维（主机 / 数据库 / 中间件 / 应用 / 接口）**不走标签聚合**，由告警侧按资源标识回连资源台账取得，属回填字段，与本模块的标签治理**解耦**——新增资源类型聚合不需要改动本模块的标签设计。

> **边界**：本模块只负责「编码正确、标签注入正确」；告警面板的聚合视图、筛选交互、下钻路径归告警模块（M08），看板归 M05。

### 5.7 字典生命周期与纠错

#### FR-24：字典状态与可选性

- 三本字典统一对外暴露四种状态：`enabled`（启用）、`disabled`（停用）、`merged`（已合并）、`revoked`（已撤销）。
- 只有 `enabled` 条目可被新增 / 编辑资源或应用平台关联选用；`disabled` / `merged` / `revoked` 均不再出现在可选下拉中。
- `merged` / `revoked` 为终态，不能再次编辑、启停、撤销或合并。
- 列表默认展示「有效条目」（启用 + 停用）；切换筛选后可查看已合并 / 已撤销条目及 `merged_into` 目标。

#### FR-25：引用数展示

- 业务、应用、平台列表均展示「引用数」列。
- 业务引用数 = 引用该 `biz_code` 的未删除资源数。
- 应用引用数 = 引用该 `app_code` 的未删除资源数。
- 平台引用数 = 引用该 `platform_code` 的未删除资源数 + 未删除的应用平台关联数。
- 引用数由服务端一次分组查询返回，禁止前端逐行请求。

#### FR-26：零引用撤销

- 引用数为零的条目可执行「撤销」。
- 撤销为终态：条目从可选下拉消失，列表保留但标识「已撤销」。
- 撤销不释放编码，不允许重新登记同一编码。
- 引用数大于零时撤销请求被拒绝，返回引用数与下一步建议（先停用或合并）。
- 撤销前必须二次确认，明确告知「编码将永久保留、不可重新登记」。

#### FR-27：错建 / 重码合并

- 已停用或启用的条目可合并到同类型、启用中的目标条目；源条目不能等于目标。
- 合并前展示影响预览：源编码、目标编码、将被迁移的资源数 / 平台关联数，并明确提示「历史监控数据不会追溯改写，计数器可能出现不连续」。
- 合并必须在单事务内完成引用迁移；任一环节失败整体回滚。
- 合并完成后源条目状态为「已合并」，展示 `合并至 <目标编码>`，不再可选。
- 合并写审计日志，记录操作人、时间、源/目标编码、迁移引用数。

#### FR-28：批量改归属

- 资源列表支持勾选多条资源，批量修改业务 / 应用 / 平台归属。
- 目标字典必须启用；组成型资源（应用服务、接口服务）的平台归属由应用主平台派生，不允许批量直接改平台。
- 静态资源批量改平台时，若其已有应用归属，目标平台须已与该应用关联（与常规编辑校验同一不变量）。
- 批量修改单事务提交，任一资源校验失败整体回滚，并返回失败明细（资源 ID / 原因）。

#### FR-29：停用引用的编辑放行

- 资源编辑时只校验**本次发生变化**的引用字段：
  - 业务编码变化 → 校验业务字典启用；
  - 应用编码变化 → 校验应用字典启用；
  - 平台编码变化，或应用变化导致平台需重新校验 → 校验平台启用及应用-平台关联；
  - 网域变化 → 校验网域可用。
- 未变化的引用字段即使当前字典已停用，也不得阻断本次编辑（例如修改负责人、运行状态、标签）。
- 新增资源仍执行全量校验。

### 5.8 资源能力属性与通用扩展属性

> **本节的定位**：为「监控对象类型应当灵活多变」提供资源侧的数据基础。M01 的类型推导规则只能引用本模块提供的属性，因此能力属性必须**既可扩展、又受控**。

#### FR-30：常见能力固定字段

- 主机资源支持 `has_npu`、`has_gpu` 两个布尔能力标记，作为**一等字段**随资源登记、编辑、Excel 导入一并维护；
- 固定字段具备完整能力：列表可展示、可筛选、可导入导出、可参与导出统计；
- 固定字段默认值为「否」，未登记时不得推断为「是」；
- 新增固定能力字段（如 `has_dpu`）属于低频变更，须评估是否需要走版本迭代；**智能扩展走 FR-31 的通用扩展属性，不要求每次新增能力都改字段**。

#### FR-31：通用扩展属性

- 提供 `ResourceAttribute`（资源 × 属性 key × 值）承载长尾能力，例如 `dpu_model`、`smart_nic`、`gpu_memory_gb`；
- 属性 key 必须有登记（扩展属性字典），记录 key、展示名、值类型（布尔 / 数值 / 文本 / 枚举）、适用资源类别、是否必填；
- 新增一个属性 key **不需要修改表结构、不需要发版**；资源登记表单按适用类别动态展示扩展属性字段；
- 值校验按属性类型执行：布尔只接受真/假，数值只接受数字并可设上下限，枚举只接受字典内取值；
- 扩展属性支持 Excel 导入（超出固定列的属性 key 以「属性名=值」形式声明），导入时校验 key 是否存在且适用当前资源类别；
- 扩展属性只描述资源事实，**不注入 Prometheus 标签**（标签只来自标签模板与实例级自定义标签，见 §5.3）。

## 6. 非功能需求

### 6.1 数据一致性

#### NFR-01：编码不可变

- 平台编码、应用编码、业务编码创建后不可修改，避免历史时序断裂。
- 展示名可修改，但修改展示名不触发监控配置重新生成。

#### NFR-02：字典停用 / 合并 / 撤销不破坏历史

- 字典条目停用后，存量资源保留历史值，仅禁止新资源引用。
- 合并只迁移元数据引用，不重写 TSDB 历史数据。
- 撤销仅允许零引用条目，编码永久保留、不复用。
- 任何生命周期动作都不得导致存量资源的 `biz` / `app` / `platform` 标签变成空值或指向不存在的编码。

#### NFR-03：判重一致性

- 同一资源类型内，按既定判重键检测重复。
- 判重键在手动录入、Excel 导入、API 调用时保持一致。

### 6.2 性能

#### NFR-04：列表响应时间

- 资源列表（默认 50 条/页）首屏加载时间 ≤ 1 秒（95 分位）。
- 筛选、排序、分页操作响应时间 ≤ 500 毫秒。

#### NFR-05：批量导入性能

- Excel 导入支持单次 1000 行资源，导入处理时间 ≤ 30 秒。
- 导入过程不阻塞其他用户操作。

#### NFR-06：采集状态查询性能

- 资源列表采集状态 badge 通过 M09 聚合 API 一次性获取，禁止逐行查询时序数据。

### 6.3 扩展性

#### NFR-07：新资源类型预留

- 「其他监控对象」类型作为兜底，未来可通过扩展端点类型预设支持 K8s 集群、网络设备、GPU 等，无需新增顶层资源类型。
- 资源能力维度通过「常见能力固定字段 + 通用扩展属性」两层承载（§3.5 / §5.8），新增一种硬件能力（NPU / GPU / DPU 等）原则上走扩展属性，不要求新增资源类型或改表结构。

#### NFR-08：外部 CMDB 接入预留

- 资源模型预留 CMDB 相关字段（`cmdb_ci_id`、`cmdb_business_path`、`cmdb_module_path`、`cmdb_maintainer`）。
- {v0.4+} 通过 Module_04 接入外部 CMDB 时，本模块消费同步后的数据。

#### NFR-09：标签模板可扩展

- 标签模板支持新增映射、转换规则、字段来源，便于未来引入新的治理维度。

### 6.4 安全性

#### NFR-10：写权限控制

- 静态资源的 user 标签写操作必须被拒绝（返回 403）。
- 字典条目的关键字段（编码）不可通过编辑接口修改。

#### NFR-11：数据隔离

- 资源数据按租户上下文隔离；{v0.2+} 多租户场景下，用户只能看到授权租户的资源。

#### NFR-12：导入安全

- Excel 导入需校验文件格式、字段长度、非法字符，防止注入或异常数据落库。
- 导入结果不包含敏感字段（如连接串）的明文日志。

### 6.5 可用性

#### NFR-13：用户语言一致性

- 用户界面统一使用「运行中 / 已停止 / 维护中」「平台 / 应用 / 业务」等业务语言，不暴露 `resource_category`、`biz_code` 等技术术语。
- 技术术语仅出现在折叠区、代码注释或接口文档。

#### NFR-14：错误提示可执行

- 导入失败、字典不存在、网域未登记等错误，提示文案必须给出下一步操作指引。
- 例如：「网域 xxx 未登记，请先到『系统设置 → 网域管理』登记后重新导入」。

#### NFR-15：表单引导

- 资源登记表单对关键字段提供说明文案，例如网域字段提示「这台机器的采集端口从哪条链路够得着？」。
- 应用服务与接口服务的字段差异需在表单上清晰区分。

### 6.6 可维护性

#### NFR-16：修改留痕

- 标签模板/映射的每次变更落只读快照，记录操作人、时间、旧值、新值。
- 资源删除为软删，保留审计记录。

#### NFR-17：模块边界清晰

- M07 不生成 `prometheus.yml`，不配置 ScrapeJob，不下发配置。
- M07 向 M01、M09 提供资源数据；资源/标签变更成功后只发送 best-effort 同步通知（不生成配置、不触发 reload），配置生成与下发仍由 M09 负责。
- 新增资源不会自动加入已有 Job 的静态选例列表；按云/条件动态全量选例不在本期范围。

#### NFR-18：应用归属完整性

- 「应用至少归属一个平台」与「应用恰有一个主平台」是**数据层不变量**，必须在服务端强制，不得仅依赖界面校验。
- 任何写入路径（页面登记、编辑、批量导入、接口直调）都不得产生「零平台归属的应用」或「多主平台的应用」。
- 违反不变量的请求须返回可执行的错误提示（例如「应用必须归属至少一个平台」「请先将其他平台设为主平台，再解绑当前主平台」），不得静默放行或静默改写主平台。

#### NFR-19：生命周期动作原子性

- 合并、批量改归属必须在单事务内完成；任一步骤失败整体回滚，不留下部分迁移。
- 撤销与合并写审计日志，日志写入与业务变更同一事务提交。

#### NFR-20：引用数一致性

- 引用数必须与资源、应用平台关联的当前有效数据一致，排除软删记录。
- 列表引用数一次分组查询完成，禁止 N+1。

#### NFR-21：状态文案一致性

- 四态文案统一为「启用 / 停用 / 已合并 / 已撤销」，不得在不同页面使用「删除 / 下线 / 作废」等混用词。
- 字典说明条明确「零引用可撤销、有引用只能停用或合并」，不得暗示删除资源可删除字典。

#### NFR-22：应用抽屉单字段可用性

- 应用抽屉的「关联平台」单字段必须支持键盘操作与屏幕阅读器：星标按钮可通过 Tab 聚焦、Enter / Space 触发，并提供可读的 `aria-label`。
- 主平台切换后立即在标签上反馈，不依赖保存后才可见。

#### NFR-23：能力属性扩展不依赖发版

- 新增一种长尾硬件能力（扩展属性 key）通过「扩展属性字典」登记完成，**不修改代码、不修改表结构、不发版**；
- 固定能力字段（`has_npu` / `has_gpu`）只承载稳定高频能力，扩容须走版本迭代；
- 能力属性对外（M01 推导规则读取）提供受控字段清单查询接口：只暴露「可参与推导」的字段名与类型，**不暴露物理列名**，由本模块维护字段名到物理列的固定映射，杜绝调用方拼接 SQL；
- 扩展属性 key 的删除须先校验资源引用，有引用时只能停用、不允许物理删除。

## 7. 数据模型概述

### 7.1 核心实体

| 实体 | 说明 | 关键属性 |
|------|------|----------|
| Resource | 监控对象台账 | 资源类型、网域、运行状态、平台/应用/业务归属、能力字段（`has_npu` / `has_gpu`） |
| LabelTemplate | 标签模板 | 资源类型、映射规则列表、是否默认 |
| ResourceLabel | 资源标签实例 | key、value、来源（system/user/cmdb） |
| AttributeDefinition | 扩展属性字典 | 属性 key、展示名、值类型、适用资源类别、启用状态 |
| ResourceAttribute | 资源扩展属性 | resource_id、属性 key、值、来源 |
| PlatformDict | 平台字典 | platform_code、platform_name、生命周期状态、merged_into、引用数 |
| ApplicationDict | 应用字典 | app_code、app_name、生命周期状态、merged_into、引用数 |
| BusinessDomain | 业务分组字典 | biz_code、biz_name、生命周期状态、merged_into、引用数 |
| AppPlatformRel | 平台-应用关联 | app_code、platform_code、是否主平台 |
| DictionaryAuditLog | 字典生命周期审计 | 字典类型、动作、源/目标编码、引用数、操作人、时间 |

### 7.2 核心关系

- **平台 → 应用服务**：多对多（通过 AppPlatformRel）；附加不变量——**每个应用至少一条平台关联**、**每个应用恰有一个主平台**。
- **应用服务 → 接口服务**：一对多（通过资源行的 `app_code`）。
- **资源 → 标签模板**：按资源类型隐式关联。
- **资源 → ResourceLabel**：一对多。
- **资源 → ResourceAttribute**：一对多；属性 key 必须存在于 `AttributeDefinition` 且适用该资源类别。
- **AttributeDefinition → ResourceAttribute**：一对多；有引用的属性 key 只能停用、不可物理删除。
- **Resource → 监控对象类型（M01）**：**无物理关联**。M01 通过 FR-30 / FR-31 提供的能力属性 + 自身推导规则隐式匹配，M07 不存 `monitor_type`、不回写类型；一个资源可同时命中多个 M01 类型。
- **资源 → 字典**：通过 `platform_code`、`app_code`、`biz_code` 引用；其中组成型资源（应用服务 / 接口服务）的 `platform_code` 由所属应用主平台派生，静态资源（主机 / 数据库 / 中间件 / 其他监控对象）显式维护。

### 7.3 关键标签

| 标签 | 来源字段 | 用途 |
|------|----------|------|
| `app` | `app_code` | 应用级聚合 |
| `biz` | `biz_code` | 业务域聚合（横切维度，回答「为谁服务」） |
| `platform` | `platform_code` | **平台级聚合 + 告警组织归属的第一维度**（组织根节点；告警分发先归平台，再下钻应用 / 实例） |
| `env` | `env` | 环境维度 |
| `cluster` | `cluster` | 集群维度 |
| `resource_id` | `resource_id` | 资源实例稳定身份键 |

## 8. 关键流程

### 8.1 资源录入流程

1. 用户选择资源类型。
2. 系统打开对应登记抽屉/表单。
3. 用户填写资源字段，选择平台 → 应用 → 业务归属。
4. 系统校验字段、判重、字典存在性。
5. 保存后，system 标签按标签模板自动生成。
6. 保存成功后 best-effort 即时通知 M01 对账 + M09 重算配置（失败由 watcher 兜底）；新增资源不会自动加入已有 Job 的静态选例列表，需重新选择。

### 8.2 Excel 导入流程

1. 用户下载对应资源类型的 Excel 模板。
2. 用户填写资源清单，可选填写「业务/应用/平台声明」sheet。
3. 上传文件，选择 `create_only` 或 `upsert` 模式。
4. 系统校验每一行数据。
5. 校验通过则创建/更新资源，同时创建声明的字典条目。
6. 返回导入报告（成功/更新/失败明细）。
7. 导入成功后 best-effort 触发一次 M01 对账 + 全量 M09 配置重算；失败由 watcher 兜底。

### 8.3 标签模板变更流程

1. 用户编辑标签模板映射（表格批量编辑）。
2. 系统整组校验映射规则。
3. 保存后生成修改快照。
4. 系统提示用户该模板被 N 个采集 Job 引用。
5. 保存成功后 best-effort 触发引用 Job 所在网域的 M09 配置重算，targets 标签即时更新；失败由 30s watcher 兜底。

### 8.4 受控标签维护流程

1. 用户进入业务类型资源（应用服务/接口服务）详情页。
2. 查看 system / user / cmdb 标签及来源标注。
3. 可新增/编辑/删除 user 来源标签。
4. 若 user 标签 key 与模板映射冲突，系统提示前往标签模板管理。
5. 标签保存成功后 best-effort 触发该资源所属网域的 M09 配置重算；失败由 watcher 兜底。

### 8.5 字典纠错流程

**零引用撤销**：

1. 运维在字典列表查看目标条目引用数；
2. 引用数为零时点击「撤销」；
3. 二次确认弹窗说明「编码永久保留、不可重新登记」；
4. 服务端再次校验引用数，写入撤销状态与审计日志；
5. 条目从可选下拉消失，列表标识「已撤销」。

**错建 / 重码合并**：

1. 运维选择源条目，点击「合并」；
2. 选择同类型、启用中的目标条目；
3. 系统展示影响预览（迁移资源数、平台关联数）与历史数据不追溯提示；
4. 确认后服务端在单事务内迁移引用、标记源条目已合并、写审计日志；
5. 相关资源归属变化触发 M09 自动配置同步。

### 8.6 批量改归属流程

1. 运维在资源列表勾选多条同类型资源；
2. 选择要修改的维度（业务 / 应用 / 平台）与目标字典；
3. 系统校验目标启用、资源类型适用（组成型资源不可直接改平台）；
4. 单事务提交，任一失败整体回滚并返回失败明细；
5. 成功后 best-effort 触发 M01 对账 + 相关网域 M09 配置重算，资源标签随配置更新；失败由 watcher 兜底。

### 8.7 资源能力属性维护流程

1. 需要登记一种新硬件能力（例如 DPU）时，运维先在「扩展属性字典」登记 key（如 `has_dpu`）、值类型与适用资源类别；该操作不改表结构、不发版；
2. 资源登记 / 编辑表单按适用资源类别动态出现该属性字段；
3. 运维在资源上填写能力值（或经 Excel 导入声明「属性名=值」）；
4. 系统按属性类型校验取值并落 `ResourceAttribute`；
5. M01 的推导规则可直接引用该属性 key 作为筛选字段，据此把资源归入对应的监控对象类型；
6. 该能力需要变更类型定义或规则时，由 M01 侧配置完成，M07 不做类型判定。

## 9. 验收标准

### 9.1 功能验收

- [ ] 系统支持维护六类资源台账，每类有独立列表与登记表单。
- [ ] 应用服务与接口服务的字段、表单、判重键相互独立。
- [ ] 平台、应用、业务字典可维护，编码创建后不可改；三者由运维工程师自助维护，平台管理员负责审计与纠错。
- [ ] 全新部署不预置任何业务字典，不存在 `infra`、`authorized-ops`、`data-innovation-lab`。
- [ ] 三个字典列表展示引用数与四态（启用 / 停用 / 已合并 / 已撤销）。
- [ ] 零引用条目可撤销；有引用条目撤销被拒绝并提示引用数。
- [ ] 错建 / 重码条目可合并，引用在单事务内迁移，源条目显示「已合并 → 目标」。
- [ ] 资源编辑只校验发生变化的引用字段，已停用字典的存量引用不阻断无关字段编辑。
- [ ] 应用抽屉只有一个「关联平台」多选字段，星标可切换主平台，只选一个平台时自动为主平台。
- [ ] 字典页说明文案不出现「删除资源即可删除字典」的误导表述。
- [ ] 应用与平台支持多对多关联，同一应用至多一个主平台。
- [ ] 每个应用至少归属一个平台；登记应用时未选平台被拒绝；删除应用最后一个平台关联被拒绝。
- [ ] 应用的首个平台关联自动成为主平台；删除主平台关联前必须先把其他平台设为主平台（不提供自动提升）。
- [ ] 应用服务 / 接口服务资源的平台归属由所属应用主平台派生，登记表单不重复要求填写；静态资源仍显式维护平台（可留空兜底）。
- [ ] 告警侧可按平台 / 应用 / 业务三维聚合，平台维为组织归属第一维度；资源类型维不经标签聚合。
- [ ] 资源登记表单支持「平台 → 应用」级联选择。
- [ ] 标签模板按资源类型管理，支持批量编辑映射。
- [ ] 六类默认标签模板包含 `app`、`biz`、`env`、`platform`、`resource_id` 等关键标签。
- [ ] 仅应用服务和接口服务支持手动添加 user 标签，静态资源标签只读。
- [ ] Excel 导入支持 create_only 和 upsert 模式，返回完整导入报告。
- [ ] Excel 中文状态可正确映射到 online/offline/maintenance。
- [ ] 导入文件支持内联声明 sheet 创建新字典条目。
- [ ] 资源列表支持按平台、应用、业务、网域、状态、采集状态筛选。
- [ ] 删除被 Job 引用的资源允许软删放行，并回显引用 Job 数。
- [ ] 删除被引用的标签模板必须阻止并回传引用清单。
- [ ] 主机资源支持 `has_npu` / `has_gpu` 固定能力字段，可登记、编辑、导入、筛选。
- [ ] 扩展属性 key 可在「扩展属性字典」登记，登记后资源表单自动出现对应字段，全程不改表结构、不发版。
- [ ] 扩展属性按值类型校验（布尔 / 数值 / 文本 / 枚举），枚举取值受字典约束。
- [ ] 扩展属性支持 Excel 导入，非法 key 或不适用的资源类别被拒绝并返回行级错误。
- [ ] 有引用的扩展属性 key 只能停用、不可物理删除。
- [ ] M07 不存储 `monitor_type`，也不回写类型；能力属性仅作为事实供 M01 推导使用。
- [ ] 能力属性不注入 Prometheus 标签。

### 9.2 非功能验收

- [ ] 资源列表首屏加载时间 ≤ 1 秒（95 分位）。
- [ ] 1000 行 Excel 导入处理时间 ≤ 30 秒。
- [ ] 静态资源 user 标签写操作返回 403。
- [ ] 字典编码不可通过编辑接口修改。
- [ ] 标签模板变更落只读快照。
- [ ] 模块边界清晰：M07 不生成 prometheus.yml，不配置 ScrapeJob。
- [ ] 用户界面统一使用业务语言，不暴露技术术语。
- [ ] 错误提示文案给出可执行的下一步指引。
- [ ] 合并 / 批量改归属失败时数据保持原状（事务回滚）。
- [ ] 字典列表引用数一次查询返回，无逐行请求。
- [ ] 应用抽屉星标可通过键盘操作，并提供可读的辅助标签。
- [ ] 新增扩展属性 key 不修改表结构、不重新打包发版，登记后立即生效。
- [ ] 能力属性字段清单对外只暴露字段名与类型，不暴露物理列名。

## 10. 依赖与风险

### 10.1 模块依赖

| 依赖方 | 依赖内容 | 说明 |
|--------|----------|------|
| Module_06 | 网域行政数据 | M07 只引用 `network_domain_id`，网域登记/命名/状态由 M06 维护 |
| Module_01 | 采集策略与 Job | M07 提供 Resource / LabelTemplate / 能力属性（固定字段 + 通用扩展属性）供 M01 只读消费；M07 不存也不推导 `monitor_type` |
| Module_09 | 配置生成、下发与采集健康度 | M07 提供数据供 M09 生成 prometheus.yml，M07 不直接下发；采集状态 badge 只读消费 M09 的覆盖率聚合接口（原 M02 查询面已并入 M09） |
| Module_04 | 外部 CMDB 同步 | {v0.4+} M04 同步外部 CMDB 数据写入 M07 |

### 10.2 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 应用团队已按自己的方式维护台账，迁移成本高 | 上线初期数据录入困难 | 提供 Excel 批量导入与字典声明 sheet，降低迁移成本 |
| 平台/应用/业务划分在不同团队理解不一致 | 标签口径混乱 | 在登记表单和导入模板中内置取值说明，提供字典管理页 |
| 用户不理解「受控标签」与「自定义标签」的区别 | 静态资源被误打标 | 静态资源标签区只读，业务类型资源才开放编辑入口 |
| 外部 CMDB 接入后数据冲突 | 标签来源优先级争议 | 明确 cmdb > user > system 的冲突优先级 |
| 合并改写资源归属但配置未及时同步 | 采集标签短暂不一致 | 合并成功后标记相关 Job 待同步，由 M09 自动重生成；失败进入同步失败并提示 |
| 用户误撤销后无法恢复 | 编码永久失效 | 撤销仅限零引用且二次确认，明确「编码永久保留、不可重新登记」 |
| 存量环境仍保留 `infra` 等演示数据 | 与新口径不一致 | 不自动删除，页面提供引用数与撤销/合并动作，执行记录给出清理步骤 |
| 能力属性自由扩张导致字段口径混乱 | M01 规则匹配不可控 | 扩展属性 key 必须登记（字典受控），值类型固定；对外只暴露受控字段清单，不暴露物理列名 |
| 同一种能力既用固定字段又用扩展属性承载（如 `has_npu` 与 `npu_present`） | 数据重复、规则匹配歧义 | 约定「常见能力走固定字段、长尾能力走扩展属性」；新增固定字段须评估，并通过字典展示名/别名提示避免重复登记 |

本文档是面向业务方和产研团队的**需求规格说明书**，强调「为什么做」和「做成什么样」。历史技术 PRD（`Module_07_Monitoring_Object_Management.md` v2.55）保留了更详细的字段表、API 契约、状态机、前端交互契约等技术实现细节。两者关系如下：

- 历史技术 PRD 用于**开发实现、接口对接、测试用例设计**。
- 若本文档与历史技术 PRD 存在冲突，以本文档的当前业务口径为准，由产品负责人决定是否反向修订历史技术 PRD。
