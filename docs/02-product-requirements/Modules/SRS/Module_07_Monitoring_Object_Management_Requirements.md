## 1. 文档目的

本文档用**便于人理解的语言**记录 M07 模块的业务需求、功能需求与非功能需求。它站在产品经理和运维经理的视角，说明「我们需要监控谁」「这些对象如何组织」「治理手段是什么」，并为后续概要设计、详细设计、开发、测试提供依据。

本文档不直接定义 API 字段级别的技术契约（历史技术 PRD 已覆盖），而是回答：**这个模块为什么存在、要解决什么问题、必须具备哪些能力、做到什么程度算合格**。

## 2. 业务背景

### 2.1 我们在监控谁

MetricCenter 的监控对象是线上各类 IT 资源。在真实运维环境中，这些资源的信息分散在：

- CMDB（如腾讯蓝鲸）
- 供应商交付的 Excel 清单
- 各应用团队自行维护的台账
- 口头交接或临时登记

结果是：同一台机器有多个名字、应用归属 missing、标签口径不统一，导致后续采集配置、告警分组、业务看板都无从对齐。

**M07 的定位**：建立 MetricCenter 内部的「监控对象台账」（即线上 CMDB），作为平台的数据基座。先定义清楚有哪些对象、它们属于谁、该打什么标签，再让采集策略（M01）和配置下发（M09）基于这份统一台账工作。

### 2.2 一句话定位

> M07 回答的问题是：**「我们在监控谁」**。

它不负责「怎么采」「怎么告警」「怎么下发配置」，只负责「监控对象本身的数据对不对、归属清不清楚、标签受不受控」。

## 3. 核心概念

### 3.1 监控对象（CI）类型

本模块管理六类监控对象：

| 类型 | 例子 | 一句话说明 |
|------|------|-----------|
| 主机 | Linux/Windows 服务器、虚拟机 | 运行 OS 与 Exporter 的实体 |
| 数据库 | MySQL、Redis、Oracle、PostgreSQL | 以数据存储/查询为主语义的实例 |
| 中间件 | Kafka、Elasticsearch、Nginx、Zookeeper | 消息、网关、搜索、协调类组件 |
| 应用服务 | 接口包装系统、数据目录系统 | 平台下的子系统/服务 |
| 接口服务 | `/api/v1/authorize`、`/api/v2/query` | 应用服务对外暴露的数据类 API 端点 |
| 其他监控对象 | K8s 集群级端点、网络设备、GPU、自定义 HTTP 端点 | 当前未大规模使用、预留扩展的兜底类型 |

### 3.2 平台、应用服务、接口服务的关系

这是本模块最关键的业务定义。

#### 平台（Platform）

- **业务含义**：一个需要整体进行等保、安测、统一运维的业务平台。例如「公共数据授权运营平台」。
- **管理主体**：平台团队。平台由哪些应用组成，由平台团队自己定义。
- **在监控中的价值**：平台是最高层聚合维度，管理层看「某个平台整体健不健康」。

#### 应用服务（Application）

- **业务含义**：平台下的子系统或服务。例如平台上的「接口包装系统」「数据目录系统」。
- **管理主体**：应用团队或供应商。一个平台可由多个应用团队或供应商分别开发和部署各自的应用服务。
- **运维组织保障**：
  - 一线运维工程师：发现告警、初步定位。
  - 二线应用运维工程师：负责深入排查和处理问题。
- **在监控中的价值**：故障定位时，先落到「哪个应用服务」，再下钻到具体实例或接口。

#### 接口服务（Interface Service）

- **业务含义**：应用服务承载的、对外暴露的数据类 API 端点。例如「接口包装系统」对外提供的 `/api/v1/authorize`。
- **核心用途**：用于 blackbox 拨测，验证接口可用性。
- **在监控中的价值**：反映业务接口的可用性，是业务可用性监控的直接载体。

#### 关系总结

```
平台（等保/安测/管理视角）
  └── 应用服务 N 个（由平台团队定义，应用团队/供应商部署）
        └── 接口服务 M 个（应用服务对外暴露的数据 API，用于拨测）
```

### 3.3 受控标签

为了在多团队、多供应商、多应用的场景下保证监控数据口径一致，本模块引入**受控标签**机制：

- **类型级标签**：通过「标签模板」按资源类型定义映射规则，例如「主机的 `app_code` 字段 → `app` label」。所有该类型实例自动生效。
- **实例级标签**：仅对业务类型资源（应用服务 / 接口服务）开放自定义标签入口；静态资源（主机 / 数据库 / 中间件 / 其他监控对象）只读展示，避免在 CMDB 治理侧之外二次打标造成口径混乱。
- **来源标注**：每条标签都标注来源（system / user / cmdb），让用户看得见「这个标签从哪来」。

## 4. 目标用户与使用场景

### 4.1 目标用户

| 用户角色 | 关注点 | 典型操作 |
|----------|--------|----------|
| 运维经理 | 监控覆盖率、资源归属是否清晰 | 查看资源列表、统计未监控资源 |
| 运维工程师 | 批量录入资源、维护标签 | Excel 导入、手动登记、编辑标签模板 |
| 应用运维工程师 | 应用服务与接口服务的可用性 | 登记应用服务、登记拨测接口 |
| 平台管理员 | 平台-应用关系、字典维护 | 维护平台字典、应用字典、业务分组 |
| 运维架构师 | 标签治理、数据一致性 | 定义标签模板、审计标签来源 |

### 4.2 典型使用场景

#### 场景 1：新平台上线，批量录入资源

- **角色**：运维工程师
- **触发**：供应商交付 300 台主机、50 个 MySQL 实例、10 个应用服务
- **目标**：一次性录入平台监控对象
- **成功标准**：
  - 按类型导入成功
  - 资源可按平台/应用/业务筛选
  - 导入错误有明确行号、字段、原因提示

#### 场景 2：新应用上线，登记应用与接口服务

- **角色**：应用运维工程师
- **触发**：新应用上线，需要配置拨测与指标采集
- **目标**：建立应用服务与拨测接口的台账
- **成功标准**：
  - 应用服务挂到平台下
  - 接口服务挂到应用下
  - Blackbox 拨测任务可从接口服务列表中选取目标

#### 场景 3：统一业务标签口径

- **角色**：运维架构师
- **触发**：各应用团队自行埋点，标签命名不统一
- **目标**：通过标签模板强制统一关键标签
- **成功标准**：
  - 新建采集 Job 时自动带出 `app`、`biz`、`env`、`platform` 等标签
  - 查询可按业务维度聚合

#### 场景 4：发现未监控资源

- **角色**：运维经理
- **触发**：例行检查监控覆盖率
- **目标**：发现监控缺口
- **成功标准**：
  - 资源列表可筛选「未监控」和「已下发未采到」
  - 三态 badge（采集中 / 已下发未采到 / 未监控）清晰可辨

## 5. 功能需求

### 5.1 资源台账管理

#### FR-01：六类资源台账维护

- 系统必须支持维护主机、数据库、中间件、应用服务、接口服务、其他监控对象六类资源。
- 每类资源有独立的列表页（Tab 切换）。
- 支持新增、编辑、删除、查看详情。
- 支持按关键字、网域、平台、应用、业务、运行状态、采集状态筛选。

#### FR-02：应用服务与接口服务差异化登记

- 应用服务登记字段：服务名、健康检查 URL、协议、指标端点、端口、负责人、运维人员、上线时间、所属平台/应用/业务等。
- 接口服务登记字段：接口名、接口 URL、所属应用服务、业务、环境等。
- 健康检查 URL 是 blackbox 拨测的目标地址，必须必填且格式正确。
- 同一应用服务可登记多个接口服务。

#### FR-03：运行状态维护

- 资源运行状态包括：运行中、已停止、维护中。
- 已停止的资源在下一配置生成周期从采集目标中移除。
- 状态变更需记录审计日志。

#### FR-04：采集状态感知

- 资源列表需展示采集状态三态：采集中、已下发未采到、未监控。
- 「已下发未采到」需高亮提示。
- 采集状态数据由 M01（选中关系）和 M02（健康度 API）提供，M07 只读消费。

#### FR-05：删除与引用保护

- 删除资源前需二次确认。
- 若资源被采集 Job 引用，允许软删放行，但需回显引用 Job 数量并提供跳转入口。
- 删除后同步回收引用 Job 中的该资源。

#### FR-06：其他监控对象兜底登记

- 为 K8s 集群级端点、网络设备、GPU、自定义 HTTP 端点等提供统一登记入口。
- 用户只需填写目标名称、端点地址、端点类型，无需理解 Exporter 术语。
- 容器 / Pod / K8s 节点等动态发现产物不在本模块登记。

---

### 5.2 平台、应用、业务字典管理

#### FR-07：平台字典维护

- 维护平台编码、平台名称、描述、状态。
- 平台编码创建后不可修改。
- 停用平台后禁止新资源引用，存量关联保留历史值。

#### FR-08：应用字典维护

- 维护应用编码、应用名称、描述、状态。
- 应用编码创建后不可修改。
- 应用与平台支持多对多关联：一个应用可属于多个平台，一个平台可包含多个应用。
- 同一应用至多标记一个主平台。

#### FR-09：业务分组字典维护

- 维护业务编码、业务名称、描述、状态。
- 业务编码创建后不可修改。
- 停用业务后禁止新资源引用，存量资源保留历史值。
- `infra` 等兜底条目禁止停用/删除。

#### FR-10：平台-应用-资源级联关系

- 资源登记表单支持先选平台、再选应用（按平台过滤应用列表）。
- 应用服务资源必须关联应用。
- 接口服务资源通过所属应用间接关联平台。

---

### 5.3 标签模板与受控标签

#### FR-11：标签模板管理

- 按资源类型定义「资源字段 → Prometheus Label」的映射规则。
- 六类资源各预置一套默认模板。
- 支持基于默认模板克隆创建自定义模板。
- 支持编辑、删除自定义模板；默认模板只读。

#### FR-12：映射批量编辑

- 标签模板映射支持表格批量编辑。
- 用户在本地草稿中连续新增/修改/删除多行映射，最后统一保存。
- 保存时进行整组校验：目标标签不能冲突、不能覆盖 Prometheus 内置 label。

#### FR-13：标签来源与冲突管理

- 标签来源分为 system（来自模板）、user（手动添加）、cmdb（外部 CMDB 同步）。
- 同 key 冲突时优先级：cmdb > user > system。
- system 标签为系统保护标签，用户不可覆盖。

#### FR-14：实例级自定义标签

- 仅应用服务和接口服务资源支持手动添加/编辑/删除 user 标签。
- 静态资源（主机、数据库、中间件、其他监控对象）的标签只读展示。
- 用户添加的标签 key 若与模板映射目标冲突，需提示用户前往标签模板管理修改。

#### FR-15：模板引用影响感知

- 标签模板详情页展示：关联实例数量、被引用采集 Job 数量。
- 模板修改后，引用该模板的 Job 显示「模板已变更，待确认」提示。
- 每次模板/映射变更落只读修改快照（操作人、时间、旧值、新值）。

---

### 5.4 Excel 批量导入

#### FR-16：固定列模板下载

- 按资源类型提供固定列 Excel 模板。
- 模板内置「取值说明 sheet」，列出网域、业务、环境等列的合法值。

#### FR-17：Excel 导入与校验

- 支持上传 Excel 并导入到对应资源类型。
- 支持 `create_only`（仅新增，重复报错）和 `upsert`（重复则更新）两种模式。
- 校验必填字段、IP 格式、端口范围、URL 格式、环境枚举、字典存在性等。
- 返回导入结果：总数、成功数、更新数、失败数、失败明细（行号/字段/值/原因）。

#### FR-18：状态映射

- Excel 中的中文状态（运行中 / 已停止 / 维护中）自动映射为内部枚举（online / offline / maintenance）。
- 未匹配状态默认映射为 offline。

#### FR-19：字典声明 sheet

- 导入文件支持内联「业务声明」「应用声明」「平台声明」sheet。
- 导入时可随批次原子创建新字典条目。
- 声明条目只增不覆盖，与资源落库在同一事务内完成。

---

### 5.5 查询与展示

#### FR-20：资源列表展示

- 按资源类型 Tab 切换列表。
- 默认展示列按类型固定，例如主机列表展示主机名、IP、操作系统、网域、业务、运行状态、采集状态等。
- 支持列显隐配置，偏好按资源类型分区记忆。

#### FR-21：多维度筛选

- 资源列表支持按平台、应用、业务、网域、运行状态、采集状态筛选。
- 筛选条件必须由后端按全量结果生效，分页总数随筛选条件变化。

#### FR-22：资源详情展示

- 详情页展示资源字段、平台/应用/业务归属、标签列表、适用模板、采集状态。
- 标签列表按来源分组展示，并标注来源。

## 6. 非功能需求

### 6.1 数据一致性

#### NFR-01：编码不可变

- 平台编码、应用编码、业务编码创建后不可修改，避免历史时序断裂。
- 展示名可修改，但修改展示名不触发监控配置重新生成。

#### NFR-02：字典停用不解绑

- 字典条目停用后，存量资源保留历史值，仅禁止新资源引用。
- 避免误操作导致大量历史数据失效。

#### NFR-03：判重一致性

- 同一资源类型内，按既定判重键检测重复。
- 判重键在手动录入、Excel 导入、API 调用时保持一致。

### 6.2 性能

#### NFR-04：列表响应时间

- 资源列表（默认 50 条/页）首屏加载时间 ≤ 1 秒（95 分位）。
- 筛选、排序、分页操作响应时间 ≤ 500 毫秒。

#### NFR-05：批量导入性能

- Excel 导入支持单次 1000 行资源，导入处理时间 ≤ 30 秒。
- 导入过程不阻塞其他用户操作。

#### NFR-06：采集状态查询性能

- 资源列表采集状态 badge 通过 M02 聚合 API 一次性获取，禁止逐行查询时序数据。

### 6.3 扩展性

#### NFR-07：新资源类型预留

- 「其他监控对象」类型作为兜底，未来可通过扩展端点类型预设支持 K8s 集群、网络设备、GPU 等，无需新增顶层资源类型。

#### NFR-08：外部 CMDB 接入预留

- 资源模型预留 CMDB 相关字段（`cmdb_ci_id`、`cmdb_business_path`、`cmdb_module_path`、`cmdb_maintainer`）。
- {v0.4+} 通过 Module_04 接入外部 CMDB 时，本模块消费同步后的数据。

#### NFR-09：标签模板可扩展

- 标签模板支持新增映射、转换规则、字段来源，便于未来引入新的治理维度。

### 6.4 安全性

#### NFR-10：写权限控制

- 静态资源的 user 标签写操作必须被拒绝（返回 403）。
- 字典条目的关键字段（编码）不可通过编辑接口修改。

#### NFR-11：数据隔离

- 资源数据按租户上下文隔离；{v0.2+} 多租户场景下，用户只能看到授权租户的资源。

#### NFR-12：导入安全

- Excel 导入需校验文件格式、字段长度、非法字符，防止注入或异常数据落库。
- 导入结果不包含敏感字段（如连接串）的明文日志。

### 6.5 可用性

#### NFR-13：用户语言一致性

- 用户界面统一使用「运行中 / 已停止 / 维护中」「平台 / 应用 / 业务」等业务语言，不暴露 `resource_category`、`biz_code` 等技术术语。
- 技术术语仅出现在折叠区、代码注释或接口文档。

#### NFR-14：错误提示可执行

- 导入失败、字典不存在、网域未登记等错误，提示文案必须给出下一步操作指引。
- 例如：「网域 xxx 未登记，请先到『系统设置 → 网域管理』登记后重新导入」。

#### NFR-15：表单引导

- 资源登记表单对关键字段提供说明文案，例如网域字段提示「这台机器的采集端口从哪条链路够得着？」。
- 应用服务与接口服务的字段差异需在表单上清晰区分。

### 6.6 可维护性

#### NFR-16：修改留痕

- 标签模板/映射的每次变更落只读快照，记录操作人、时间、旧值、新值。
- 资源删除为软删，保留审计记录。

#### NFR-17：模块边界清晰

- M07 不生成 `prometheus.yml`，不配置 ScrapeJob，不下发配置。
- M07 只向 M01、M09 提供只读数据消费接口。

## 7. 数据模型概述

### 7.1 核心实体

| 实体 | 说明 | 关键属性 |
|------|------|----------|
| Resource | 监控对象台账 | 资源类型、网域、运行状态、平台/应用/业务归属 |
| LabelTemplate | 标签模板 | 资源类型、映射规则列表、是否默认 |
| ResourceLabel | 资源标签实例 | key、value、来源（system/user/cmdb） |
| PlatformDict | 平台字典 | platform_code、platform_name、状态 |
| ApplicationDict | 应用字典 | app_code、app_name、状态 |
| BusinessDomain | 业务分组字典 | biz_code、biz_name、状态 |
| AppPlatformRel | 平台-应用关联 | app_code、platform_code、是否主平台 |

### 7.2 核心关系

- **平台 → 应用服务**：多对多（通过 AppPlatformRel）。
- **应用服务 → 接口服务**：一对多（通过资源行的 `app_code`）。
- **资源 → 标签模板**：按资源类型隐式关联。
- **资源 → ResourceLabel**：一对多。
- **资源 → 字典**：通过 `platform_code`、`app_code`、`biz_code` 引用。

### 7.3 关键标签

| 标签 | 来源字段 | 用途 |
|------|----------|------|
| `app` | `app_code` | 应用级聚合 |
| `biz` | `biz_code` | 业务域聚合 |
| `platform` | `platform_code` | 平台级聚合 |
| `env` | `env` | 环境维度 |
| `cluster` | `cluster` | 集群维度 |
| `resource_id` | `resource_id` | 资源实例稳定身份键 |

## 8. 关键流程

### 8.1 资源录入流程

1. 用户选择资源类型。
2. 系统打开对应登记抽屉/表单。
3. 用户填写资源字段，选择平台 → 应用 → 业务归属。
4. 系统校验字段、判重、字典存在性。
5. 保存后，system 标签按标签模板自动生成。

### 8.2 Excel 导入流程

1. 用户下载对应资源类型的 Excel 模板。
2. 用户填写资源清单，可选填写「业务/应用/平台声明」sheet。
3. 上传文件，选择 `create_only` 或 `upsert` 模式。
4. 系统校验每一行数据。
5. 校验通过则创建/更新资源，同时创建声明的字典条目。
6. 返回导入报告（成功/更新/失败明细）。

### 8.3 标签模板变更流程

1. 用户编辑标签模板映射（表格批量编辑）。
2. 系统整组校验映射规则。
3. 保存后生成修改快照。
4. 系统提示用户该模板被 N 个采集 Job 引用。
5. 引用 Job 在下次配置生成时按新映射生效。

### 8.4 受控标签维护流程

1. 用户进入业务类型资源（应用服务/接口服务）详情页。
2. 查看 system / user / cmdb 标签及来源标注。
3. 可新增/编辑/删除 user 来源标签。
4. 若 user 标签 key 与模板映射冲突，系统提示前往标签模板管理。

## 9. 验收标准

### 9.1 功能验收

- [ ] 系统支持维护六类资源台账，每类有独立列表与登记表单。
- [ ] 应用服务与接口服务的字段、表单、判重键相互独立。
- [ ] 平台、应用、业务字典可维护，编码创建后不可改。
- [ ] 应用与平台支持多对多关联，同一应用至多一个主平台。
- [ ] 资源登记表单支持「平台 → 应用」级联选择。
- [ ] 标签模板按资源类型管理，支持批量编辑映射。
- [ ] 六类默认标签模板包含 `app`、`biz`、`env`、`platform`、`resource_id` 等关键标签。
- [ ] 仅应用服务和接口服务支持手动添加 user 标签，静态资源标签只读。
- [ ] Excel 导入支持 create_only 和 upsert 模式，返回完整导入报告。
- [ ] Excel 中文状态可正确映射到 online/offline/maintenance。
- [ ] 导入文件支持内联声明 sheet 创建新字典条目。
- [ ] 资源列表支持按平台、应用、业务、网域、状态、采集状态筛选。
- [ ] 删除被 Job 引用的资源允许软删放行，并回显引用 Job 数。
- [ ] 删除被引用的标签模板必须阻止并回传引用清单。

### 9.2 非功能验收

- [ ] 资源列表首屏加载时间 ≤ 1 秒（95 分位）。
- [ ] 1000 行 Excel 导入处理时间 ≤ 30 秒。
- [ ] 静态资源 user 标签写操作返回 403。
- [ ] 字典编码不可通过编辑接口修改。
- [ ] 标签模板变更落只读快照。
- [ ] 模块边界清晰：M07 不生成 prometheus.yml，不配置 ScrapeJob。
- [ ] 用户界面统一使用业务语言，不暴露技术术语。
- [ ] 错误提示文案给出可执行的下一步指引。
