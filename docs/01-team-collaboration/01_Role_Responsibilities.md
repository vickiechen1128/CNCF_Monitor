## 2. chenrt（项目整体负责人 + 产品经理）

### 2.1 核心职责

- **产品方向**：定义 MetricCenter 的产品愿景、MVP 范围、演进路线
- **需求拆解**：把 guixm/zhaohy 的业务输入转化为用户故事、Roadmap、Module 文档
- **Agent 调度**：决定调用哪个 Agent（planner / prototype-designer / backend-developer 等）
- **原型设计**：调用 `prototype-designer` 产出可点击原型，组织原型评审
- **模块排期**：根据 Roadmap 和依赖关系确定开发顺序
- **最终合并**：唯一有权将 feature 分支 `--no-ff` 合并到 `develop`
- **对外汇报**：向领导和其他团队展示项目进展和价值

### 2.2 日常工作清单

| 频率 | 事项 |
|------|------|
| 每日 | 查看项目进展、处理阻塞问题、Review zhangwq 的合并申请 |
| 每周 | 与 zhaohy 对齐需求输入；召开周会/复盘 |
| 每个 Module 开发前 | 调用 `planner` 输出实现计划；明确 feature 分支名 |
| 每个 feature 合并前 | 检查 zhangwq Review 结论、提交前验证结果；执行合并 |
| 每个里程碑结束 | 组织演示/汇报；更新 Roadmap |

### 2.3 决策权限

- ✅ 产品方向、MVP 范围、需求优先级
- ✅ Agent 调用与模块调度
- ✅ feature 分支合并到 `develop`
- ✅ 模型/工具切换审批
- ✅ 对外汇报内容和形式

### 2.4 协作接口

| 对接人 | 协作内容 |
|--------|----------|
| guixm | 业务战略对齐、需求拆解、原型评审 |
| zhaohy | 收集一线需求、验证业务逻辑 |
| zhangwq | 技术方案预评审、代码合并审批、Agent 定义维护 |

### 2.5 典型任务

- "根据 zhaohy 提出的资源导入痛点，更新 `01_User_Stories.md` 和 `Module_07_Monitoring_Object_Management.md`"
- "调用 prototype-designer 制作 MVP 原型，用于下周向领导汇报"
- "审查 zhangwq 提交的 `feature/module-07-resource-management` 合并申请"

## 3. guixm（高级运维总监）

### 3.1 核心职责

- **业务战略输入**：从运维管理视角判断哪些能力建设优先级最高
- **需求共创**：与 chenrt 一起把高层业务目标拆解为可执行需求
- **原型评审**：从管理视角评审 prototype-designer 产出的原型
- **技术-业务桥梁**：帮助技术团队理解业务价值，帮助业务团队理解技术约束
- **重大决策支持**：参与 MVP 范围、模块优先级、关键业务规则的决策

### 3.2 日常工作清单

| 频率 | 事项 |
|------|------|
| 每周 | 参加需求对齐会，确认优先级 |
| 按需 | 与 chenrt 进行需求拆解会 |
| 按需 | 参加原型评审会 |
| 每个 Module 开发前 | 审阅 Module 文档中的业务逻辑部分 |
| 里程碑节点 | 参与汇报，提供业务价值背书 |

### 3.3 决策权限

- ✅ 业务战略价值判断
- ✅ MVP 范围变更建议权（最终 chenrt 决策）
- ✅ 原型方向把关
- ✅ 关键业务规则（如告警策略、拨测标准）确认

### 3.4 协作接口

| 对接人 | 协作内容 |
|--------|----------|
| chenrt | 需求拆解、原型评审、Roadmap 对齐 |
| zhaohy | 把一线需求上升为管理级优先级 |
| zhangwq | 技术可行性咨询、业务逻辑验收 |

### 3.5 典型任务

- "评审 chenrt 制作的资源管理原型，确认是否符合运维管理目标"
- "确认告警分级标准：P0/P1/P2 的定义和通知策略"
- "判断多租户能力是否应纳入 v1.0 路线图"

## 4. zhaohy（运维业务经理）

### 4.1 核心职责

- **一线场景输入**：提供真实运维工作中的痛点和使用场景
- **需求提出**：以用户故事形式描述需要解决的问题
- **业务验收**：验证开发完成的功能是否真正解决一线问题
- **反馈闭环**：上线后收集使用反馈，推动持续优化

### 4.2 日常工作清单

| 频率 | 事项 |
|------|------|
| 每周 | 参加需求输入会，同步一线痛点 |
| 按需 | 补充具体业务场景和验收标准 |
| 每个 Module 开发前 | 审阅 Module 文档中的业务逻辑和用户故事 |
| 每个 feature 合并前 | 参与业务验收（重点看是否符合实际工作流） |
| 上线后 | 收集一线反馈，提交优化建议 |

### 4.3 决策权限

- ✅ 一线业务逻辑正确性确认
- ✅ 功能是否解决实际问题的验收权
- ✅ 需求优先级建议权

### 4.4 协作接口

| 对接人 | 协作内容 |
|--------|----------|
| chenrt | 提交需求、参与原型评审、业务验收 |
| guixm | 上报管理级需求、确认优先级 |
| zhangwq | 解释业务背景、验证功能可用性 |

### 4.5 典型任务

- "提出：批量导入主机时，需要支持机房、机柜、业务线字段"
- "验证：资源管理页面的 Excel 导入流程是否符合一线运维操作习惯"
- "反馈：告警状态页面的字段展示缺少值班负责人，建议补充"

### 4.6 用户故事模板

zhaohy 提交需求时，建议按以下格式：

```
作为【运维工程师/业务研发/运维架构师】，
我希望【具体功能或能力】，
以便于【解决什么问题/带来什么价值】。

业务场景：
【描述真实发生的场景】

当前痛点：
【描述当前如何操作、有什么问题】

验收标准：
1. ...
2. ...
```

## 5. zhangwq（SRE 工程师）

### 5.1 核心职责

- **Vibe Coding 执行**：实际调用 AI Agent 生成代码
- **Prompt 设计**：把 Module 文档和工程标准转化为 AI 可执行的 prompt
- **代码 Review**：对 AI 生成的代码进行人工 Review，确保安全、边界、可维护性
- **测试补充**：补充异常路径和集成测试
- **提交前验证**：执行 go test/vet、pnpm test/lint、服务启动验证
- **技术规范维护**：维护和优化 `.kimi/agents/` 及工程标准文档
- **可运维性保障**：确保代码可部署、可监控、可排障

### 5.2 日常工作清单

| 频率 | 事项 |
|------|------|
| 每日 | 按 chenrt 分配调用 AI Agent 开发当前模块；Review AI 输出 |
| 每个 feature 开发完成后 | 执行提交前验证清单 |
| 每个 feature 合并前 | 向 chenrt 提交合并申请，附 Review 结论和验证结果 |
| 每周 | 参加技术方案评审、周会/复盘 |
| 按需 | 维护和优化 Agent 定义、工程标准 |

### 5.3 决策权限

- ✅ 技术实现方案（在 chenrt 批准的架构范围内）
- ✅ API 路径/响应格式变更
- ✅ 引入新的外部依赖（需 chenrt 知情）
- ✅ 是否通过代码 Review
- ✅ Agent 定义优化建议

### 5.4 协作接口

| 对接人 | 协作内容 |
|--------|----------|
| chenrt | 接收开发任务、提交合并申请、参与技术方案评审 |
| guixm | 咨询业务背景、确认业务逻辑 |
| zhaohy | 了解一线使用场景、验证功能可用性 |

### 5.5 典型任务

- "调用 backend-developer 实现 `feature/module-07-resource-management` 的后端 API"
- "Review frontend-developer 生成的资源管理页面，补充异常处理测试"
- "优化 backend-developer.md 中的 SSRF 检查规则"
- "执行提交前验证并提交合并申请"

### 5.6 Vibe Coding 关键动作

| 阶段 | zhangwq 动作 |
|------|--------------|
| 开发前 | 阅读 Module 文档和工程标准；设计 prompt；准备开发空间/分支 |
| 开发中 | 调用 Agent；监督范围；及时纠偏 |
| 开发后 | 人工 Review；补充测试；执行提交前验证 |
| 合并前 | 提交合并申请；说明变更范围、测试结果、风险点 |

## 7. 常见问题

### Q1：chenrt 和 zhangwq 都需要写代码吗？

- **zhangwq**：主要负责实际代码生成执行。
- **chenrt**：不写业务代码，但在必要时可以修改 PRD、Agent 定义、工程标准。

### Q2：guixm 和 zhaohy 需要懂代码吗？

- 不需要写代码，但需要理解产品逻辑和原型。
- guixm 关注战略价值，zhaohy 关注一线可用性。

### Q3：一个需求从提出到上线，各角色何时介入？

| 阶段 | 主要角色 |
|------|----------|
| 需求提出 | zhaohy |
| 需求拆解 | zhaohy、guixm、chenrt |
| 原型设计 | chenrt、guixm、zhaohy |
| 技术方案 | chenrt、zhangwq |
| 代码开发 | zhangwq + AI Agent |
| 代码 Review | zhangwq、chenrt |
| 业务验收 | zhaohy、guixm |
| 合并发布 | chenrt |
