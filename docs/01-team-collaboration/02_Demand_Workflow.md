# MetricCenter 需求设计环节详细流程

> 文档类型：团队协作规范  
> **目标读者**：chenrt、guixm、zhaohy（产品与业务侧）——zhangwq 可选参考  
> 更新日期：2026-07-21（v1.25 去重：原型设计细节指向 `.kimi/agents/prototype-designer.md`）

---

## 1. 目标

明确 MetricCenter 项目从"业务痛点"到"可开发需求"的完整流转过程，确保：

- 一线运维场景不被遗漏
- 业务战略方向与实现方案对齐
- 每个需求都有清晰的文档载体和验收标准
- 原型在开发前被业务方确认

---

## 2. 需求生命周期

```
Stage 1: 痛点收集
   zhaohy 提出一线运维场景/痛点
        │
        ▼
Stage 2: 需求草稿
   chenrt 整理为用户故事草稿
        │
        ▼
Stage 3: 需求拆解
   chenrt + guixm 拆解需求，判断业务价值与优先级
        │
        ▼
Stage 4: 文档化
   chenrt 更新 PRD 文档
        │
        ▼
Stage 5: 原型设计（按需）
   chenrt 调用 prototype-designer 产出可点击原型
        │
        ▼
Stage 6: 原型评审
   guixm + zhaohy 评审原型，提出修改意见
        │
        ▼
Stage 7: 技术预评审
   zhangwq 参与，补充技术约束、API 标准、数据模型
        │
        ▼
Stage 8: 需求冻结
   chenrt 确认 Module 文档，进入开发队列
```

## 3. Stage 1：痛点收集

### 3.1 触发条件

- zhaohy 在日常运维工作中发现效率问题
- 现有工具无法满足新业务场景
- 团队反馈某个流程重复、容易出错

### 3.2 负责人

- **主要责任人**：zhaohy
- **配合人**：guixm（如涉及管理级痛点）

### 3.3 输出物

- 用户故事草稿（可使用下方模板）
- 相关截图、Excel 示例、现有工具截图（如有）

### 3.4 用户故事模板

```markdown
## 用户故事

**角色**：运维工程师  
**需求**：我希望能够批量导入主机资源  
**价值**：以便于避免手动逐台录入，降低出错率

### 业务场景
在新建机房或扩容时，一次性需要录入几十到上百台主机。目前使用 Excel 维护资产信息，再手工在多个系统中分别录入。

### 当前痛点
1. 手工录入效率低，容易填错字段
2. 不同系统字段格式不一致，需要反复转换
3. 无法快速校验导入结果

### 验收标准
1. 支持下载标准 Excel 模板
2. 支持上传 Excel 批量导入
3. 导入失败时返回具体错误行和原因
4. 导入 100 条数据在 5 秒内完成
```

### 3.5 提交方式

- 优先提交到飞书/钉钉/内部文档（按团队约定）
- 每周需求输入会上统一对齐
- 紧急需求可单独找 chenrt 沟通

## 4. Stage 2：需求草稿

### 4.1 触发条件

- 收到 zhaohy 的用户故事
- chenrt 主动发现产品优化点

### 4.2 负责人

- **主要责任人**：chenrt
- **配合人**：zhaohy（澄清业务细节）

### 4.3 输出物

- `docs/02-product-requirements/01_User_Stories.md` 更新
- 需求优先级初评

### 4.4 chenrt 动作

1. 阅读用户故事，理解业务场景
2. 判断是否与产品愿景一致
3. 初步归类到已有 Module 或新建 Module
4. 更新用户故事文档，标注来源人、优先级、状态

### 4.5 用户故事状态

| 状态 | 含义 |
|------|------|
| `待拆解` | 已记录，尚未进行需求拆解 |
| `拆解中` | chenrt 和 guixm 正在拆解 |
| `待原型` | 拆解完成，等待原型设计 |
| `原型评审中` | 原型已产出，正在评审 |
| `待开发` | 需求已冻结，等待进入开发队列 |
| `开发中` | 已分配模块，正在开发 |
| `已验收` | 功能已上线并被业务方验收 |

## 5. Stage 3：需求拆解

### 5.1 触发条件

- 用户故事进入"拆解中"状态
- 涉及多个模块或较大范围的需求

### 5.2 负责人

- **主要责任人**：chenrt
- **必须参与**：guixm
- **可选参与**：zhaohy（澄清一线细节）、zhangwq（评估技术可行性）

### 5.3 会议：需求拆解会

#### 会议目标

- 判断需求是否值得做
- 明确 MVP 范围 vs. 后续迭代
- 确定优先级
- 明确模块归属

#### 会议议程

1. zhaohy 介绍业务场景（5 分钟）
2. guixm 补充管理视角和战略价值（5 分钟）
3. chenrt 提出初步产品方案（10 分钟）
4. zhangwq 评估技术可行性和大致工作量（10 分钟）
5. 讨论并确定优先级和范围（10 分钟）

#### 会议输出

- 会议纪要
- 需求优先级
- 是否进入原型设计
- 归属 Module

### 5.4 决策规则

| 情况 | 处理方式 |
|------|----------|
| 业务价值高 + 技术可行 | 纳入高优先级，尽快安排原型/开发 |
| 业务价值高 + 技术复杂 | 拆分为多个子需求，分阶段实现 |
| 业务价值低 + 技术简单 | 纳入待办池，后续视资源安排 |
| 业务价值低 + 技术复杂 | 暂缓或否决，记录原因 |

## 6. Stage 4：文档化

### 6.1 触发条件

- 需求拆解完成
- 明确归属模块

### 6.2 负责人

- **主要责任人**：chenrt
- **配合人**：zhangwq（技术约束）

### 6.3 输出物

根据需求范围，更新以下一个或多个文档：

| 文档 | 更新内容 |
|------|----------|
| `01_User_Stories.md` | 用户故事状态、优先级、验收标准 |
| `02_Product_Roadmap.md` | 里程碑、Phase 安排 |
| `03_Functional_Architecture.md` | 新增/调整功能模块位置 |
| `Modules/Module_XX_*.md` | 模块详细需求、业务规则、页面原型、验收标准 |
| `05_Code_Implementation_Plan.md` | 实施顺序、依赖关系 |

### 6.4 Module 文档模板

每个模块文档建议包含以下章节：

```markdown
# Module XX: 模块名称

## 1. 目标
## 2. 用户故事
## 3. 业务规则
## 4. 功能清单
## 5. 页面/交互说明
## 6. API 接口（如已知）
## 7. 数据模型（如已知）
## 8. 验收标准
## 9. 风险与依赖
```

## 7. Stage 5：原型设计（按需）

### 7.1 触发条件

- 新模块首次设计
- 交互流程较复杂
- 需要向领导/业务方汇报确认

### 7.2 负责人

- **主要责任人**：chenrt
- **执行工具**：`prototype-designer` Agent

### 7.3 chenrt 动作

1. 准备原型任务卡，包含：需要展示的页面列表、关键业务流程、参考的 Module 文档
2. 调用 `prototype-designer` 生成原型到 `design/module-mvp-demo` 分支（命令见 [`04_Team_Git_Operations_Guide.md`](04_Team_Git_Operations_Guide.md) §5）
3. 在本地启动验证原型效果
4. 如需修改，继续与 Agent 迭代

> **v1.25 去重**：原型的详细设计规范（用户视角设计 / 两段评审 / 提示分区 / 组件选型）见 `.kimi/agents/prototype-designer.md`；此处只保留人视角的调用动作。

### 7.4 原型范围控制

- 使用 mock 数据，不连接真实后端
- 重点展示页面布局、导航、核心交互
- 不做复杂表单校验、权限控制、性能优化

---

## 8. Stage 6：原型评审

### 8.1 触发条件

- 原型分支已推送到远程仓库
- 或原型静态站点已部署

### 8.2 负责人

- **组织者**：chenrt
- **评审人**：guixm、zhaohy
- **记录人**：chenrt

### 8.3 评审重点

| 评审人 | 重点关注 |
|--------|----------|
| guixm | 是否符合运维管理目标、是否体现业务价值、是否便于汇报 |
| zhaohy | 是否符合一线操作习惯、字段是否完整、流程是否顺畅 |
| chenrt | 产品一致性、与全局架构是否冲突、是否可开发 |

### 8.4 评审结论

| 结论 | 后续动作 |
|------|----------|
| **通过** | 更新 Module 文档，进入技术预评审 |
| **小修改** | chenrt 迭代原型后再次确认（可异步） |
| **大修改** | 重新召开原型评审会 |
| **不通过** | 回退到需求拆解阶段，重新评估范围 |

### 8.5 原型分支处理

- 原型分支保留在远程仓库，供团队查看
- **不合并到 `develop`**
- 原型中的有效设计需在正式模块分支重新实现

---

## 9. Stage 7：技术预评审

### 9.1 触发条件

- 原型评审通过
- 需求文档已冻结初版

### 9.2 负责人

- **主要责任人**：zhangwq
- **配合人**：chenrt

### 9.3 zhangwq 动作

1. 阅读 Module 文档和原型
2. 评估技术方案，补充：API 路径设计、数据模型建议、关键算法或第三方依赖、性能/安全/可运维性风险
3. 在 Module 文档中补充技术约束部分（PRD 骨架规范见 `.kimi/agents/prototype-designer.md` Phase 3）
4. 反馈实现工作量和阻塞点

### 9.4 预评审输出

- Module 文档中的 API/数据模型章节补充
- 技术风险清单
- 是否需要调用 `planner` 输出详细实现计划

---

## 10. Stage 8：需求冻结

### 10.1 触发条件

- 原型评审通过
- 技术预评审完成
- chenrt 确认 Module 文档完整

### 10.2 负责人

- **主要责任人**：chenrt

### 10.3 冻结动作

1. 在 Module 文档顶部标注状态：`状态：已冻结`
2. 更新 `01_User_Stories.md` 状态为 `待开发`
3. 将模块加入 `05_Code_Implementation_Plan.md` 开发队列
4. 通知 zhangwq 准备开发

### 10.4 冻结后变更

- 原则上冻结后不再大改需求
- 如需变更，需重新走 Stage 3 需求拆解会
- 小范围字段调整可由 chenrt 和 zhangwq 协商，记录在变更日志中

---

## 11. 需求变更控制

### 11.1 变更类型

| 类型 | 定义 | 处理方式 |
|------|------|----------|
| 小调整 | 字段增减、文案修改、顺序调整 | chenrt + zhangwq 协商，记录变更日志 |
| 中调整 | 新增子功能、流程微调 | 更新 Module 文档，必要时补充原型 |
| 大调整 | 模块范围变更、目标用户变更 | 重新召开需求拆解会 |

### 11.2 变更记录模板

```markdown
## 变更记录

| 日期 | 变更人 | 变更内容 | 影响范围 | 审批人 |
|------|--------|----------|----------|--------|
| 2026-07-21 | zhaohy | 主机导入增加 "机柜" 字段 | Module_07 资源管理 | chenrt |
```
