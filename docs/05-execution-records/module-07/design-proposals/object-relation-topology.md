## 1. 需求背景

四层骨架（`platform → app → service → instance`）与五类资源归属分型落地后，**「实体」已齐，但「实体之间的关系」仍缺**。现状把关系压成了**单值外键字段**，于是暴露三个问题：

1. **字典不可删，用户困惑**：平台 / 应用 / 服务 / 业务四个「…管理」页红线均为「停用不删除」。这**是刻意设计而非缺陷**——四者都是 label 取值权威（`platform` / `app` / `svc` / `biz`），删了即断历史时序。但用户看到「叫什么什么管理却没有删除按钮」会质疑，需在 PRD 明确解释「字典 vs 对象」定位差异。
2. **应用↔平台做不了 M:N**：应用条目的 `platform_code` 是**单值可选父级**（§5.19 / §5.21），只能表达 `platform(1) → app(N)`。而现实是「一套软件（如数据开发利用工具系统）可同时在授权数据平台 + 实验室平台部署」，是 M:N。
3. **业务↔服务关系不可见**：服务字典**无 `biz_code` / 无 `app_code`**（§5.22），业务↔服务、应用↔服务的关联**全靠资源行同时填多个码隐式扛着**，字典层无关系、无维护入口。

**关键共识（chenrt 定档）**：从 Prometheus 运维角度，**归属聚合确实要下沉实例、用 label 扁平化管理**；但**拓扑关系在排障时价值极大**，必须**并行补齐**——二者不是二选一。

### 结论摘要

| # | 议题 | 结论 | 状态 |
|---|------|------|------|
| 1 | 字典「无删除」现象 | **维持不可删**（label 取值权威、停用不删除是正确生命周期）；在 PRD 明确「字典 ≠ 可删除对象」的定位解释 | ✅ 已澄清 |
| 2 | 应用 ↔ 平台 | 改为 **M:N**（`app_platform_rel` 关联表，含 `is_primary`）；`platform` label **下沉到资源行、以资源行一等字段唯一确定** | ✅ chenrt 已拍板 |
| 3 | 业务 ↔ 服务 | **默认方案：服务字典加可空 `biz_code`（N:1 主归属）+ 可空 `app_code`（应用↔服务 1:N）**；**备选方案：独立关系表**（`service_biz_rel` / `app_service_rel`）。**MVP 交付关系维护表单** | ✅ chenrt 已拍板（**提前至 MVP**） |
| 4 | 双轨定位 | **归属聚合（label 扁平）** 与 **对象拓扑（关系边）** 两轨并存、数据同源、用途解耦；拓扑边**不进 label** | ✅ 已澄清 |
| 5 | 资源实例层拓扑 | 五类资源间边（部署 `deployed_on` / 依赖 `depends_on` / 调用 `calls`）**{v0.3+}**，与 `service_dependency` 同批 | ✅ 待评审 |
| 6 | 版本落点 | **MVP：A 层字典关系全量落数据契约 + 关系维护表单（无聚合视图）**（`app_platform_rel` M:N + 资源行 `platform_code` 一等字段 + 服务字典关系字段）；**{v0.2}：业务 / 平台详情页聚合拓扑视图（只读）**；**{v0.3+}：资源实例边 + 连线拓扑图 / 影响面分析** | ✅ chenrt 定档（**A 层提前到 MVP**；“聚合视图”留 {v0.2}） |

## 2. 设计范围

- **在**：字典实体层关系建模——应用↔平台（M:N）、应用↔服务（1:N）、服务↔业务（N:1）、服务↔服务（N:N，§5.23 已有预留）。
- **在**：`platform` label 的**定性纠正 + 资源字段一等化**——`platform` **不是派生标签**，而是资源行的一等业务字段（登记期第一个确定的业务信息）；派生**降为兜底**（仅当资源行未显式填时用所属应用的主平台填充）。
- **在**：资源实例层关系（CI 拓扑）建模方向——部署 / 依赖 / 调用边的形态登记与版本归属。
- **在**：PRD 对「字典不可删」的定位解释（面向用户的说明性增量）。
- **不在**：**业务 / 平台详情页的聚合拓扑视图（只读）归 {v0.2}**（MVP 只落「数据契约 + 关系维护表单」）。
- **不在**：**连线拓扑图可视化 / 影响面分析归 {v0.3+}**；自动拓扑推导（trace / 服务发现，{v0.3+}）；`service_dependency` 本体实现（{v0.3+}，维持 §5.23 预留）。
- **不改**：四个字典的「编码不可变 + 展示名必填 + 停用不删除 + source 审计」红线；资源判重键（`platform_code` **不参与判重**）；五类资源归属分型（决策 108）。

## 3. 详细设计

### 3.1 双轨定位（总纲）

| 维度 | 数据形态 | 消费方 | 用途 | 是否进 label |
|---|---|---|---|---|
| **归属聚合**（扁平） | 资源行字段 → label（`platform` / `app` / `biz` / `svc`） | M01 生成 / M02 查询 | 聚合、过滤、看板、告警分组 | ✅ 是 |
| **对象拓扑**（关系） | 关系边表（`*_rel` / `*_dependency`） | M02 排障 / M08 降噪 | 影响面分析、根因定位、告警压制 | ❌ 否 |

**原则**：拓扑边**不参与 label 注入**，label **不承载拓扑**。两者**数据同源**（都源自登记数据），**用途解耦**——这样既保住 Prometheus 侧扁平聚合的干净，又补齐排障所需的图关系。

### 3.2 字典实体层拓扑（A 层）

| 关系 | 基数 | 关系表 / 承载 | label 是否跟随 | 交付版本 |
|---|---|---|---|---|
| 应用 ↔ 平台 | **M:N** | `app_platform_rel(app_code, platform_code, is_primary)` | **否**（`platform` 下沉资源行，见 §3.3） | **MVP** |
| 应用 ↔ 服务 | 1:N | **默认：**服务字典加**可空父级** `app_code`；**备选：**独立 `app_service_rel` | **否**（`svc` 独立，不经 app 派生） | **MVP** |
| 服务 ↔ 业务 | N:1（主归属唯一） | **默认：**服务字典加**可空** `biz_code`；**备选：**独立 `service_biz_rel` | **否**（`biz` 独立，不经 svc 派生） | **MVP** |
| 服务 ↔ 服务 | N:N | `service_dependency`（§5.23，已预留） | 否 | {v0.3+} |

> **统一口径（修正初稿内部矛盾）**：业务↔服务、应用↔服务的承载**默认方案 = 「服务字典加可空关系字段」**，**备选方案 = 独立关系表**；两类关系**不再表述为「必须建显式关系表」**。无论取默认或备选，字典字段 / 关系表都是**关系权威**，资源行字段只是**实例归属的镜像**（见 §3.5-④）。

> **为什么把关系落在字典（而非全靠资源行）**：资源行只能表达「某个实例同时填了哪些码」，**跨实例的实体关系（如「该应用包含哪些服务」）无法从资源行稳定推导**——某服务当前无实例时关系即丢失。故字典层需**显式**关系字段 / 关系表，拓扑才可独立维护与查询。

> **与决策 96 的关系**：决策 96 裁定的是 **biz ↔ app 横向正交**（「应用挂业务 / 业务挂应用」两个方向都不引入父子）。本提案的**服务↔业务**是**服务**（非应用）与业务的 N:1，且**只建显式关系、不改 biz↔app 正交**；**应用↔平台**是应用自身的纵向关系（决策 104 / 107 已确立），与之不冲突。

### 3.3 `platform` 定性纠正与一等字段化（核心）

**定性纠正（本提案最重要的改动）**：`platform` **不是派生标签**，而是**资源行的一等业务字段**——平台归属是**登记期第一个确定的业务信息**（先定平台，才知道这套软件部署在哪个平台上）。此前决策 104 把 `platform` 定为「纯派生标签、资源侧无 `platform_code` 字段」（对齐 `cloud` 经网域派生先例），**本提案修订该定性**。

**技术硬约束**：`platform` label 的取值**必须在资源行唯一确定**，不能在应用层多值。原派生链是 `资源 app_code → 应用父级 platform_code（单值）`；一旦应用可挂多个平台（M:N），同一 target 就不知该打哪个 `platform` label，`sum by (platform)` 将歧义（与决策 109 四层聚合口径冲突）。

**落地方案（MVP 交付）**：

- 资源行（Resource）新增**可空 `platform_code`**——**一等业务字段**（登记期显式填写，非纯派生）；
- **注入机制 = 标签模板 `resource_field` 映射**：默认标签模板新增 `platform_code → platform` 行，走 **target 级标签模板映射注入**（§5.13 默认模板 / §5.12.1 映射表）；**不走**配置生成器的 system 层派生（`cloud` / `zone` / `network_domain` 那一路）；
- **派生降为兜底**：仅当资源行**未显式填** `platform_code` 时，才用**所属应用的 `is_primary` 平台**兜底填充；未填且应用无主平台时**不注入** `platform`；
- `app_platform_rel` 的 M:N 关系**承担两件事**：①为兜底提供「应用主平台（`is_primary`）」；②留待 {v0.2} 聚合视图展示「该应用部署在哪些平台」；
- **资源登记表单级联顺序**：**先选平台 → 再选应用（按所选平台过滤）→ 再选服务**——平台是一等字段，故作为登记第一问。

**效果**：`数据开发利用工具系统` 在授权平台、实验室平台各有一组实例 → 各实例 `platform_code` 分别指向两平台，`sum by (platform)` **零歧义**；同时应用层能看见「一个应用横跨两平台」的关系。

> **显式声明（supersede）**：本提案**修订决策 104 的定性**——原定「`platform` 为纯派生标签、资源侧无 `platform_code` 字段」，现改为「**`platform_code` 为资源行一等业务字段，派生降为兜底**」。完整 supersede map 见 §3.8。

> **与决策 103（云上提网域）方向相反（纠正初稿的类比错误）**：初稿曾以「对齐 `cloud` 经网域派生先例（决策 103）」为类比，**该类比方向错误，此处纠正**——决策 103 是把 `cloud_code` **上提**到 NetworkDomain、资源侧**删字段**（网域是云 / 分区的唯一枢纽）；本提案是把 `platform_code` **下沉**到资源行、资源侧**加字段**。二者**方向相反、理由不同**：`cloud` 是**网域环境维度**（先登记网域即确定云与分区，N:1 上卷维度物化到资源会重复填写）；`platform` 是**业务组织维度**（登记期就需要、跨网域可部署，物化到资源行才唯一确定）。故**不得再以决策 103 为先例类比 `platform`**。

### 3.4 资源实例层拓扑（B 层，CI 模型关系）

五类资源**实例之间**的边，直接复用决策 108 的「组成 / 依赖 / 部署」三分型落成关系边：

| 资源实例关系 | 关系类型 | 语义 | 排障价值 |
|---|---|---|---|
| application / database / middleware → host | `deployed_on`（部署于） | 跑在哪台机器上 | 主机故障 → 反查受影响的 app / 库 / 中间件 |
| application → database / middleware | `depends_on`（依赖） | 应用依赖哪个库 / 中间件 | 库 / 中间件故障 → 定位受影响应用 |
| application → application | `depends_on` / `calls`（调用） | 服务间调用链 | 上游故障 → 下游影响面、根因链路 |

> 这一层对标蓝鲸 CMDB 的「关联关系 / 拓扑」模型，是**排障价值最大**的部分，也是最重的，**{v0.3+}** 与 `service_dependency` 同批落地（含**连线拓扑图 / 影响面分析**）。

### 3.5 A 层连带项（资源字段 / Excel / 迁移 / 约束）

A 层提前到 MVP 后，`platform_code` 下沉资源行带来以下**必须一并落地**的连带项：

| # | 连带项 | 口径 |
|---|---|---|
| ① | **Excel 模板新增列** | 五类资源导入模板**新增 `platform_code` 列（可空）**；application / generic\_target 适用，host / database / middleware 按平台为组织维度**也可填**（保持可空）。**导入语义：留空则按该资源所属 `app_code` 的 `is_primary` 平台兜底**（与登记期兜底同口径） |
| ② | **判重键不动** | 五类资源判重键（host `(domain, instance_ip)`；database / middleware / generic\_target `(domain, instance_ip, port)`；application `(domain, service_name, endpoint)`）**不变**；`platform_code` **不参与判重键**（平台是归属属性、非身份） |
| ③ | **存量迁移规则** | ① **存量资源**：`platform_code` 回填自「所属应用的父级平台」（原单值派生链的取值），做到存量 `platform` label 不断、时序不裂；② **存量应用**：现单值 `platform_code` **一次性转入 `app_platform_rel`（转入一行、`is_primary=true`）**，迁移后应用侧字段废弃 |
| ④ | **字段可读入口** | `platform_code` 须成为**资源字段可读入口**——标签模板映射可读到（`resource_field` 来源可选 `platform_code`），§5.12.1 映射表 / §5.13 默认模板 / 资源列表详情响应均需暴露该字段 |
| ⑤ | **`is_primary` 唯一性约束** | `app_platform_rel` 中**同一 `app_code` 至多一个 `is_primary=true`**（服务端唯一性校验；应用表单「主平台」单选）；兜底取值恒取该唯一主平台 |
| ⑥ | **平台停用 / 解绑处置** | ① **平台停用**：存量关联**保留历史值、不自动解绑**（沿用字典「停用不删除」语义）——应用 / 资源侧以「平台名（已停用）」标识展示，禁止新引用；② **解绑**：应用解除与某平台的关联时，**若某资源 `platform_code` 悬空（指向已解绑平台且该资源未显式填）**，登记期**不做强制改写**、仅提示（避免批量误改历史归属）；资源行显式填的 `platform_code` **不受应用解绑影响**（一等字段优先） |

### 3.6 label 维度分层与角色视图

**新增口径**：label 按**粒度 / 读者 / 用途**分三层——

| 层级 | label | 读者 | 用途 |
|---|---|---|---|
| **高维（粗粒度）** | `platform` / `biz` | 平台负责人 / 管理层 | 平台整体健康、跨应用汇总（管理视角） |
| **中维** | `app` / `env` / `cluster` / `network_domain` | 应用负责人 / 运维架构师 | 应用级 / 环境级 / 位置级聚合与过滤 |
| **低维（细粒度）** | `svc` / `resource_id` | 运维工程师 | 排障下钻、实例定位 |

**结论（`platform` 非排障主维度）**：`platform` 是**高维 / 粗粒度**维度，读者是平台负责人 / 管理层、用途是平台整体健康——**不应作为告警分析 / 看板的默认下钻入口**。运维排障的默认维度是 **`app` / `svc` / `network_domain` / `resource_category`**，`platform` 退为**顶层可选过滤器**（`platform → app → svc` 逐层下钻的可选顶层，而非默认起点）。

**跨模块建议（登记为契约 / 建议）**：
- **M08（告警分析）{v0.2+} 建议**：告警分组 / 降噪 / 分析视图的默认维度采用 `app` / `svc` / `network_domain` / `resource_category`，`platform` 作为可选顶层过滤器；
- **M05（看板）{v0.2+} 建议**：看板下钻入口默认从中 / 低维起步，`platform` 作为可选顶层过滤；平台维度聚合（`sum by (platform)`）仅用于管理视角汇总卡。

> 本结论**只登记契约与建议**，不修改 M05 / M08 PRD 正文（落 `design-decisions.md` 顶层跨模块契约区）。

### 3.7 字典「不可删」定位解释（面向用户）

在 PRD 明确：**平台 / 应用 / 服务 / 业务是「字典」（编码取值权威），不是「可删除的对象」**——四者编码即 label 值，删除会断历史时序，故生命周期为「启用 ↔ 停用」；真正可删除的是**资源（Resource）**（被采集 Job 引用时按 §6.1 阻断）。此解释同步进原型页面说明，消除「管理页为何无删除」的困惑。
