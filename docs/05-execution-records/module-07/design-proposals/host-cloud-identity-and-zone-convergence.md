## 2. 背景与根因

### 2.1 用户架构澄清（本轮对话）

- **混合云**：资源分布在**政务云**（内含**政务外网区** + **互联网区**）与**腾讯云**；
- **云命名现状**：**当前在用码仅 `PUB-TX`（腾讯云）**；政务云规划为同形制复合码 **`GM-CU`**（`GM` = 政务云，`CU` = 联通）；将来若由移动承载则按同形制 `GM-CM`（**暂不启用**）——即**同一朵政务云可由不同运营商承载**，且**云名会随时间变化**；
- **云类型**：**公有云 / 政务云 / 行业云 / 私有云需可区分**，其中**政务云本身是一种云类型**；**腾讯只是载体（厂商）之一**，同一载体可提供多种云类型，故 `TX` **不得**被等同于「公有云」；
- **接入形态**：中心直连节点位于**政务云互联网区**；
- **告警去向**：政务云与腾讯云的告警通知到**同一个运维团队**。

> 该澄清直接影响 §3 的职责划分：`cloud`/`zone` **不承担 Alertmanager 首级 route 分发**（同一团队、同一接收方），其价值需重新定位。

### 2.2 云厂商维度：字段存在，但链路「四断」

`cloud_code` 目前是**埋在后端模型、前端类型与 Excel 模板里，但 UI 一处置没渲染、后端列表也不返回**的状态：

| 环节 | 位置 | 现状 |
|------|------|------|
| 后端模型 | `platform/models/host.go` → `CloudCode` | ✅ 有列，能存库 |
| 前端实体类型 | `ui-custom/web/src/types/resource.ts` → `Host.cloud_code` | ✅ 有声明，无人引用 |
| Excel 模板 | `assets/templates/excel/host_template.md` §1 第 2 行 | ✅ 有列，导入可写库 |
| 后端列表返回 | `platform/config/resource/list.go` → `buildListItem` host 分支 | ❌ 不返回 `cloud_code` |
| 前端列表行类型 | `ui-custom/web/src/pages/resources/useResources.ts` → `ResourceListItem` | ❌ host 平铺字段无 `cloud_code` |
| 列表表格列 | `ui-custom/web/src/pages/resources/ResourcesPage.tsx` → host `buildColumns` | ❌ 无「云」列 |
| 新增/编辑表单 | `ui-custom/web/src/pages/resources/ResourceFormDrawer.tsx` → host `renderTypeFields` / `buildTypeFields` | ❌ 无输入、不提交 |
| 详情抽屉 | `ui-custom/web/src/pages/resources/ResourceDetailDrawer.tsx` → host `typeItems` | ❌ 不展示 |
| 标签生成链路 | `platform/models/resource_fields.go` → `getHostField` / `LegacyFieldMap`；`platform/models/label_template.go` → `DefaultMappingBuilders` | ❌ 均无 `cloud_code`，**导入了也不会变成 label** |

**即：Excel 导入能进库，但列表看不见、表单改不了、详情不展示、标签不生成。**

### 2.3 分区维度：同一概念建模两次，枚举互不相同

| | 网域「网络分区」 | 主机「区域-环境」 |
|---|---|---|
| 字段 | `network_domain.zone_type` | `host.zone_env` |
| 值域 | `internet` / `extranet` / `private-line` / `dmz`（`platform/models/zone_type.go` 定义，seed 仅启用前两项） | `INT` / `GOV`（`host_template.md` §2.2 硬编码两值） |
| 枚举来源 | 部署级只读字典 `ZoneType`（`platform/db/seed/zone_type.go`） | Excel 模板硬编码 |
| 表单性质 | 网域登记可选项（`ui-custom/web/src/pages/admin/domains/DomainForm.tsx`，label「网络分区（可选）」） | 仅 Excel 导入列，前端无表单/列表/详情 |

**根因判定**：这不是「用户填错」，而是**系统提供了两套词汇描述同一个东西**。在此前提下要求「引导用户保持一致」，等于用流程补丁掩盖数据模型缺陷。

**命名现状更需一并收敛**：同一「政务外网」概念目前存在 **三种叫法**——字典 code 注释写「外网区」（`zone_type.go` `ZoneTypeExtranet`）、字典 display_name 写「政务外网区」（`seed/zone_type.go`）、Excel 模板写「政务网区」（`host_template.md` §2.2）。收敛时必须统一为 1 个 code + 1 个 display_name。

## 3. 设计原则：三个维度正交，互不推断

| 维度 | 承载字段 | 语义 | 决定什么 |
|------|----------|------|----------|
| **云标识** | `cloud_code`（+ 字典描述属性 `cloud_type` / `carrier`） | 资源归属哪朵云整体（腾讯云 / 政务云·联通） | 告警**分组/去重/定位/静默**、跨云指标聚合维度 |
| **网络分区** | `network_domain.zone_type` | 分区隔离边界（互联网区 / 政务外网区） | 同上（分组/定位）；**不**决定下发通道 |
| **接入通道** | `network_domain_id` / `channel` | 网络可达性与下发方式（`local` 中心直连 / `agent_pull` 边缘拉包） | **配置怎么下发** |

> **云类型 / 云载体不是独立的告警维度**。它们作为 `cloud_code` 的**字典描述属性**存在（用于展示、分类、筛选），但告警与 `group_by` 只面向「云」这个**整体**（`cloud` label 的复合值），用户不会单独按类型或载体告警——因此上表列的是**三个**维度，而非四维。

**两条红线**：

1. **不得用 `cloud`/`zone` 推断下发通道**。中心直连节点在政务云互联网区，只说明该区走 `management` 域 `local` 直采；通道判定永远由 `network_domain` 承载。
2. **告警分发职责已按澄清收窄**。两朵云的告警通知到同一团队 ⇒ `cloud`/`zone` 不再承担 Alertmanager 首级 route 分发；其职责为 `group_by` 区分、同名实例去重、告警文案定位（「政务外网区 · 某机 · 磁盘」）、静默与筛选定位。**因此这两条 label 属「治理与可读性」收益，不是「分发正确性」的必要条件** —— 这也意味着它们可以分阶段落地，不阻塞当前 MVP。

## 4. 详细设计

### 4.1 云维度（`cloud_code` + 云字典）

**决策：代码做标识，名称做展示，沿用项目既有「字典模式」。**

项目内已有完全一致的先例：`AppCode → 应用字典 AppName`（决策 92）、`os_dict`、`zone_type`。云厂商按同一套路收敛：

| 职责 | 字段 | 取值 | 用途 |
|------|------|------|------|
| 稳定身份 / 标签 / 筛选 / 聚合 | `cloud_code` | 稳定复合码，如 `PUB-TX`（腾讯云）、`GM-CU`（政务云·联通） | 进 Prometheus label、规则过滤、聚合分组 |
| 云类型（描述属性） | `cloud_type`（云字典条目属性） | `公有云` / `政务云` / `行业云` / `私有云` | 展示、分类、筛选；**非告警维度** |
| 云载体（描述属性） | `carrier`（云字典条目属性） | `腾讯` / `联通` / `移动` | 展示、分类、筛选；**非告警维度** |
| 人类可读展示 | `cloud_name`（字典派生） | `腾讯云`、`政务云（联通）` | 前端表格列、筛选下拉、告警文案 |

**为什么不用中文名称直接当标识（用户已确认「名字会变化」）**：云名称一旦成为 label value，会进入 series 标签集、参与 `group_by`、静默匹配与通知模板变量；中文 UTF-8 在 matcher、webhook 透传链路中更易出编码/转义问题。更重要的是——

> **用户已确认：载体（厂商）名字会随时间变化**——`TX`（腾讯）、`CU`（联通）、`CM`（移动）是**载体**名字；当前在用云 code 仅 `PUB-TX`（腾讯云 = 公有云·腾讯），政务云规划为同形制复合码 `GM-CU`（`GM`=政务云、`CU`=联通）。

这意味着**展示名是易变的、身份必须稳定**。若把名字直接当标识，每次改名都会牵连已写入 TSDB 的历史标签、已下发的规则与静默，且无法追溯。故：**code 恒稳定、name 可自由演进**，两者解耦是本设计的第一性理由，而非仅仅「中文不好处理」。

**命名形制统一修正（本节修正要点，用户明确）**：`TX` 只是**载体**（腾讯），不再单独充当云 code；腾讯云的完整云 code 为 **`PUB-TX`**（公有云 `PUB` + 载体 `TX`），**不得把 `TX` 等同于「公有云」**。

> 用户指出：**腾讯作为厂商，可能同时提供公有云、行业云、私有云**；「公有云」是**云类型**，与厂商（载体）不是同一维度，必须分开表达——这正是复合码 `{类型}-{载体}` 的由来。

因此确立本节的**核心模型**：**一个云 = 云类型 × 云载体 的组合（整体不可分割）**；`cloud_code` 标识的是这个**整体**，云类型、云载体则是该整体的两个**描述属性**。原设计把腾讯云的云 code 写成单 token `TX`（只编码载体）是**不完整**的，已统一为复合码 `PUB-TX`（公有云 + 腾讯）；其展示名为「腾讯云」、云类型标注为「公有云」。

> 对照：`PUB-TX` 中 `PUB`=公有云（**云类型**）、`TX`=腾讯（**云载体**）；`GM-CU` 中 `GM`=政务云（**一种云类型**）、`CU`=联通（**云载体**）——类型与载体合起来，才是「腾讯云」「政务云·联通」各自的完整身份。

**落地方案（对齐 `os_dict` / `zone_type` 模式）**：

1. **命名形制（统一 `{类型}-{载体}` 复合码）**：一个云的完整 code = **云类型 + 云载体 的复合码**，形制统一为 `{类型}-{载体}`（大写短码）。**腾讯云也须改为复合码 `PUB-TX`（公有云 + 腾讯），不再使用单 token `TX` 作为云 code**——`TX` 退化为**载体 code**（仅承担字典的载体描述属性）。当前**在用值仅 `PUB-TX`**。

2. 新增**云字典表**（`cloud_dict`）与 seed，登记如下（`cloud_type`、`carrier` 为**描述属性**，均为大写短码）：

   | code | display_name | **云类型 `cloud_type`** | **载体 `carrier`** | 说明 |
   |---|---|---|---|---|
   | `PUB-TX` | 腾讯云 | `PUB` 公有云 | `TX` 腾讯 | **当前唯一在用值**；历史 Excel 值 `TX` **归一至此**（`TX → PUB-TX`） |
   | `GM-CU` | 政务云（联通） | `GM` 政务云 | `CU` 联通 | **规划中**；历史 Excel 值 `CU` 归一至此 |
   | *（不预置）* | — | — | — | 政务云改由移动承载 → 同形制 `GM-CM`；腾讯若提供行业云/私有云 → `IND-TX` / `PRI-TX` 另登记独立条目。均**不预先占用** |

3. 主机 `cloud_code` 存编码（列已存在，不改名），前端提交/展示均以此为唯一权威；
4. 前端表格/筛选展示 `cloud_name`（字典解析，缺条目回退 `cloud_code`），停用云以「（已停用）」标识 —— 完全复用 `resolveAppName` / `isAppDisabled` 既有模式；
5. **历史 Excel 值归一化**：`TX → PUB-TX`（腾讯云）、`CU → GM-CU`（政务云·联通）。归一映射在导入层实现，映射规则本身即「名字 → 稳定身份」的落地。

**「政务云多载体」建模范式 —— ✅ 已拍板：扁平多条目**

用户已确认采用**扁平多条目**：每个「云（类型+载体）」组合**独立占一条字典项**，形态即 `PUB-TX` / `GM-CU` / （将来）`GM-CM`。该范式与复合码形制天然一致——**code 自身就编码了云类型与云载体**。

| 要点 | 说明 |
|---|---|
| 一维一 label | 云标识始终只占**一个** Prometheus 维度（`cloud`），`group_by (cloud)` 语义直白；规则/静默可直接写死 value，无需组合条件 |
| 「全部政务云」聚合 | 用正则 `cloud=~"GM-.*"`（Prometheus / Alertmanager matcher 均支持），可接受 |
| 未采纳 | 两级拆分（`cloud_code` + `cloud_carrier`）——需多一个字段与一条 label，而当前仅 1 条真实数据，属**为假设需求提前付费**；若将来「全部政务云」聚合成为硬需求，再走独立提案升格，**升格成本低于过早引入冗余维度** |

**云的类型与载体（`cloud_type` / `carrier`）—— 本轮修正的落点（✅ 已拍板）**

用户对「云」的定义已收敛为：**「云」= 云类型 + 云载体，二者合起来才是一个不可分割的云整体**。具体口径：

**云类型（cloud type，云的形态分类，大写短码）—— 政务云本身即一种云类型**：

| code | 展示名 | 说明 |
|---|---|---|
| `PUB` | 公有云 | 面向公众的多租户云；对应 `PUB-TX` 腾讯云 |
| `GM` | 政务云 | **政务专属云，本身即一种云类型**；对应 `GM-CU` 政务云 |
| `IND` | 行业云 | 面向特定行业的专属云 |
| `PRI` | 私有云 | 单租户专属部署 |

**云载体（carrier / 厂商，云的承建与运营方，大写短码）**：

| code | 名称 |
|---|---|
| `TX` | 腾讯 |
| `CU` | 联通 |
| `CM` | 移动（预留，暂不登记） |

**一个云 = 云类型 × 云载体 的组合（整体不可分割，code = `{类型}-{载体}`）**：

| 云 code | 云 = 类型 + 载体 | 状态 |
|---|---|---|
| `PUB-TX` | 公有云 + 腾讯 | 当前唯一在用 |
| `GM-CU` | 政务云 + 联通 | 规划中 |
| `GM-CM` | 政务云 + 移动 | 未登记（预留形制） |

**核心结论（用户明确，直接决定承载方式）**：

> **用户对告警规则的考虑是「面对『云』这个整体」，不会单独按云类型告警，也不会单独按云载体告警。**

因此：

- **云类型、云载体都只是云字典条目的描述属性**（用于展示 / 分类 / 筛选），**不独立成主机字段、不独立成 label、不独立成告警维度**；
- 告警与 `group_by` 只面向**复合 `cloud` label 这个单一整体**（如 `cloud="GM-CU"`、`cloud="PUB-TX"`）；
- 若将来确需「按类型聚合全部政务云」，用正则 `cloud=~"GM-.*"` 即可，无需拆分维度。

> 这同时**回退**了上一版（v0.4）「云类型独立成维、考虑独立 label（方式 B）」的过度设计：既然用户明确不单独告警类型/载体，就没有理由为它们各开一个 label 维度。简化后，云类型/载体收敛为**字典条目属性**（原 §8 开放项 ④，现已闭环为方式 A）。

> **命名形制已统一（本轮修正要点）**：所有云 code 一律 `{类型}-{载体}` 复合码，类型与载体均为大写短码——`PUB-TX`（腾讯云）、`GM-CU`（政务云·联通）。`TX` 仅作为**载体 code** 存在，不再单独充当云 code。类型 code `PUB` / `GM` / `IND` / `PRI` 中，`GM` 为用户既定，`PUB` / `IND` / `PRI` 为本次暂定，**若产品侧已有既定类型缩写，回填 PRD 时统一替换**。

### 4.2 网络分区维度（方案 A · 已拍板）

**核心判断：分区的本质是网络可达性/隔离边界，是「一个网域整体」的属性，不是单台主机各填各的。**

主机已归属网域（`host.network_domain_id` 在导入时按 `ip_cidrs` 自动推导），**同一网域内主机的分区必然等于该网域的 `zone_type`** ⇒ `host.zone_env` 是冗余字段。

**方案 A（采纳）：主机不设独立分区字段，云内分区 = 所属网域的 `zone_type`，只读派生展示。**

| 项 | 设计 |
|---|---|
| 唯一权威 | `network_domain.zone_type`（网域登记时选一次，入口已存在） |
| 主机侧 | **不新增**分区字段/表单项；列表与详情如需展示「互联网区/政务外网区」，经 `network_domain_id` 关联解析 `zone_type` 的 `display_name` |
| 接口层 | 后端列表 item 可**派生**返回 `zone_type`（host 专属派生字段，只读，非独立列） |
| CMDB 预留语义 | 由 `zone_type` 字典承载（它本就是「部署级只读字典」，正适合映射对齐）；CMDB 对接时系统可给出**权威且唯一**的云分区值，优于在主机表冗余一份造成双写漂移 |
| 用户侧 | **不存在「两处填一致」的问题，因此不需要任何引导话术** |

## 6. 验收标准

1. **云维度可见可维护**：主机 Tab 列表展示「云」列（显示名）、新增/编辑表单可维护 `cloud_code`、详情抽屉展示云标识，三处口径一致（显示名经字典解析，缺条目回退 code）；**云类型 / 云载体作为字典描述属性可区分展示（公有云 / 政务云 / 行业云 / 私有云 × 腾讯 / 联通 / 移动），但 `PUB-TX` 的展示名须为「腾讯云」，不得为「公有云」**。
2. **云维度进标签**：主机默认模板生成 `cloud` label，值等于 `cloud_code`（不含中文）；存量库经幂等补映射后同样生效。
3. **分区单一权威**：`network_domain.zone_type` 为分区唯一来源；主机侧**无**可编辑的分区输入；主机详情「网络分区」为只读派生展示。
4. **无冗余填写动线**：全流程不存在「同一分区需在两处填写」的入口，验收时需确认**无需任何一致性引导文案**。
5. **枚举收敛**：`zone_type` 与 `zone_env` 映射规则可验证（`INT↔internet`、`GOV↔extranet`）；字典命名唯一，不再出现「外网区/政务外网区/政务网区」三种叫法。
6. **无回归**：五类资源列表契约字段稳定（非 host 类不受影响）；`make check-repo-map` 与全量 `go test ./platform/...` 通过；前端 `pnpm test` / `pnpm lint` 通过。
7. **改名不伤身份**：字典 `display_name` 变更（如「政务云（联通）」改名）**不影响**已落库的 `cloud_code`、已写入的 `cloud` label、已下发的规则与静默；验证方式为改字典名后重查，序列标签与规则匹配结果不变。
8. **不越界**：不改动 `upstream/`；不修改 `docs/02-product-requirements/` 与 `docs/prototypes/`（由产品负责人评审后统一回填）。
