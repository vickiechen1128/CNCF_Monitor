# M02 查询中心 vs M08 告警收敛与通知管理：功能边界与注入代理设计思路

> **文档性质**：跨模块设计分析与决策依据说明（非 PRD，不承载开发契约）
> **关联决策**：决策 55 / 56 / 57（全文见同目录 `design-decisions.md`「决策 9」）
> **日期**：2026-08-31
> **触发**：用户评审中提出「M02 的当前告警与 M08 的告警状态是否重复」「M02 是否应单独成模块」「注入代理的必要性」「network_domain 是否应强制注入」四个问题，经两轮讨论后收敛为本文结论。

## 1. 问题背景

评审 M02（查询中心）与 M08（告警收敛与通知管理）PRD 时发现表面重叠：M02 v0.3 规划代理 Prometheus `/api/v1/alerts`（当前 firing/pending 告警），M08 v0.3 规划「告警状态查看」。需要回答：

1. 两者是否真的重复？
2. M02 偏后台 API、为全局排障做准备，是否还应单独成模块？
3. 重叠功能归属哪个模块更适合（产品设计 + 用户动线视角）？
4. M02 的租户/网域注入代理是否必要？M08 直连 Alertmanager 是否可以？去掉注入代理是否更利于未来对接夜莺等开源告警产品？
5. `tenant_id` 服务端强制注入可以接受，但 `network_domain` 是部署拓扑维度、业务通常跨网域，是否应强制注入？

## 2. M02 / M08 功能异同对照

### 2.1 职责对照表

| 维度 | M02 查询中心 | M08 告警收敛与通知管理 |
|------|-------------|----------------------|
| 核心定位 | **查询代理 + 隔离执行点**：带租户/网域上下文注入的 Prometheus Query API 代理 | **告警域工作台**：Alertmanager 的接收人/路由/静默/抑制 UI 化管理 + 通知状态 |
| 数据源 | Prometheus（`/api/v1/query*`、`/targets`、`/alerts`、`/rules`） | Alertmanager（`alertmanager.yml`、AM API） |
| 写操作 | 无（只读代理） | 有（生成 alertmanager.yml、reload、创建/删除静默） |
| 持有状态 | 无状态 | 有状态（Receiver/Route/Silence/InhibitionRule/AlertmanagerConfigVersion） |
| 用户可见页面 | 查询页（P0）；目标状态页（P1 极简，全局排障兜底） | 接收人/路由/静默/抑制管理页；告警状态页 |
| 典型消费方 | M01 Job 回显、M07 badge、M08 告警状态页、Grafana（强制）、M05 首页、Open API | 运维工程师直接操作 |
| 版本重心 | MVP 即 P0（注入骨架 + targets 代理） | MVP 起（配置文件管理），告警状态页 v0.3 |

### 2.2 「告警状态」重叠的真实形态

「当前告警」在数据链路上天然分两层，重叠只是措辞层面的：

| 层 | 内容 | 归属 |
|----|------|------|
| **API 层** | 代理 Prometheus `/api/v1/alerts`，注入租户/网域上下文 | **M02**（注入是 M02 的存在意义） |
| **页面层** | 告警状态页：同页展示 Prometheus firing/pending（来自 M02 API）+ Alertmanager 通知状态（active/silenced/inhibited） | **M08**（告警域工作台） |

修复前 M02 PRD §11.1 验收项 9 的「告警状态页展示…」措辞越界（查询代理模块不应交付页面），已在 v1.7 收敛为「API 供 M08 告警状态页消费」。

### 2.3 用户动线（心智）分析

**归属判定的核心依据是用户任务链，而非数据源：**

- **告警处理链**（M08 语境）：什么出了问题（firing/pending）→ 通知了谁/是否被静默（通知状态）→ 要不要加静默、调路由（操作）。三个环节语境全是「告警」，拆到两个菜单会迫使用户在同一条告警上来回跳转对照——那是按数据源切页面，不是按用户任务切页面。
- **查询排障链**（M02 语境）：指标异常/怀疑没采到 → 写 PromQL 验证 → 看 target 采集状态（up/down、lastError）→ 定位采集问题还是数据问题。语境是「查询与排障」，与告警处理是两类心智任务。

**结论：告警状态页归 M08；M02 只提供注入代理 API，告警完全退出 M02 的 UI 叙事。**

## 3. M02 单独成模块的必要性

### 3.1 能力维度：必须独立，且是 P0 级安全模块

M02 的核心不是「查询」而是**租户/网域注入代理**——全平台唯一执行 `tenant_id`/`network_domain` 授权约束的位置：

- **底层组件零多租户**：Prometheus / Alertmanager 原生无认证、无租户概念，能连上 `:9090` 即可查全部数据；Alertmanager 的静默规则全局生效（租户 A 的宽 matcher 静默可摁掉租户 B 的告警）。隔离层必须外挂在组件前面。
- **唯一执行点原则**：隔离强度 = 最弱访问路径。允许任何消费方直连（Grafana、M08、外部 API）都意味着隔离语义被复制 N 份，任何一处漏注入即跨租户泄露。决策 50（Grafana 数据源强制指向 M02）与决策 49（否决 Grafana Alerting/夜莺，因其自带查询路径绕开注入）都是在守这一条。
- **代理先行比事后回填便宜**：MVP 注入是恒值骨架（default 网域 + platform_admin 租户），成本极低；若 MVP 让各消费方直连，v0.2 再逐个改道，漏改一个就是安全事故。先把门立在那里，v0.2 只需装锁。

**「薄 UI、厚约束」的模块恰恰最需要独立成模块**——它的价值是约束而不是页面。

### 3.2 产品形态维度：用户直觉正确

M02 的用户可见交付物确实薄：查询页（P0）、目标状态页（已降 P1）、告警相关仅存在于 API 层。它定位为「全局排障的最后一个入口」，不是用户日常动线的主路径。这与其能力定位自洽，无需拆分或降级。

### 3.3 对「去掉注入代理便于对接夜莺」的回应

- **代理不是对接夜莺的障碍，配置生成架构才是**。若未来整体转向夜莺，要放弃的是 M09 文件化配置流水线（prometheus.yml/rules.yml 生成、ConfigDraft 确认、Edge 离线包）与 Alertmanager 选型——夜莺规则/通知策略为 DB 驱动，与声明式文件配置不兼容。薄薄一层 Go 代理在那种场景下重写成本可忽略。
- **代理反而保护可替换性**：所有消费者只认 M02 的 Prometheus 兼容 API，中心存储换成 VictoriaMetrics 时消费者零改动（防腐层）；去掉代理直连 `:9090` 才是真正把平台焊死在 Prometheus 上。
- 退出条件：若产品定位收缩为单租户内部工具，注入代理可简化。它是产品决策（企业级多租户、隔离网域交付）的函数，不是普适技术真理。

## 4. 注入语义三层模型（决策 56）

用户的判断「tenant_id 强制注入可接受、network_domain 不应强制注入、业务跨网域」成立，且与既有设计同向——「自动注入 network_domain」的措辞容易读歪为「锁定单网域」，实际语义是**授权集合收敛**。明确为三层：

| 层 | 执行位置 | 语义 |
|----|----------|------|
| `tenant_id` | 服务端**强制注入** | **硬隔离边界**，永远存在，用户不可见不可改 |
| `network_domain` 授权集合 | 服务端**强制校验** | **软授权边界**：查询结果不得越出用户授权网域集合；授权集合 = 租户全部网域时**不注入任何 matcher**（零感知，与裸查 Prometheus 一致）；用户显式 matcher 收敛于授权集合，越权返回空 |
| `network_domain` 筛选 | 前端/用户 | 纯 UX：授权集合内自由下钻、按业务线聚合；**不承担任何安全职责** |

**红线：安全必须服务端执行。** 只要「只被允许看某网域」是授权要求，前端筛选就是视觉遮蔽（curl 即绕过），不构成权限。前端筛选只承担体验。

**实际体验**：授权全部网域的运维查 `sum by (biz)` 时系统零注入，跨网域业务聚合天然成立（与决策 51 补充一致）；只授权 gov-cloud-a 的值班员，服务端把结果钉死在 a 网域内，前端怎么筛都出不去。

**Alertmanager 侧同步约束（M08 落点）**：

1. **读路径**：M08 代理 AM `/api/v1/alerts` 时服务端强制注入授权集合 filter，不信任前端传参；
2. **写路径**：创建静默/抑制时校验 matcher 收敛于该用户授权网域集合——静默全局生效，不校验即为跨租户写武器。

## 5. 部署拓扑与存储可替换性（决策 57）

- **拓扑确认**：1 控制面 + N 采集节点的扁平化部署为确定形态。
- **中心存储可替换**：预留从 Prometheus 换为 VictoriaMetrics 的可能。M02 代理作为防腐层保证替换时消费方零改动。
- **隔离契约保持标签制**：`tenant_id`/`network_domain` 由 M09 `external_labels` 在写入侧打标、M02 在查询侧校验——Prometheus 与 VM 单机/集群通吃，边缘 remote_write 已按此打标，换存储不改契约。
- **v0.2 架构决策点**：若采用 VM 集群版，可评估其原生多租户（vmauth + accountID 路由，隔离下沉、M02 退化为 user→accountID 映射）。暂定保持标签隔离（契约单一、可回切 Prometheus），v0.2 开启多租户语义前正式评审。
- **告警分发前期形态**：M08 前期以维护 `alertmanager.yml` 配置文件落地（UI 生成文件 + reload），维持决策 49 的文件化配置闭环，不引入 DB 驱动方案。

## 7. 被否掉的备选方案（留存备查）

| 备选方案 | 否决理由 |
|----------|----------|
| 安全要求由前端筛选承担 | 前端筛选 = 视觉遮蔽，curl 即绕过；授权边界必须服务端执行 |
| M08 直连 Alertmanager 且不做过滤 | AM 无租户概念，读路径泄露 + 静默全局生效构成跨租户写武器 |
| 去掉 M02 注入代理以便对接夜莺 | 代理非对接障碍（配置流水线才是）；代理是防腐层，去掉反而焊死 Prometheus |
| M02 降级/合并进其他模块 | 注入是唯一安全执行点，拆散即隔离不可证明；「薄 UI 厚约束」模块更应独立 |
