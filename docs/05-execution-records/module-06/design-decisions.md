## 补充对齐：2026-08-15（M06 网域行政层与 M09 监控纳管层拆分）

- **参与 Agent**：prototype-designer
- **触发原因**：用户指出 M06「网域生命周期管理」与 M09「网域注册页」存在功能重叠，需明确职责边界。
- **关联模块**：Module_09、Module_01、Module_07。

### 关键决策

#### 决策 4：M06 作为 NetworkDomain 行政 Owner

- **问题**：M06 与 M09 各自应管理 `NetworkDomain` 的哪些字段和流程？
- **结论**：
  1. **M06 是网域的行政 Owner**：负责创建、编辑、禁用、删除网域，以及将网域分配给租户、设置配额。
  2. M06 网域创建/编辑表单只维护行政信息：`id`（可自动生成）、`name`、`tenant_id`、`status`；**不包含**监控参数（`agent_type`、`remote_write_url`、WAL 参数等）。
  3. `Tenant.network_domain_ids` 表示「该租户被授权可使用的网域列表」，但**不等于**这些网域都已接入监控；真正的「已纳管」状态由 M09 维护。
  4. `platform_admin` 租户拥有 `default` 管理域，系统预置且默认视为已存在；`default` 的监控纳管状态由 M09 特殊处理（中心 Prometheus 直接采集，不部署 Edge Agent）。
- **依据**：M06 是权限与平台管理模块，必须先确认租户对网域的拥有权；M09 是监控运维模块，只在用户有实际监控需求时执行纳管。
- **影响范围**：M06 PRD 3.1 / 5.1；网域创建/编辑页字段；租户详情页「被授权网域」展示。

#### 决策 5：租户内按网域授权的 RBAC 预留 {v1.0+}

- **问题**：用户提出「按不同域对人分权限管理」，是否把网域抬到租户之上？
- **结论**：
  1. **权限顶层仍是 Tenant**；网域不作为最高权限边界。
  2. v1.0+ 或外部 IAM 接入后，可在租户内角色策略中增加 `network_domain_id` scope，实现「某用户在医院 A 专网是 editor、在医院 B 专网是 viewer」。
  3. MVP / v0.2 阶段不做细粒度按域授权，仅保证租户级数据隔离。
- **依据**：M06 PRD 关键约束已明确「MetricCenter 不存在跨租户的全局平台管理员身份」。
- **影响范围**：M06 PRD 3.1 / 5.1；用户/角色权限设计（v1.0+）。

- [x] 权限顶层仍是 Tenant，网域仅作为租户内二级授权维度（v1.0+）（用户确认）。

## 补充对齐：2026-08-18（MVP 租户语义、登录模型与网域分类）

- **参与 Agent**：chenrt、AI 助手

- **关联模块**：Module_03（网关认证，MVP 不实现）、Module_09（网域纳管层）。

### 关键决策

#### 决策 7：租户 = 数据隔离与权限作用域单位，不是公司客户

- **问题**：租户应定义为「公司客户」还是「客户内部的业务单元」？
- **结论**：
  1. 租户 = 数据隔离与权限作用域单位，与 BlueKing CMDB 的 Business 1:1 映射；
  2. 「公司客户」是更外层的运营/交付概念，由私有化部署实例本身承担；
  3. MVP 只存在系统预置租户 `platform_admin`，租户 CRUD 归 v0.2。
- **依据**：M06 PRD §3.3（Tenant ↔ CMDB Business 1:1）、§10 术语映射、原型 mock 租户示例（平台运营部/电商业务/金融业务）。
- **影响范围**：M06 PRD 3.3 / 10 术语映射、MVP 范围说明。

#### 决策 8：MVP 不实现登录，但数据模型按「租户 + 用户 + 密码」三段式预留

- **问题**：登录页是否要走「租户名 + 密码」两段式？
- **结论**：
  1. 长期方向为「租户名 + 用户名 + 密码」三段式：租户名定作用域、用户名定操作人、密码做认证；
  2. MVP 不开发 M03 网关认证功能，网域管理接口在 MVP 期间处于无细粒度鉴权状态，依赖部署网络隔离；
  3. PRD 需显式声明 MVP 无鉴权是已知风险；
  4. 即使 MVP 只有 `platform_admin` 租户管理员，数据模型也要从「用户挂靠租户」开始设计，避免 v1.0 接入 IAM/SSO 时推翻认证体系。
- **依据**：M06 PRD §6.3（用户/权限 v1.0+ 或外部 IAM 承接）。
- **影响范围**：M06 PRD 6.3、MVP 风险说明；M03 PRD 认证/登录页范围（MVP 不实现）。

#### 决策 9：网域术语统一为「管理域 / 边缘域」，且全系统仅有一个管理域

- **问题**：用户原话中的「配置域」与 PRD 中的「边缘域」如何统一？
- **结论**：
  1. 统一使用「管理域」与「边缘域」：管理域由系统预置（`default`），其余用户创建的采集网域均为边缘域；
  2. 全系统有且只有一个管理域；
  3. 创建网域接口不接受 `domain_type=management`；编辑接口不允许修改 `domain_type`。
- **依据**：M06 PRD 3.2 / 5.2 `domain_type` 枚举与状态机。
- **影响范围**：M06 PRD §10 术语映射、网域创建/编辑接口约束、验收标准。

#### 决策 10：`zone_type` 受控字典 + `category` 自由分类双字段

- **问题**：用户希望网域分类「用户想怎么管就怎么管」，但 PRD 已规定 `zone_type` 来自部署级字典、不开放自由文本。
- **结论**：
  1. `zone_type` 保持受控：其值会进入 M09 指标标签，必须受控以保证 PromQL 聚合查询稳定；
  2. 受控体现在「值集受控」，用户填写时从下拉框选择，不能自由输入；
  3. 用户的自由分类诉求由新增字段 `category`（行政分组）承接，`category` 不进标签、可自由文本或租户级自维护；
  4. 字典治理规则：条目 = `code`（进标签，不可变） + `display_name`（展示用，可改） + `description`；被引用的条目只能停用不能删除；后端校验 `zone_type` 属于启用字典项；
  5. MVP 采用配置文件预置字典 + 只读接口 `GET /api/v2/platform/zone-types`；v0.2 升级为「平台预置 + 租户扩展」两级字典，并增加字典维护入口。
- **依据**：M06 PRD 3.2（`zone_type` 部署级字典与标签注入语义）、验收标准 L307（zone_type 不开放自由文本）。
- **影响范围**：M06 PRD 3.2 / 5.2 / 6.2 / 11.2；网域数据模型新增 `category` 字段（待确认是否进 MVP）；M09 指标标签注入。

#### 决策 11：网域 ID 从 MVP 起强制租户前缀

- **问题**：PRD 建议 `network_domain_id` 采用 `<tenant_id>-<domain_code>` 前缀，但 MVP 单租户下是否执行？
- **结论**：
  1. MVP 起所有用户创建的网域 ID 强制按 `<tenant_id>-<domain_code>` 自动生成；
  2. `default` 管理域是唯一例外（历史预置）。
- **依据**：M06 PRD 3.2 `network_domain_id` 全局唯一与租户前缀建议、技术验收 9.2。
- **影响范围**：M06 PRD 4.1 / 6.2 / 9.2；网域创建接口实现；v0.2 多租户上线无需数据迁移。

## 补充对齐：2026-08-19（MVP 业务登记入口与网域-业务正交性）

- **参与 Agent**：chenrt、AI 助手
- **触发原因**：用户明确 MVP 场景为项目交付、单一运维团队、网域固定、业务多样；追问业务登记入口位置、蓝鲸 CMDB 业务映射方式，以及多业务共用网域的处理。
- **关联模块**：Module_07（业务分组与资源必填）、Module_04（CMDB 业务同步）、Module_09（标签注入链路）。

### 关键决策

#### 决策 12：MVP 单租户 = 单一项目空间，租户 ≠ 业务

- **问题**：MVP 单租户模式下，租户、网域、业务三者的关系如何定位？
- **结论**：
  1. MVP 单租户 `platform_admin` 等价于**一套部署 = 一个项目空间**，界面无租户切换，MVP 不启用租户隔离注入；
  2. 租户是**权限/管理边界**（对应单一运维团队/组织），业务是**监控对象的分组维度**（对应 CMDB Business / 项目条线），两者解耦；
  3. 网域是**网络/采集边界**，与租户、业务均正交。
- **依据**：M06 PRD §3.3 当前 Tenant ↔ Business 1:1 映射与用户「单一团队、多业务」场景冲突；用户已确认 MVP 不需要多团队隔离。
- **影响范围**：M06 PRD §3.3 / §10 术语映射；M07 资源模型、导入校验；M04 CMDB 业务同步映射。

#### 决策 13：业务登记入口归 M07，`business_domain` MVP 必填

- **问题**：业务登记入口应放在哪里？MVP 是否强制资源填写业务字段？
- **结论**：
  1. 业务是资源的分组维度，资源 Owner 是 M07，因此业务登记入口归 M07；
  2. MVP **不提供**业务分组维护页面；业务字典（业务编码 `business_domain` + `display_name` + 状态）由配置文件在交付时预置，新增业务走配置变更（2026-08-19 二轮确认：避免用户频繁改名引发配置下发，见决策 17）；维护入口推迟到 v0.2+ 再评估；
  3. MVP 所有资源类型的 Excel 导入模板和手工录入表单中，`business_domain` 字段**必填**；导入校验发现未登记业务时报错并引导到 M07 业务分组登记（与网域报错引导对称）。
- **依据**：M07 PRD §3.1（资源管理职责）、§5.8 / §5.12 / §5.15（`business_domain → biz` 标签映射已存在）、§5.16（Excel 导入校验）。
- **影响范围**：M07 PRD §3.1 核心功能总表、§5.x 数据模型与标签模板、§5.16 Excel 规范、§6 接口、§11 前端交互契约。

#### 决策 14：`business_domain` / `biz` 是受控字典，治理规则与 `zone_type` 同构

- **问题**：业务字段由用户填写，如何保证受控？
- **结论**：
  1. `business_domain` 会经 LabelTemplate 映射为 `biz` 指标标签（M07 5.15 / M09 3.3），必须受控，不能自由文本；
  2. 业务字典治理规则：条目 = `business_domain`（进标签，创建后不可变）+ `display_name`（可改）+ `description`；被资源引用的条目只能停用，不能删除；后端校验资源上的 `business_domain ∈ 启用字典项`；
  3. MVP 字典由配置文件/初始化 SQL 预置 + 只读接口承载；v0.4+ 由 M04 同步 CMDB Business 后自动维护。
- **依据**：M07 PRD §5.15（`biz` 标签注入）、M06 决策 10（`zone_type` 受控字典治理规则已对齐）。
- **影响范围**：M07 PRD §5.16.2 导入校验、新增业务字典接口；M09 标签注入链路无需改动，但需明确引用 M07 LabelTemplate。

#### 决策 15：网域与业务正交，多业务共用网域无需特殊处理

- **问题**：用户先有业务需求，发现业务跨网域，再登记网域；多业务共用 1 个网域如何处理？
- **结论**：
  1. 网域由网络环境决定（登记制），不是为某个业务创建的；业务需求只是触发登记网域的时机；
  2. 每个资源单一归属：1 个网域 + 1 个业务；
  3. 多业务共用 1 个网域、1 个业务跨多网域均为正常状态，无需特殊处理，查询通过 `biz` + `network_domain` 标签组合过滤；
  4. 业务与网域不得互相编码进命名（网域名不带业务、业务名不带网域）。
- **依据**：M06 PRD §3.2（网域是逻辑操作上下文与采集边界）、M07 PRD §5.16.1（网域列只引用 M06 已登记网域）。
- **影响范围**：M06 PRD 网域登记入口文案（引导创建边缘域）；M07 资源详情/列表展示；M09 配置生成逻辑（保持网域与业务独立注入）。

#### 决策 16：对接蓝鲸 CMDB 时业务同步映射方式

- **问题**：后续对接蓝鲸 CMDB，业务字段如何映射？
- **结论**：
  1. 不再把 Tenant 1:1 映射到 BlueKing Business；CMDB Business 映射为 M07 业务分组字典条目；
  2. 资源字段 `business_domain` 取 CMDB 的 `bk_biz_id`（或稳定业务路径编码），`display_name` 取 `bk_biz_name`；
  3. M07 业务字典条目预留 `cmdb_business_id` 可空字段，用于手工登记条目与 CMDB 业务匹配合并；
  4. CMDB 同步失败时沿用旧业务字典，不影响配置生成。
- **依据**：M04 PRD §3 / §4.1（原 Tenant → Business 映射与当前结论 12 冲突，需调整）。
- **影响范围**：M04 PRD §3 核心功能、§4.1 Provider 字段映射、§5 同步策略；M06 PRD §3.3 映射表；M07 PRD §5.x 业务字段说明。

#### 决策 17：`biz` 标签只承载不可变 code，业务名变更零配置影响

- **问题**：业务信息（尤其业务名）用户侧可能频繁变化，若 `biz` 标签随之变化会导致监控配置重新生成与下发，是否符合最佳实践？
- **结论**：
  1. **标签只注入不可变 `business_domain`（code），永不注入 `display_name`**——业务改名只改字典 `display_name`，不进标签、不进配置，UI 展示时 join 字典；业务名任意变化对监控配置**零影响**；
  2. 业务归属作为 target label 注入 `static_configs[].labels` 符合 Prometheus 最佳实践（target labels 本就用于稳定、低基数的归属元数据）；不合规的做法是把可变值（如业务名）当标签，本设计不这么做；
  3. 真正触发配置变化的只有一种业务操作：**资源换业务归属**（targets 中该 target 的 labels 变化）。这属于真实拓扑变化、本来就该变；且按 M09 §3.5.1 reload 策略，targets 变化只原子重写 `targets/*.json`，file_sd 自动感知，**不触发采集器 reload**，`agent_pull` 通道下次心跳拉包即可，代价极低、频率低（业务重组级别）；
  4. v0.2+ 若开放业务分组维护页面，红线：**页面只允许编辑 `display_name` / `description` / 状态，`business_domain` 创建后永不可改，停用不删除；查询/告警/聚合一律用 code**；
  5. 业务合并/拆分（真实身份变化）导致的批量换归属是例外场景，需要迁移资源归属，v0.2+ 再评估「合并到」映射辅助。
- **依据**：用户担心 MVP 阶段用户频繁改业务名引发配置重下发（2026-08-19 二轮讨论）；M09 PRD §3.5.1（targets 变化不触发 reload）；M06 决策 10 / 决策 14（code/display 分离、code 不可变）。
- **影响范围**：M07 PRD §5.15（`biz` 标签取值口径补充"值为不可变编码"）；M07 业务字典维护入口（v0.2+）编辑约束；M09 无需改动。

#### 决策 18：租户-网域-业务三维正交（架构原则级）

- **问题**：MVP 单租户场景下，租户、网域、业务三者应如何定位才能既满足当前 simplicity 又为未来多租户/多客户层扩展留空间？
- **结论**：
  1. **租户（Tenant）** 是**治理与权限作用域**单位，回答"谁能看/改"；在 MVP 中对应单一运维团队/组织/部门，等价于一个项目空间。
  2. **网域（NetworkDomain）** 是**物理采集拓扑**单位，回答"采得到吗"；是配置生成、采集器部署、配置下发的唯一结构化维度。
  3. **业务（`business_domain` / `biz`）** 是**监控对象分组**单位，回答"归哪条业务线"；与 CMDB Business 对应，进入 target 级标签。
  4. 三者**正交**：1 租户可授权使用 N 网域、N 业务；1 网域可承载 N 租户、N 业务；1 业务可跨 N 网域、N 租户。
  5. 此原则为**架构原则级**，已写入 `docs/02-product-requirements/00_Global_Architecture.md §1.1` 与 `docs/02-product-requirements/03_Functional_Architecture.md §1.6`，作为后续所有模块设计的判定标准。
- **依据**：用户反复确认"业务多个、组织/部门单一、网域固定"（2026-08-19 多轮讨论）；`00_Global_Architecture.md` 与 `03_Functional_Architecture.md` 已同步更新。
- **影响范围**：M06 PRD §3.2/§3.3；M07 PRD §3.1/§5.x；M09 PRD §3.3/§5；M04 PRD §3/§4.1；全局架构文档。

#### 决策 19：租户不进入采集拓扑，`tenant` 标签走 target 级

- **问题**：`tenant_id` 应放在 M09 `external_labels`（全局标签）还是通过 M07 LabelTemplate 注入为 target 级标签？
- **结论**：
  1. **租户不拥有网域，也不进入采集拓扑**。M09 `external_labels` 中移除 `tenant_id`，`external_labels` 只保留部署级、物理维度的不可变元数据（如 `network_domain_id`、`zone_type`、`replica`）。
  2. 未来若多租户需要在指标上体现租户归属，由 M07 LabelTemplate 将资源字段 `tenant_id` 映射为 target 级 `tenant` 标签；MVP 单租户下此映射可选、不强制注入。
  3. 查询时的租户隔离优先在 **API Gateway / 查询代理层**通过 PromQL 注入 `tenant=~"..."` 实现，而不是依赖采集侧全局标签。
  4. 该原则确保"租户或业务部门调整"不会触发采集配置重新生成与下发，符合"组织变更零配置影响"目标。
- **依据**：决策 18 正交原则；`00_Global_Architecture.md §1.1` 具体约束第 3 条；M09 PRD §3.3.1 当前写入 `tenant_id` 需修正。
- **影响范围**：M09 PRD §3.3.1（`external_labels` 列表移除 `tenant_id`）；M07 PRD §5.12（默认标签模板补充 `tenant_id → tenant` 可选映射说明）；M06 PRD §3.2（租户-网域关系描述）。

#### 决策 20：多运维团队共享网域配置治理模型

- **问题**：部门 1/部门 2 各有独立运维团队，但物理环境共用 1 个网域，团队 2 修改配置是否会影响团队 1？应如何在权限与配置影响上做隔离？
- **结论**：
  1. **网域是物理边界，不是团队边界**。多个租户/运维团队可被授权使用同一个网域，这是正常且应被支持的形态。
  2. 配置影响按**三层矩阵**隔离，避免"改 A 团队配置把 B 团队配置冲掉"：

     | 隔离层 | 控制对象 | 团队 1 操作影响 | 团队 2 操作影响 | 实现归属 |
     |--------|----------|-----------------|-----------------|----------|
     | 写权限 | NetworkDomain 行政记录（名称/zone_type/category/状态） | 若团队 1 是 domain owner 或 platform_admin，可改；否则不可写 | 同理 | M06 权限模型 |
     | 配置内容 | 各租户在该网域下的 scrape targets、relabel、rules | 只生成/重写本租户命名空间下的配置片段 | 只生成/重写本租户命名空间下的配置片段 | M09 configgen（按 tenant + network_domain 分目录） |
     | 下发动作 | Edge Agent 拉取的配置包、Prometheus reload | 只下发本租户包，reload 只触本租户实例/本租户 file_sd | 同理 | M09 配置包构建与下发通道 |

  3. **MVP 单团队场景退化为默认共享**：只有一个 `platform_admin` 租户，所有配置都在该租户命名空间下，不存在跨团队覆盖问题。
  4. 未来多租户时，**同一网域下的多租户配置通过目录/包名命名空间隔离**；只有在"写权限层"获得网域行政 Owner 授权的用户才能修改网域本身的属性（如 zone_type、category、禁用）。
- **依据**：决策 18 正交原则；用户确认"部门 1 和部门 2 可能共用网域"场景（2026-08-19）；M06 PRD §3.1/§3.2、M09 PRD §3.5。
- **影响范围**：M06 PRD §3.1/§3.2/§5.1（租户-网域授权与 Owner 模型）；M09 PRD §5（配置生成目录结构与下发命名空间）；M07 PRD §5.1（资源 `tenant_id` 字段）。

#### 决策 21：业务字段命名统一为 `biz_code` + `biz_name`

- **问题**：`business_domain` 命名是否保留，还是统一为 `biz_code` + `biz_name`？
- **结论**：
  1. 资源字段与字典主键统一命名为 `biz_code`（不可变编码，进 `biz` 标签）；字典展示名字段为 `biz_name`（可改，不进标签）；
  2. 指标标签名保持 `biz` 不变；
  3. 理由：`business_domain` 中的 "domain" 与 `network_domain` 语义撞车、易误读；`biz_code` / `biz_name` 与决策 10 `zone_type`（code + display_name）字典风格一致，且与标签名 `biz` 直接对应；
  4. 资源只存 `biz_code`，`biz_name` 由字典 join 展示（与 `network_domain_id` 模式一致）；
  5. MVP 无存量数据，改名零迁移成本。
- **依据**：用户确认改名方向（2026-08-19 三轮）；决策 10 / 14 / 17。
- **影响范围**：M07 PRD §5.1/5.2/5.8/5.12/5.15/5.16/§6/§11 全部 `business_domain` 更名；M06 PRD §10 术语表词条更名；M04 PRD §4.1 字段映射更名。

#### 决策 22：CMDB 业务删除时本地字典停用、资源保留历史值

- **问题**：M04 v0.4+ 同步时，若 CMDB 业务被删除，本地业务字典条目如何处理？资源上的 `biz_code` 是否保留？
- **结论**（用户拍板 2026-08-19 三轮）：
  1. 本地业务字典条目**标记停用（disabled），不删除**；
  2. 资源上的 `biz_code` **保留历史值**，不清空、不迁移，保证监控数据可回溯；
  3. 停用条目不允许被新资源/编辑操作选用；存量资源继续携带该 code，配置生成不受影响（标签值只是字符串）；
  4. UI 对停用业务加「已停用」标识，查询/告警仍可按历史 `biz` 值过滤；
  5. 若 CMDB 同 `bk_biz_id` 业务重建，按 `cmdb_business_id` 匹配复用原条目并重新启用，不新建条目，避免 code 漂移。
- **依据**：用户确认（2026-08-19 三轮）：「显示停用，保留历史值，方便监控平台后续回溯记录」。
- **影响范围**：M04 PRD §5 同步策略（删除/停用/重建语义）；M07 PRD §5.16.2 校验规则（停用不可新选）与 §11（停用标识）。

#### 决策 30：网域「冻结」语义跨模块传导闭环

  3. **M06 §9 验收**：补一条联动用例——禁用网域后，M01 建 Job 选不到该域、M09 变更单拒绝新建。

#### 决策 31：采集认证/TLS 最小集 + 中等项处置（H1 / M1 / M2 / M3）

- **问题（H1，需拍板）**：ScrapeJob 模型仅 `scheme`(http/https)，无认证/TLS 能力；政务/AIDC 隔离网 https+自签、受保护 exporter 为常态，缺失即交付现场直接采集失败，属致命而非体验问题。
- **结论（H1 拍板：MVP 加最小集；全部可选、默认无认证）**：
  1. ScrapeJob 新增：`auth_type`(none/basic/bearer，默认 none) + 对应 `username`/`password` 或 `token`；`tls_skip_verify`(bool，自签证书场景)；`ca_file`(可选 CA 路径)；

  3. 全部可选字段默认不启用，不影响既有裸 http 场景。
- **结论（M1~M3 中等项处置）**：
  1. **M1**：不新增工作——`is_monitored` badge（M01 维护、M07 只读展示）即「未纳入任何 Job」识别入口（P0 已有）；M07 资源列表支持按「未监控」过滤即可；PRD 记录为已知裁剪，完整覆盖率视图归 v0.2+；
  2. **M2**：MVP 即回写 `change_status=deployed`（M09 ConfigDeployment 已有 success 记录，回写成本低），消除「已生效 vs 无变更」歧义；
  3. **M3**：删除 M09「未指定网域资源自动归 default」兜底 clause，以 M07「network_domain_id 必填」为准，M09 不做隐式归集（避免掩盖导入漏填）。
- **依据**：M01 §5.4 ScrapeJob 模型、M09 §3.3 scrape_configs 生成、M07 §5.16 导入校验、M01 Change Log v3.24（规则文件挂载）。
- **影响范围**：M01 §5.4 数据模型 + §6 接口 + §11 表单折叠区；M09 configgen 透传 + blackbox；M07 资源列表「未监控」筛选；M09 §5 目录组织。

  2. **决策 8 第 2/3 条修订**：MVP 从「无任何认证、依赖部署网络隔离」改为「**轻量认证（用户名 + 密码登录 + 会话），无授权隔离**」——登录要真实生效，最小实现必须包含认证中间件（拒绝匿名请求），否则登录形同虚设；但不做角色 / 权限点 / 租户数据隔离，所有登录用户在单租户 `platform_admin` 下等价。「MVP 无鉴权是已知风险」的声明收窄为「MVP 无授权隔离是已知风险」；
  3. **租户管理 MVP 边界**：仅管理 `platform_admin` 一个租户；**不开放新建租户**；**唯一租户禁止禁用**；页面提供查看 / 编辑（展示名、`multi_site_enabled` 等行政字段）；
  4. **用户管理 MVP 边界**：`platform_admin` 租户内用户 CRUD + 修改密码；不引入角色体系（v1.0+）；
  5. **流程定位**：本需求走 Track B/B+ 轻量规格直派开发（prototype-designer 产出轻量 PRD 增量、用户书面确认后标 `dev-ready`），验收后回填 PRD 为 as-built 并补登 ready。
- **依据**：用户 2026-08-28 需求沟通原话（MVP 单租户但要有租户管理功能、用户管理也要有、轻量密码登录、新建租户不开放、不允许禁用唯一租户）；双轨制设计。
- **影响范围**：
  - M06 PRD：§1「MVP 无鉴权声明（决策 8）」改写为「轻量认证、无授权隔离」、§5 新增 User 数据模型、§6.3 用户与权限落地 MVP 子集、§9 验收补登录/租户/用户条目——下轮 Track B 轻量规格迭代落版（版本 +1，含 Change Log）；

- **触发**：用户（chenrt）反馈 M06 网域概念对普通用户不友好——①大多数用户不理解「边缘采集节点（Edge Sync Agent）」概念；②网域需做成通用化概念，覆盖**单域多集群**与**多域**两种形态，对标**网络可达性区域**；③M06 网域管理页缺乏指引（用户不清楚管理域是什么、无缘无故注册边缘域、注册完不清楚网域的作用、跳 M09 纯属机械化操作、不知道后续如何在不同网域安装采集节点）；④M07 资源管理按 CI 类型，需评估 K8s 集群是否单列类型管理；⑤`zone_type`（网络区域类型）不像通用概念，需讲清政务云/公有云两种情形下代表的含义。**本轮全为文档落档（PRD + 决策），不改代码、不动数据模型。**

#### 决策 73：网域用户侧定义与判断规则（网域 = 网络可达性区域）

- **一句话定义（用户语言，进 M06 页首概念卡与新建表单）**：网域 = 一组**网络互通**的机器的集合；平台中心**能不能直接访问**机器，决定要不要建网域。
- **判断规则（二选一，无需理解新概念）**：中心能直接访问 → 不用建网域（放 `default` 中心直连区）；中心访问不到（专网 / 隔离 DMZ / 另一个 VPC / K8s overlay 集群）→ 建一个网域，并在该网络内挑一台常开机器安装**采集节点**，由它把数据带回中心。
- **通用化覆盖**：该定义天然覆盖两种形态——**多域** = 多个可达性区域（每域一个/多个采集节点）；**单域多集群** = 一个可达性区域内放多个采集节点（分片 / HA / 多探测点），属**域内部署细节、不产生新概念**（与 M09 PRD「同一网域内多采集节点属 v0.4+ 演化」口径一致）。
- **网域存在的意义（回答「注册完有什么用」）**：网域告诉平台两件事——①这批机器由**哪个采集节点**去采；②采回的数据打上**来源区域标签**（`network_domain`），便于按区域筛选、定位故障与权限隔离。**登记网域本身不采集任何数据**——它只是「划片」，数据从采集节点上线那一刻才开始流。
- **依据**：PRD §3.2 既有「划域指导原则」（可达性同质性 + 故障自治单元）与决策 52（接入可见、消费隐藏）在技术层已正确，本决策将其**翻译为用户语言并前移到界面**；概念本身不变。

#### 决策 74：术语降噪——用户侧叫法与「接入方式」呈现（修订决策 9 的 UI 展示名口径）

- **用户侧叫法表**（数据模型枚举 `management` / `edge` 与后端术语不变，仅 UI 展示名与用户文案调整）：

  | 当前用户可见术语 | 用户困惑 | 决策后用户侧叫法 | 理由 |
  |---|---|---|---|
  | 管理域（`management`） | 「管理域是什么？」 | **中心直连区** | 它就是「中心自己所在、能直接采到机器的区域」，`default` 是其唯一实例 |
  | 边缘域（`edge`） | 「无缘无故注册一个边缘域」 | **隔离区（采集节点接入）** | 名字本身回答「为什么建它」：中心够不到 |
  | Edge Sync Agent / 边缘采集节点 | 不理解 | **采集节点**（Edge Sync Agent 仅保留在技术名 / 安装命令 / 文档） | M09 §3.2 已把用户心智单元定为「采集节点（在哪台机器上装了什么）」，推广到 M06/M09 全部用户文案 |

- **`domain_type` 呈现方式**：`domain_type` 本质是**接入方式**的实现分类泄漏到 UI；M09 已按网域固定通道（`default`=local、其余=agent_pull）。用户侧只呈现**只读字段「接入方式：中心直连 / 采集节点接入」**，自动推导、不可选择——用户只需回答「中心能不能直连」，类型自行得出。**模型枚举不变**（`management` / `edge` 保留，M06 行政分类语义不变）。
- **与决策 9 的关系**：决策 9 统一的后端术语「管理域 / 边缘域」**保留**（模型与文档技术层不变），本决策仅修订 **UI 展示名与用户文案**口径。

#### 决策 75：M06 网域管理页引导设计四件套

1. **页首概念卡 + 空态改写（MVP）**：页首放概念卡——三行拓扑示意（中心 ─直连→ default 区机器；中心 ─✕→ 隔离区 ← 采集节点回传）+ 决策 73 的一句话定义与二选一判断规则；空态从「暂无网域」改为提问式引导：「你的所有机器都能被平台中心直接访问吗？能 → 无需新建；不能 → 登记一个网域」。
2. **新建表单前置判断问题（MVP）**：表单第一问「这个区域的机器，平台中心能直接访问吗？」选「能」→ 提示通常无需建域（或登记为中心直连区）；选「不能」→ 展开行政登记字段，并在表单底部预告后续三步（纳管取凭据 → 装采集节点 → 节点上线后配采集）。把「无缘无故建域」挡在源头。
3. **列表「接入进度」四态列（v0.2，替代现「监控纳管」二态列）**：网域生命周期对用户为四步——①已登记（M06）→ ②已纳管、拿到凭据（M09）→ ③采集节点已上线（Agent 心跳）→ ④已出数据（该域有生效 targets）；每行展示当前所在步骤，**行内主操作 = 下一步动作**（未纳管 →「去纳管」；已纳管未上线 →「查看安装指引」深链 M09；已上线 →「去配置采集 Job」跳 M01 预选该网域）。数据源均已存在（M09 纳管状态 / EdgeAgent 心跳 / M09 生效配置），M06 列表接口做跨模块聚合（v0.2 落地接口扩展）。
4. **登记成功行动卡（MVP）**：创建成功由 toast「请前往 Module_09 完成监控纳管」升级为**结果弹窗**：「网域已登记，还需 3 步产出数据：① 去纳管获取接入凭据 → ② 在该网域一台常开机器上安装采集节点 → ③ 节点上线后即可为该网域资源配置采集」，附直达按钮。解决「跳 M09 机械化」。
- **安装指引增强（M09 侧配套）**：安装指引保持在 M09 页面顶部常驻；每个已纳管网域提供**一键复制安装命令**（`NETWORK_DOMAIN_ID` / `TOKEN` 预填的环境变量块 + systemd 步骤）；M06 列表对「已纳管未上线」网域显示「查看安装指引」深链。用户无需理解 Agent 概念，只需「复制命令 → 到目标机器粘贴执行」。

#### 决策 76：zone_type 语义澄清（纯分类标签 + 两种部署形态含义）

- **一句话语义（进表单 extra 与字典说明）**：`zone_type` 只是给网域贴的**分类标签**，对应「这个网域在你们的网络规划里叫什么分区」；用于列表筛选与标识，**不影响采集、不下发、可留空**。
- **两种部署形态下的含义**（部署级字典预置时按此写 `description`，UI 选项带说明）：

  | 部署形态 | zone_type 代表 | 预置示例 | 含义 |
  |---|---|---|---|
  | 政务云 | 政务网络规划的**安全分区**（一组互通策略相同、与其他区隔离的网段） | `internet` 互联网区 / `extranet` 政务外网区 / `private-line` 专线区 / `dmz` | 这个网域的机器处在政务网哪个安全区 |
  | 公有云 | 云厂商 **region（地域）**（同地域内网互通，跨地域默认不通） | `cn-hangzhou` / `cn-beijing`… | 这个网域对应哪个地域的 VPC；**AZ 不进 zone_type**（可用性是地域内部维度，非监控隔离边界，维持 PRD 既有口径） |

- **减负配套**：表单中保持**可选、可留空**（现状不变），文案补「不确定可留空，仅用于分类筛选」；UI 展示名由「网络区域类型」改为「**网络分区（可选）**」。
- **禁止方向**：不把 `zone_type` 做成死枚举、不赋予行为语义（如按 zone_type 决定通道 / 标签规则）——一旦影响行为，部署级字典灵活性即失效；现有定位（纯分类属性 + 进 `external_labels` 供筛选）维持不变。
- **被决策 78 修订（2026-09-26）**：`zone_type` 由「可选、可留空」改为 **网域登记必填**；`zone` 由「不下发、进 `external_labels` 供筛选」改为 **target 级 system 层注入 `zone` label**（非 `external_labels`，决策 68-§2.5）；纯分类标签 / 两种部署形态 / AZ 不进 zone_type 仍成立；字典补充公有云 region 取值（上海/北京…）。详见 M06 决策 78 + M07 决策 103。

#### 决策 77：K8s 集群不设第六资源类型（四归属）

- **结论**：M07 **不新增**「K8s 集群」资源类型（第六类）。理由：①五大类按**采集形态**分类（用什么 exporter / 协议采），K8s 集群是**部署形态**而非采集形态——集群内要采的对象（节点 node exporter / kube-state-metrics / 业务 Pod）仍落回现有五类；②「K8s 集群」诉求由四个现有对象分头完整承接：

  | 用户想表达的 | 归属 | 现状 |
  |---|---|---|
  | 集群是一个网络边界（Pod 网段外部不可达） | **NetworkDomain**（overlay CNI 独立建域，`zone_type` 字典届时加 `k8s`） | 划域原则已决策（PRD §3.2），M09 机制零改动复用 |
  | 集群是资源的分组 / 筛选维度 | **Resource.cluster 字段 → `cluster` 标签** | 已有字段与标签映射（M07 §5.2 / §5.15） |
  | 集群是动态实例的发现源（kubeconfig / APIServer 凭据） | **M04 服务发现源**（KubernetesProvider） | 已预留（M07 §6.3 / M04），v0.3+ 落地 |
  | 集群本身要监控健康（apiserver / etcd / kube-state-metrics） | **generic_target** + M01 `monitor_type=k8s` 映射 | 现有机制可表达 |

- **如客户强诉求「在资源管理里看到集群清单」**：给的是**集群视图**（按 `cluster` 字段分组 / 筛选的展示层，或后续轻量 Cluster 字典被 Resource 引用）——视图问题不是模型问题，MVP 不做。

## 补充对齐：2026-09-14（接入进度四态 = 聚合视图，M09 保持原子状态，决策 78）

- **背景**：决策 75 落版后出现跨模块设计问题——M06 网域列表新增「接入进度」四态列，而 M09 网域纳管页已有「纳管状态 + 运行状态」列，两侧是否对齐为同一四态存在分歧；用户动线主轴已定在 M06（决策 73~77），M09 承接纳管动作与采集节点安装指引。
- **选项**：A 双侧对齐四态（M09 纳管页同样展示四态）；**B M09 保持原子状态 + 映射注记（推荐）**；C M09 也压缩为单一进度列。
- **结论（方案 B，chenrt 2026-09-14 确认）**：
  1. **四态是聚合视图而非新状态机**：已登记 = M06 行政状态；已纳管 = M09 `registration_status`；采集节点已上线 = M09 运行状态 online（Agent 心跳）；已出数据 = M01 生效配置聚合。
  2. **数据流向单向**：M06 列表接口 → 聚合 M09 / M01 数据；M09 不反向聚合「已出数据」（数据源在 M01，反向聚合属职责倒置且模糊 M09 边界）。
  3. **M09 保持「纳管状态 + 运行状态（含最后心跳）」原子列**：运维语义需要心跳时间细节，压缩为进度列会丢失诊断信息、并与 M09 §3.8「采集节点状态页 = 节点平铺表」的既有取舍冲突。

## 前端设计优化：2026-09-14 第三轮（引导条扁平化 + 表单改抽屉 + 判断口径澄清 + 列表列数治理，决策 80）

## 决策 82：网域生命周期闭环——回收路径修正 + 禁用/纳管联动具象化（2026-09-15）

- **日期**：2026-09-15
- **状态**：已采纳（PRD 双模块落版：M06 v2.14→v2.15、M09 v1.71→v1.72；原型本轮不动）
- **触发**：chenrt 走查 M06 网域管理后提出两个深层问题——① **已纳管网域没有「删除 / 回收」路径**：删除入口在已纳管场景恒不可用（硬约束含「无已纳管 EdgeAgent」），用户预期「网域随业务下线应可回收」，现状只能「禁用」（行政冻结），而禁用不影响存量采集，不构成真·回收；② **M06「启用 / 禁用」与 M09「纳管」语义割裂**：禁用是平台侧行政动作，采集节点安装却是线下动作，禁用后在 M09 仍看到「已纳管 + Agent 在线」，两个模块各说各话。
- **证据核对（当前 PRD 原文）**：
  1. M06 §6.2 `DELETE /network-domains/:id`：「**仅限空网域**：前置校验无 M07 资源引用 且 无已纳管 EdgeAgent，否则拒绝并引导走『禁用』」；
  2. M06 §6.2 `PATCH .../status`：「禁用 = 冻结……存量资源与采集配置不受影响、继续采集（**是否停止采集由 M09 退纳管决定**，不归 M06 禁用管）」——**PRD 已许诺「M09 退纳管」这一动作，但 M09 侧从未定义该动作**（决策 62 仅拍板 MVP 不联动、口径① 归 v0.2，未落地动作定义）；
  3. M09 §3.1 功能表「网域删除（由 M06 承责）」行：本页不提供删除、仅监控纳管状态切换；
  4. M09 §1 MVP 注记（决策 62）：M06 行政禁用网域（`Status=disabled`）**不联动** M09 纳管状态（`IsMonitored` 独立维护），「禁用是否联动取消纳管 / 冻结 Token」属 v0.2 多网域版本决策。
- **选项（回收路径）**：A 修正删除约束（「已纳管」由硬拒绝改为级联清退，**推荐**）／B 禁用弹窗加「同时停止采集」复选联动／C 维持现状 + M09 补「退纳管」动作（退纳管后网域变空再删）。
- **结论（chenrt 2026-09-15 确认方案 A + 短期 UI 补强 + 中期退纳管）**：
  1. **82-1 删除约束修正（MVP）**——`DELETE /network-domains/:id` 的硬拒绝条件**收敛为「存在 M07 资源引用」单一条件**（资源是有主数据，不得因删网域连带丢失）；原「无已纳管 EdgeAgent」条件从**硬拒绝改为级联清退**：删除二次确认弹窗展示级联影响清单（该网域已纳管 → N 个采集节点将断连、凭据将废止），确认后 M06 软删网域 + M09 侧级联清退纳管状态（**废止 Token / 停止配置下发 / `EdgeAgent` 记录标记 retired**）。采集节点侧**不要求线下卸载**——Token 废止后 Agent 心跳鉴权失败自然转离线，指引说明即可。`management`（`default`）域禁止删除不变。
  2. **82-2 禁用确认弹窗补强提示（MVP）**——已纳管且存在在线 Agent 的网域，禁用二次确认弹窗在原有「影响范围」（M07 资源数 / 已纳管 EdgeAgent 数）之外追加固定提示：「禁用为**行政冻结**：新资源登记与新纳管将被阻止，但**已接入的采集节点不会自动停止采集**。如需停止采集并回收网域，请使用『删除』（级联清退）；如需保留网域仅停止采集，v0.2+ 提供『退纳管』。」——把「割裂」从隐性设计变为显式告知。
  3. **82-3 退纳管动作定义（v0.2+，决策 62 口径① 具象化）**——M09 网域纳管页新增「退纳管」动作：**废止 Token → 停止配置下发 → `registration_status` 归位 `created`（未纳管，保留历史记录）→ `EdgeAgent` 心跳鉴权失败转离线**。与 M06 禁用**正交**：禁用管「能不能新建」（准入），退纳管管「现有采集停不停」（运行）。v0.2 落地时随多域场景评审（含 Token 冻结与恢复流程，沿用决策 62）。
  4. **语义边界定版（写入 PRD 用语）**——M06 三个动作一次性说清：**禁用 = 行政冻结**（不准新入、不强制停旧）／**删除 = 退场回收**（级联清退、从平台移除）／**退纳管 = 停止监控**（保留网域、清空纳管，v0.2+），三者覆盖「不再使用某网域」的三种强度。

## 决策 83：网络分区（zone_type）字典命名口径统一 + 分区唯一权威（2026-09-25）

- **日期**：2026-09-25
- **状态**：已采纳（PRD 落版：M06 v2.15→v2.16；属契约级增量，**原型无需同步**）
- **触发**：M07 主机「云标识与网络分区」设计提案 `docs/05-execution-records/module-07/design-proposals/host-cloud-identity-and-zone-convergence.md`（v0.6）评审通过后回填 PRD——同一「政务外网」概念在系统内存在**三种叫法**（字典 code 注释写「外网区」、字典 `display_name` 写「政务外网区」、Excel 模板写「政务网区」），且「云内分区」被网域 `zone_type` 与主机 `zone_env` **重复建模两次**（值域互不相同）。
- **结论（chenrt 2026-09-25 确认，收敛命名 + 明确权威归属）**：
  1. **命名口径统一（1 个 code + 1 个 display_name）**：`internet` = **互联网区**、`extranet` = **政务外网区**；三处旧叫法一律归口——字典 code 注释「外网区」、字典 `display_name`「政务外网区」、Excel 模板「政务网区」→ 统一为**政务外网区**（PRD 侧只声明口径，代码 / seed / 模板侧收敛由开发侧后续执行）。
  2. **分区唯一权威归网域 `zone_type`**：分区是**网域级属性**（网络可达性/隔离边界属「一个网域整体」），下游（M07 资源 / CMDB 同步）**只引用不冗余**——M07 主机**不新增**独立分区字段、不设表单项；主机详情如需展示分区，经 `network_domain_id` 关联解析网域 `zone_type` 的 `display_name`，标注「继承所属网域」，**只读派生**（跨模块见 Module_07 §5.6）。
  3. **`Host.zone_env` 降级为兼容导入列**：承接历史 Excel / CMDB 数据，不进新增 UI、不进标签、不作权威值；枚举与 `zone_type` 字典同源，映射 `INT → internet`、`GOV → extranet`；存量非空值保留、不再读取为权威。
  4. **`zone` 不进 Prometheus label**：分区仅用于分类筛选与定位；本期不输出为 label。备忘：将来若确有 `group_by (zone)` 诉求，更合适的位置是网域级 `global.external_labels`（项目已有通过该机制注入 `network_domain_id` 的先例），而非回填主机映射。
  5. **既有语义不变（决策 76 维持）**：`zone_type` 仍是**纯分类标签**——**不影响采集、不下发、可留空**，不开放自由文本，不做死枚举、不赋予行为语义（如按 `zone_type` 决定通道 / 标签规则）。本决策**只收敛命名与权威归属**，不改行为。
- **影响范围 / PRD 落点（Module_06 PRD v2.15→v2.16）**：§3.2「唯一入口原则」补分区同样遵循单一事实来源；§5.2 `zone_type` 行补命名口径 / 分区唯一权威 / `zone` 不进 label；§6.2 `GET /api/v2/platform/zone-types` 补返回项口径（`code` + `display_name`，仅启用项）；§9.2 新增 1 条 P0 技术验收（命名唯一 + 资源侧无独立分区字段）；§10 术语映射 `zone_type` 行对齐；Change Log 新增 v2.16 + 轮转 v2.13 迁完整历史。
- **跨模块影响**：**Module_07 §5.6**（主机资源字段 / 物理列备注——主机无独立分区字段、详情只读派生，`Host.zone_env` 降级说明）；**Module_09 配置产物**（不注入 `zone` label；`zone` 不进主机默认标签模板）；**`assets/templates/excel/host_template.md`**（`zone_env` 兼容列 + 命名统一为「政务外网区」）；字典 code / seed 命名收敛由开发侧派生实施任务执行。
