## 1. 背景与讨论过程

chenrt 要求把 v0.2 版本涉及的 PRD 需求确定下来。讨论分四轮收敛：

1. **第一轮**：基于 `02_Product_Roadmap.md` v2.1 §1.5 功能-版本矩阵整理 v0.2 全量功能点，并做合理性评估。评估结论：原 v0.2 横跨 7 个模块、引入 4 个新组件，范围偏大；建议拆批次（批次 A = 边云主链路，批次 B = M10 接入 + M01/M07 增强）。
2. **第二轮**：chenrt 确认 M03/M10 外联需求优先级低可后移；指出 M07 业务目录 MVP 已交付（矩阵表述过时）。
3. **第三轮**：chenrt 纠正——M01/M09 是 v0.2 核心，**网域扇出（决策 54）与 filter 自动纳入（决策 53）必须留 v0.2**；克隆 Job 因扇出存在而失去必要；实例级端口覆盖需要；服务发现先做容器实例场景。
4. **第四轮**：结合真实业务拓扑（公有云+私有云混布、多 VPC、vmagent 部署在每朵云边缘节点、经 VPC 对等访问业务机器、容器用 cAdvisor 监控、容器网段与虚机网段不重复）逐项澄清技术疑问后定版。

## 2. 真实业务拓扑（决策的事实前提）

- 两朵云（公有云 + 私有云）混布，虚拟机部署，多 VPC；**容器网段与虚机网段不重复**（规划约束）。
- vmagent 装在每朵云的**边缘节点**（有外网能力），经 **VPC 对等连接**访问其他 VPC 的业务虚机。
- 容器监控现状：**cAdvisor**；容器非 host network 模式；EIP 绑宿主机供用户访问容器应用（即业务端口已发布或经宿主机反代）。
- 同一台主机跑多个同类 exporter 实例（端口各不相同）的场景**多见**。
- 「CMDB 归资产团队管、采集团队只有 Job 配置权限」的组织割裂场景**不存在**。

| D2 | filter（决策 53）、Job 多网域扇出（决策 54） | **保留 v0.2** | M09 是 v0.2 核心，必须自动按 Job 涉及网域拆分生成各域配置；filter 自动纳入 targets 是核心诉求 |

| D4 | 草稿/批量提交生效、业务健康度看板 | **后移 v0.3** | 非主链路；`draft_status` 字段 MVP 已落库默认 `ready` 不变 |
| D5 | 实例级端口覆盖 | **v0.2 落地，Resource 级 `scrape_port`** | 同机多实例不同端口场景多见；端口跟随资源走，filter/SD 动态纳入时自带端口；**Job 级端口映射表明确不做**（与动态纳入模式冲突，且其服务的组织割裂场景不存在）。M09 生成期解析，优先级：`Resource.scrape_port` → 网域覆盖表 → 映射默认 → ExporterTemplate 默认 |
| D6 | 容器实例监控 | **v0.2 走 cAdvisor**：每虚机一个 exporter，作为普通采集 Job 绑定主机类资源 + filter 自动纳入新主机；容器发现由 cAdvisor 在宿主机内部完成，平台不感知容器个体 | docker_sd 发现的容器 bridge IP 从边缘节点（经 VPC 对等）不可达，直采路径不成立；cAdvisor 监听宿主机端口，可达性与现有 exporter 采集一致 |
| D7 | `docker_sd_configs` / `kubernetes_sd_configs` | **降级 v0.3+ 预留** | 仅当需要直采容器内应用 `/metrics`（已发布端口或 host network）时启用；已发布端口的容器应用 v0.2 即可按普通 application 资源登记采集 |
| D8 | 容器是否进 M07 CI | **不进** | ITIL/CMDB 方法论：CI 是相对稳定、有责任人、有生命周期的管理对象；容器易逝，登记即腐化。稳定资产进 CMDB、易逝实例走发现；将来 K8s 若登记，粒度是 Workload（Deployment/Service），Pod 永不进 CMDB |
| D9 | M07 IP 推导（决策 52/58）、M06 `ip_cidrs` | **后移 v0.3** | v0.2 导入/录入仍显式指定网域（与 MVP 一致），范围最干净 |
| D10 | M07 业务目录表述 | 矩阵 v0.2 单元格**删除与 MVP 重复的表述**（字典/归属/自定义标签 MVP 已交付）；残余「独立业务目录聚合视图（成员+健康度+采集覆盖）」归 v0.3 | 事实修正 |
| D11 | K8s 划域原则 | **overlay CNI（Calico/Flannel）：集群独立建网域**（zone_type 增 k8s），集群内 vmagent（Deployment/DaemonSet，worker 节点）作为该域边缘采集节点，M09 机制零改动复用；**VPC 原生 CNI：可并入所在 VM 网域**；不建议控制面节点承载采集负载 | 网域定义锚点 = 可达性同质性 + 故障自治单元，不是物理场所；overlay Pod 网段仅集群内可达，是标准的可达性孤岛 |
| D12 | 同网域多采集节点 | **保持 v0.4+ 演化不变** | K8s 场景用独立建域绕开，不需要提前；该能力意味着下发粒度细化到节点、Job 分片/绑定，是一笔独立工作量 |
| D13 | 网域作为用户动线 | **维持现设计不动** | 「接入可见、消费隐藏」（决策 52）已内置防滥用：消费侧（查询/看板/告警）不感知网域；接入侧网域是物理硬约束的一次性声明，且低频固定、由 IP 推导（v0.3）进一步压缩人工成本 |

## 4. 关键技术问答实录（备查）

**Q：docker_sd_configs 是 Prometheus 原生功能吗？用户编写流程？K8s 是否同流程？**
A：原生内置 SD 机制之一。手写流程：`docker_sd_configs`（host 指向 docker daemon socket/TCP，可配 filters）+ `relabel_configs` 对 `__meta_docker_*` 元标签做 keep/replace，业界惯例由容器 label 自我声明（`prometheus.io/scrape=true`、`prometheus.io/port`）。两个约束：采集器须与容器网络层可达（通常同宿主机）；docker.sock 权限等同 root，生产建议只读 socket 或 socket proxy。K8s 心智模型相同（`kubernetes_sd_configs` + `__meta_kubernetes_*` + pod annotation 惯例），差异仅在 API Server 凭证/RBAC 与 role 语义。**在 MetricCenter 中用户不写 YAML**：建 Job → 选「服务发现」→ 选 SD 类型 → 配筛选/映射 → M09 生成下发。

**Q：什么情况下容器要发布端口（-p）？**
A：只有一个触发条件——容器外的网络主体需要直达该容器端口：①用户/外部流量访问（EIP 场景已是如此）；②无 overlay 时的跨机容器互调；③监控直采容器内应用指标。

**Q：Job 级端口映射表适用什么场景？**
A：本质只服务静态 manual 模式——台账归别人管、采集团队只有 Job 权限、临时一次性目标。动态模式（filter/SD）下实例集合每周期变化，静态映射表立刻腐化；容器场景端口本来就从 SD 元数据来。该组织场景经确认不存在，故不做。

**Q：未来 K8s 在本拓扑下怎么实现？**
A：每个 K8s 集群当作一个特殊边缘网域，集群内嵌 vmagent（Agent Mode），`kubernetes_sd_configs` 在集群内消化 Pod IP 可达性，remote write 走同一条外联通道。若用 VPC 原生 CNI（如阿里云 Terway），Pod 分 VPC 子网 IP、经对等连接可路由，可省掉集群内 vmagent 并入 VM 网域——「容器网段不与虚机网段重复」的规划正是为此预留的红利。

**Q：`scrape_port` 由谁消费，用户动线改不改？**
A：M09 配置生成期解析，不是 M01 配 Job 时触发。动线改动仅一处：M07 资源登记/编辑/Excel 导入新增**可选**「采集端口」字段/列（留空走解析链）；M01 建 Job 动线不变，Job 实例列表可只读回显「生效端口」。

## 5. v0.2 最终功能清单

**主题**：多网域 Edge-Cloud 架构落地 + 租户-网域关联（预估 4 ~ 5 周）

- **Module_09（核心）**：网域生命周期与 Token；Edge Sync Agent（心跳、按域配置拉取、进程守护/reload）；vmagent / Prometheus Agent Mode 接入；中心 VictoriaMetrics Remote Write 汇聚 + Remote Write 参数；采集节点状态监控与诊断（在线/配置同步/WAL 积压/RTT/最近错误）；**Job 网域扇出生成（54）**；**filter 实时求值（53）**；**target 端口解析链（scrape_port 优先）**
- **Module_01（核心）**：网域级覆盖表 `CITypeExporterMappingOverride` + 参数继承/同步；filter 实例选择模式（53）；Job 多网域绑定（54）；**实例级端口覆盖（Resource.scrape_port）**；**cAdvisor 容器资源监控**（绑定主机 + filter 自动纳入）
- **Module_06**：租户数据模型、租户-网域关联、`multi_site_enabled` 启用；划域指导原则（文档）
- **Module_07**：资源可选 `scrape_port` 字段（登记/编辑/Excel 可选列）
- **Module_02**：租户/网域查询上下文注入
- **M04 / M05 / M08**：v0.2 无增量

**后移 v0.3**：M03（统一入口/Ingestion 路由）、M10 整体、M01 克隆 Job（待评估）/草稿批量提交/业务健康度看板/service_discovery、M07 IP 推导（52/58）/业务目录聚合视图、M06 `ip_cidrs`。

## 7. 风险与后续待办

1. **v0.3 变重**：门户 + 告警状态 + M10 + M03 + 后移增强并入，原 2~3 周估算失效，v0.3 规划时需重新估算、必要时再拆分。
2. **原型待对齐**：M09 原型仍欠决策 60 对齐（⚠️）；本次各模块变更为纯契约/归属调整，原型行为不变，对齐状态保持。
3. **M01/M09 v0.2 实现难点**：filter 实时求值 + 按域扇出是本版最大技术点，L2/L3 规划时优先安排技术验证。
4. **SQLite 沿用至 v0.3**：多租户数据模型落地后，元数据层避免 SQLite 特有写法，为 v0.4 PG/MySQL 迁移留路。
5. **工程提醒**（实施时带走）：cAdvisor 指标基数大，容器密度高的机器配 `--docker_only=true` 与指标白名单；VPC 对等的路由表/安全组需放通边缘节点 → 业务虚机的各 exporter 端口，建议全平台端口规范统一。
