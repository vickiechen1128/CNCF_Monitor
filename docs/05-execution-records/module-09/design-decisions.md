## 决策：配置生成文件映射、targets 模式与 Edge Agent 能力边界（2026-08-05）

### 背景

用户基于 Module_09 原型（v1.2）评审提出 5 个设计讨论点，经 Orchestrator 派发技术预研（Prometheus / VictoriaMetrics 官方文档）与两轮讨论后确认以下决策。

### 决策记录

| # | 决策 | 依据 | 影响范围 |
|---|------|------|----------|
| 1 | 标签模板（`LabelTemplate`）变更触发 **targets 列表 labels 变化**，而非 `prometheus.yml` 结构变化 | 资源标签（CMDB/user/system 来源）在生成 targets 时静态展开到 target labels；`prometheus.yml` 仅含网域级 `global.external_labels`（network_domain/tenant_id，由 NetworkDomain 驱动） | 配置文件映射、3.3 节、配置生成 |
| 2 | **MVP 范围 = 单网域 + 前端自动化下发**：配置生成 → UI 确认 → 自动写文件并 reload 中心 Prometheus；无 Edge Agent 协议暴露（后端保留、UI 隐藏） | 与 3.11 节单网域模式一致；MVP 聚焦中心自动化，隔离域能力延后 | MVP 边界、下发流程 |
| 3 | targets 采用 **file_sd（JSON 文件）**，暂不考虑 http_sd | 政务/金融专网断网风险：file_sd 的 targets 文件落本地磁盘，断网进程存活可继续抓取、**断网重启后本地立即恢复**；http_sd 依赖中心 API 在线、重启后 targets 丢失，不满足弱网自治要求 | 配置包结构、下发链路、3.3 / 6.2 节 |
| 4 | **MVP 即实施 file_sd**（难度中等偏低，增量约 15-20%）。关键设计点：targets 用固定文件名 `targets/<job>.json` + 原子写；**联合 checksum 需纳入 targets 内容**；生成器侧做 JSON schema 校验（`promtool check config` 对 file_sd 内容不校验）；reload 策略分离（仅结构变化才 reload，targets 变化由磁盘监听自动感知） | 最高频变化对象是 targets，file_sd 让 targets 变更免 reload、避免采集抖动；官方定位即"外部系统驱动 targets 的桥接机制" | 数据模型（ConfigDraft/ConfigVersion 承载 targets）、联合 checksum 算法、配置生成 |
| 5 | **Edge Agent 能力分层**：L1（配置同步 + vmagent 控制 + 心跳回执）为 v0.2 核心；**L2（为下游节点安装 exporter）因安全边界暂不纳入 PRD** | L2 扩大 agent 信任半径，涉及凭据管理、供应链、合规审计，需单独立项评审（详见下方风险备注） | Edge Agent 协议、模块边界、PRD 范围 |

### L2 能力风险备注（暂不纳入 PRD 的文字说明）

边缘 Agent 的 L2 能力（为网域内下游节点安装/升级 exporter）涉及安全边界扩展，暂不纳入 PRD 范围。风险点如下：

1. **凭据暴露面扩大**：Agent 需持有下游节点的 SSH/Agent 凭据才能安装 exporter。一旦 Agent 所在主机被攻破，网域内全部监控节点的凭据随之暴露，攻击面从"单个采集节点"放大为"整个网域"。
2. **供应链风险**：Agent 需向网域内节点分发并安装 exporter 二进制，若分发链路缺乏校验/签名，被篡改的恶意二进制将被批量植入所有节点。
3. **敏感配置注入**：部分 exporter 需注入账号密码等敏感配置（如 MySQL/Redis），传输与落盘环节的加密与密钥管理要求随之提高。
4. **合规与审计缺口**：自动化安装减少人工介入，必须提供完整的安装/升级/卸载审计与回执，否则难以满足政务/金融专网的变更审计要求。
5. **与现有流程冲突**：当前 `ExporterInstallationConfirmation` 采用人工确认制；自动化安装将改变该流程（转为"安装回执驱动"），需重新评审后再变更。

**结论**：L2 技术可行但信任半径过大。建议单独立项，先定义凭据管理、分发校验（checksum/签名）、回执模型与审计方案，再考虑进入 PRD。

### 补充决策（2026-08-05 第三轮评审：中心/边缘校验分层与衔接）

用户提问"配置生成功能的前端展示与 Edge Sync Agent 能力的关系"，确认以下设计：

| # | 决策 | 依据 | 影响范围 |
|---|------|------|----------|
| 10 | **中心/边缘校验分层与衔接**：前端「配置生成/预览」对标的是**中心侧控制**（生成 + 内容校验 + 人工确认），Edge Sync Agent 对标的是**边缘侧消费**（拉取 + 传输校验 + 应用 + 回执），两者由**同一份配置产物（ConfigVersion / zip 包）**衔接，不是"对标 Agent 能力"也不是"另一套独立校验"。校验分两层：**中心①内容校验**（promtool / blackbox --config.check / targets schema，结果以 `validation_status` 在前端展示）防**生成错误**，**边缘②传输校验**（metadata.json checksum 完整性 + targets JSON 解析，PRD 6.3）防**传输损坏/篡改/半写**。设计要点：① Agent 为「哑校验」——不做 promtool 级语法校验（中心已保证产物合法，校验①失败会阻止确认下发）；② 联合 checksum 双用途——中心草稿去重裁决 + 边缘拉包完整性校验；③ `config_sync_status`（in_sync / out_of_sync / manual_override）为 Agent 应用回执，与中心 `validation_status` 构成闭环两端 | 同产物两段链路（中心控制 / 边缘消费）；校验防不同风险；Agent 哑校验降低边缘实现复杂度 | Module_09 6.3 / 5.2 / 3.5.1、校验语义 |

### 补充决策（2026-08-06 第五轮评审：注册必要性闭环与 Agent 状态组件分类）

用户对 Module_09 功能设计提出两点疑问：①「网域管理」的「注册网域」手动填写的必要性（若安装完 Edge Sync Agent 可自动抓取，是否只需保留「安装指引」）；②「Agent 状态」的采集器维度为何单一（理论上采集器有 vmagent 也有 blackbox 等，应分类展示）。经分析确认以下决策：

| # | 决策 | 依据 | 影响范围 |
|---|------|------|----------|
| 14 | **注册网域为必要前置步骤（登记制闭环），不可被安装指引替代，但表单最小化**：闭环为「注册（登记制，最小化表单）→ 安装指引（下载离线包 + 注入凭据）→ Agent 心跳自动上线」。理由：① **Token 前置签发**——Edge Sync Agent 启动时必须携带平台签发的 `NETWORK_DOMAIN_ID` + `TOKEN`（PRD 6.3 第 2 条），Token 只能由注册时生成，未预注册网域无法鉴权，谈不上自动抓取；② **自动注册对象是 Agent 实例而非网域**——Agent 首包握手后自动创建的是 `EdgeAgent` 运行态记录，`NetworkDomain`（网络边界 + 租户映射）必须先于 Agent 存在（配置生成按网域分组并注入 external_labels 依赖网域→租户映射）；③ **安全信任锚点**——不做「首包自动建域」（隐式信任问题，且与 v0.4+「网域 = CMDB 云区域 1:1」边界约束冲突）；④ v0.4+ 注册将演化为 CMDB 同步，但 v0.2 前手动注册是唯一来源。**最小化表单**：必填仅网域名称 + 租户，`id` 按租户前缀自动生成、Token 自动签发、**Remote Write URL 由平台自动推导**（中心 ingress + 网域路径，可手动覆盖，减少手动填写项） | 用户疑问①：注册必要性 + 手动填写项过多 | Module_09 3.1 / 3.1.1、原型网域注册表单 |

#### 决策 24：技术确认 vs 审批上下文（ITIL 边界声明）+ 版本一致性语义 + 断网草稿显式说明

- **结论**：
  1. **ITIL 边界声明**：配置预览/Diff 为平台内技术确认的运维排查工具、**不构成审批上下文**；审批信息（人话摘要/变更清单/风险等级）为主区；未来 ITSM 审批上下文仅含人话摘要 + 影响范围 + 风险等级，**技术产物（YAML/Diff/checksum）不传出平台**（3.4）；

  3. **断网草稿显式说明**：断网不影响中心草稿/版本持久化（pull 模式 + DB 落库）；边缘侧保留最后一份有效配置自治采集，恢复后心跳拉取最新已审批版本（6.3）；
  4. **ITSM 集成预留**：本轮仅声明边界（v0.4+/v1.0 另行设计集成路径）。

#### 决策 25：网域上下文分层设计（跨模块一致性）

- **问题**：网域在不同模块中应以「全局上下文」「筛选器」还是「被管理对象」出现，才能避免用户动线混乱？
- **结论**：
  1. **租户是权限顶层边界，网域是操作上下文 + 采集边界**：不存在跨租户全局管理员；网域不替代租户成为最高权限边界，但可作为租户内的二级授权维度（v1.0+）。
  2. **M06 = 网域行政层**：负责 `NetworkDomain` 生命周期、租户分配、配额，是网域的行政 Owner。
  3. **M09 = 网域监控纳管层**：负责把 M06 已存在的网域接入监控（选择 `agent_type`、配置 `remote_write`、部署 Edge Sync Agent），生成 `EdgeAgent` 实例后该域才视为「已纳管」。
  4. **M01 / M09 配置下发页 = 强网域上下文**：顶部上下文栏只展示「已纳管网域」；未纳管网域提示用户先到 M09 完成纳管。
  5. **M07 = 网域作为筛选器**：资源列表无顶部网域上下文栏，用「网域」筛选器默认记忆 + 可展开「全部网域」；`Resource.network_domain_id` 为必填字段但资源本身是全局配置。
  6. **未来可视化大屏模块 = 网域作为数据标签维度**：大屏消费中心 Prometheus（管理域）聚合数据，通过 `network_domain` 标签过滤/分组，不采用 M01/M09 的上下文切换器。
  7. **禁止全局顶栏「弱提示」**：不在所有模块统一展示当前网域 pill，避免「有的模块受控、有的模块不受控」的认知断裂。
- **依据**：M01 ScrapeJob 必须绑定单一网域；M09 ConfigDraft/ConfigVersion 按网域独立生成；M07 Resource 为全局配置但带域属性；规则由中心统一求值；大屏天然跨域聚合。
- **影响范围**：
  - M06 PRD 3.1 / 5.1：明确行政 Owner 与字段边界；
  - M09 PRD 3.1 / 3.4 / 4.1 / 4.4：区分「网域注册」与「网域纳管」、上下文栏仅展示已纳管网域；
  - M01 PRD 3.1 / 5.4：ScrapeJob 网域选择仅展示已纳管网域；
  - M07 PRD 3.1 / 5.2：资源列表采用筛选器模式；
  - 未来大屏模块概念设计。

#### 决策 26：M06 与 M09 网域职责拆分

- **问题**：M06「网域生命周期管理」与 M09「网域注册页」存在功能重叠。
- **结论**：
  - M06 负责「域是否存在、归哪个租户、状态与配额」；表单字段仅限行政信息（`id/name/tenant_id/status`）。
  - M09 负责「域是否已接入监控」；从 M06 已授权网域中选择，填写监控参数（`agent_type`、`remote_write_url`、WAL 参数等），部署 Edge Sync Agent。
  - `default` 管理域由系统预置，默认视为已纳管（中心 Prometheus 直接采集，不部署 Edge Agent）。
- **依据**：M06 是权限管理模块，必须先确认租户对网域的拥有权；M09 是监控运维模块，只在用户有实际监控需求时执行纳管。

#### 决策 27：配置确认模型保留，自动发布作为可选开关

- **问题**：技术侧建议取消用户确认、由 Edge Agent 拉取成功时自动生成版本；并质疑配置文件历史记录必要性。
- **结论**：
  1. **保留 `ConfigDraft → 人工确认 → ConfigVersion → 下发/拉取` 默认模型**：用户确认是 go/no-go 审批，不是技术审查；高风险变更（删除目标、规则变更、标签模板变更）必须人工闸门。
  2. **配置历史（ConfigVersion / ConfigDeployment）必须保留**：用于回滚、审计、断网恢复后的版本同步、故障回溯。
  3. **未来可增加「自动发布」开关（P1 / v0.2+）**：仅对低风险 targets 变化自动确认；高风险仍强制人工。开关默认关闭。
  4. **版本生成时机不依赖 Agent 拉取成功**：用户确认（或自动确认）后立即生成 `ConfigVersion` 快照，Agent 断网恢复后拉取该快照。
- **依据**：M09 3.4/3.5/4.4/4.5/4.6 已定义状态机与全链路追溯；ITIL 变更管理要求审批与留痕；断网自治要求中心侧保留版本快照。
- **影响范围**：M09 PRD 3.4/3.5/4.4/4.5/4.6；M06 PRD（若自动发布开关放租户级）；后续需补写自动发布开关数据模型。

- **影响范围**：M01 PRD 5.4 网域约束；M01 创建 Job 表单校验逻辑。

- **关联模块**：Module_06（租户/网域行政层）、Module_09（网域监控纳管与下发）、Module_01（采集策略）、Module_02/M08/M07（网域作为数据/筛选维度）。

### 关键决策

#### 决策 34：网域是逻辑操作上下文与采集边界，不是控制面层级

- **问题**：随着企业级场景演化，是否应将 `NetworkDomain` 提升为独立的「域级控制面」，或为每网域部署一套完整 MetricCenter 产品实例？
- **结论（用户确认）**：
  1. **控制面保持单一中心实例（单租户内）**。所有配置生成、变更确认、版本管理、租户/权限、查询入口都在中心完成；网域不拥有自己的控制面进程或数据库。
  2. **`NetworkDomain` 是逻辑操作上下文 + 采集边界**：用于按隔离网络区域组织采集节点、在配置中注入 `external_labels.network_domain`、在 M01/M09 中按网域筛选/下发、在 M02/M08/M07 中按网域聚合/过滤。它不是独立的控制面层级，也不替代租户成为权限顶层边界。
  3. **采集节点是实际执行单元**。MVP 阶段一个网域对应一个逻辑采集组，由 `NetworkDomain.channel` 决定下发路径：
     - `local`：与中心同机/同 Pod，中心直接写盘并 `/-/reload`；
     - `agent_pull`：远端节点部署 Edge Sync Agent，心跳拉取 zip 配置包，采集器通过 remote write 回传数据到中心 TSDB。
  4. **数据面扁平化**：边缘采集器（vmagent / prometheus-agent / blackbox exporter）直接 remote write 到中心存储，中心 Prometheus / Thanos / VictoriaMetrics 提供全局查询层。不引入网域级 Prometheus federation 或中间聚合层。
  5. **跨网域大规模场景仍遵循「一个中心控制面 + 多个网域的采集节点」模型**。只有在完全空气隔离、网络不可达的极少数场景，才允许通过**离线包/摆渡**方式交付配置或数据，而不是部署第二套完整 MetricCenter 产品实例。
  6. **未来同网域多节点 / 混合通道需求按「节点级通道」演进**（见决策 33「v0.4+ 演化影响备忘」），而不是升级为「域级控制面」或「每域一套产品」。
- **依据**：
  - VictoriaMetrics 官方推荐：每集群/节点一个 vmagent，各自 remote write 到中心 VM，配置由中心统一下发——无中间控制层。
  - Prometheus 早年的层级 federation 已被社区基本废弃，原因是层级控制面版本一致性、部分失败、中间层 HA 等问题过痛。
  - Zabbix proxy 是层级中间层的反例：它能工作，但 proxy 本身成为有状态中间层，带来版本同步、故障域、升级编排负担。
  - 用户侧当前与未来可预见的 MVP~v0.4 场景均未提出跨多层控制的需求；引入域级控制面会显著增加产品复杂度且无真实收益。
- **影响范围**：
  - **Module_09 PRD**：4.1 `NetworkDomain` 模型说明中补充「网域是逻辑操作上下文，不是控制面层级」；6.5 管理面 API 保持中心集中式，不出现「域级控制面」接口。
  - **Module_06 PRD**：3.1 租户-网域关系中明确 `multi_site_enabled` 只是行政能力开关，网域不承载控制面拆分；`platform_admin` 仍为系统预置租户，不存在跨租户全局管理员。
  - **Module_01 PRD**：ScrapeJob 绑定网域作为「采集边界/目标可达性约束」，不改变「规则由中心统一求值」的原则。
  - **Module_02 / M08 / M07**：网域仅作为查询/告警/资源筛选的标签维度与筛选器，不承载控制面语义。
  - 讨论记录：`docs/04-source-architecture/2026-08-15_network-domain-and-delivery-channel-architecture-discussion.md` §6 已完整记录思辨过程。

## 补充决策（2026-08-16：纳管动线、菜单结构与采集节点状态交互闭环）

- **触发原因**：用户对 Module_09 原型（v1.24）评审提出 4 个 UX 问题：① 网域管理页同时存在右上角「纳管网域」按钮与行内「纳管」按钮，动线重复；② M09 第一页仍叫「网域管理」，与 M06 行政入口同名且易与「采集器管理」混淆；③ 原型缺少单/多网域、有/无 Agent 等形态的切换说明，不利于评审理解渐进呈现规则；④ Agent 状态页「配置同步」列只展示状态，未在「无配置」与「未同步」两种典型场景下提供引导操作，断了从安装到配置确认的闭环。
- **关联模块**：Module_09（PRD + 原型）、Module_06（网域行政命名边界）、Module_01（采集 Job 配置动线）。

### 关键决策

#### 决策 35-1：纳管入口单一化——去掉右上角「纳管网域」，仅保留行内「纳管」

- **问题**：网域纳管页右上角有「纳管网域」按钮，同时每行未纳管网域又有「纳管」按钮，哪个是主入口？
- **结论（用户确认）**：
  - 移除页面右上角「纳管网域」按钮；
  - 仅保留行内「纳管」按钮，且只在 `registration_status=created`（已创建未纳管）的行上显示；
  - 列表页本身已展示 M06 授权的全部网域及「纳管状态」列，行内动作自带目标网域上下文，无需在弹窗内二次选择。
- **完整动线**：M06 行政创建网域 → M09 列表出现「未纳管」行 → 行内点「纳管」填写监控参数（`channel` 固定、`agent_type` 固定 `vmagent`、Remote Write URL 自动推导、Token 自动签发）→ 成功后自动滚动高亮页面顶部「安装指引」提示区 → 按指引在边缘节点部署 Edge Sync Agent → 心跳上线。
- **顶部提示区定位**：页面顶部的「新网域接入操作流程」是**纳管成功之后**的安装步骤说明，不是纳管动作入口，两者不冲突。
- **依据**：决策 31 已明确网域纳管页常驻展示全部授权网域；MVP 无批量纳管需求；行内入口上下文更完整。
- **影响范围**：M09 PRD 3.1；原型 `NetworkDomainsPage`（移除右上角按钮、保留行内 `纳管`）。

#### 决策 35-2：M09 页面/子菜单改名

- **问题**：M09 第一页叫「网域管理」与 M06 行政入口同名，且「采集器管理」容易与 M01 的采集器管理 Tab 混淆。
- **结论（用户确认）**：
  - **M09 第一页由「网域管理」更名为「网域纳管」**（菜单同步改），准确表达「把 M06 已存在的网域接入监控」的职责；
  - **M09 子菜单「Agent 状态」更名为「采集节点状态」**，更贴近页面对象（边缘节点上的 Agent 部署实例 = Edge Sync Agent + 采集器组合），也比「Agent」更讲人话；
  - **M06 页面保留「网域管理」**，作为网域行政创建/分配/配额的唯一入口；
  - 不使用「采集器管理」「采集接入管理」等易与 M01 / M10 撞名的命名。
- **依据**：决策 26 已区分 M06 行政 Owner / M09 监控纳管 Owner；决策 34 强调「采集节点是实际执行单元」；M01 已有「采集器管理」Tab，M10 有监控源接入。
- **影响范围**：M09 PRD 3.1 / 3.2 / 3.8 / 3.11 / 4.2 / 6.5 / 9.x / 10；原型菜单、页面标题、页内文案、README 导航映射。

#### 决策 35-3：M09 菜单分为「网域与节点管理」和「配置下发」两组

- **问题**：四个平铺菜单项职责混杂，用户日常动线不清晰；单网域时 Agent 状态入口如何呈现也需要明确规则。
- **结论（用户确认）**：
  - **一级菜单「网域与节点管理」**（接入面）：
    - 子菜单 ①「网域纳管」；
    - 子菜单 ②「采集节点状态」；
  - **一级菜单「配置下发」**（配置面）：
    - 子菜单 ①「配置变更确认」；
    - 子菜单 ②「下发记录」；
  - **渐进呈现规则在子菜单层落地**：一级菜单组「网域与节点管理」始终常驻（因为「网域纳管」常驻）；「采集节点状态」子菜单也**常驻**，无 `EdgeAgent` 实例时不隐藏入口，而是进入**空态引导页**，提示用户先到「网域纳管」完成纳管并按安装指引接入 Edge Sync Agent。
- **依据**：决策 31 原允许「隐藏或空态」；落到子菜单结构后，空态方案能避免菜单项随数据出现/消失造成导航不稳定，同时空态页本身承担 onboarding 引导价值。
- **影响范围**：M09 PRD 3.11 / 原型 MainLayout 导航结构 / 原型 README 导航映射。

#### 决策 35-4：采集节点状态页「配置同步」列升级为带引导操作的状态机

- **问题**：刚安装完采集器（无配置）时状态应如何表达？M01 改完 Job 后显示未同步，如何引导用户回配置确认页？
- **结论（用户确认）**：
  - **状态扩展为 4 档，且两档提供引导按钮**：
    1. **未下发配置**：EdgeAgent 已上线，但该网域尚无 `ConfigVersion` → 文案「尚未生成采集配置」+ 操作按钮 **「去配置采集 Job」**，跳转 M01 采集 Job 页并预选该网域；
    2. **未同步**：存在已确认新版本但 Agent 未拉取，或存在待确认变更导致 `config_sync_status=out_of_sync` → 文案「配置未同步」+ 操作按钮 **「前往配置确认」**，跳转 M09 配置变更确认页并预选该网域；
    3. **已同步**：`config_sync_status=in_sync` → 纯展示；
    4. **人工覆盖**：`config_sync_status=manual_override` → 纯展示。
  - **推导规则**：「未下发配置」为前端推导态（`EdgeAgent.status=online && 该网域无已确认 ConfigVersion`），不扩展 `config_sync_status` 枚举；`config_sync_status` 本身仍只保留 `in_sync / out_of_sync / unknown / manual_override`。
- **依据**：形成安装 → 上线 → 引导配 Job → 变更检测 → 未同步 → 一键确认 → 已同步的完整闭环；避免用户看到无意义的「已同步/未同步」。
- **影响范围**：M09 PRD 3.2 / 3.8.1 / 4.2 / 9.x；原型 `EdgeAgentsPage` 配置同步列 / mock 数据。

#### 决策 35-5：原型演示场景切换器不进用户 UI

- **问题**：评审者需要看到单网域/多网域、有/无 Agent 等形态，但不能复活全局 banner 开关。
- **结论（用户确认）**：原型增加「演示场景」切换器，放在页面底部「原型与实现说明（面向产品/技术评审）」折叠区内，明确标注「非用户界面」；场景至少三档：① 单网域·仅 default（local）→ 采集节点状态空态；② 多网域·已纳管未上线 → 空态引导；③ 多网域·Agent 在线 → 完整展示。
- **依据**：决策 25/31 已禁止全局顶栏网域/模式开关；演示场景切换器仅供评审，不改变运行时 UI。
- **影响范围**：原型 README / MainLayout 评审折叠区 / mock 数据。

### 关键决策

#### 决策 29：M09 接管规则组织与交付（`rules.yml` 生成下发）

- **问题**：M01 创作的告警规则如何进入配置包并按网域/作用域正确下发？
- **结论**：
  1. **M01 负责规则内容创作**：`MonitoringRule` 的 expr、阈值、标签、启用状态、scope 在 M01 编辑并保存；保存时仅做「指标存在性」校验，不做 Alertmanager 路由/通知相关校验。
  2. **M09 负责规则组织与产物生成**：configgen 按 Prometheus `group` 语法自动把 `MonitoringRule` 分组为 `rules.yml`（MVP 不暴露 RuleGroup 实体给用户，避免概念冗余）；分组键由系统按规则类型/业务域自动派生，用户不可手工调整分组名。
  3. **按 `scope` 下发**：MVP~v0.3 `scope` 固定 `central`（中心统一求值）；v0.4+ 支持 `edge`/`both` 时，M09 按 scope 决定 `rules.yml` 是否进入中心配置目录或边缘 zip 包。
  4. **变更对象与影响文件**：`MonitoringRule` 变化对应的变更对象为「告警规则」，影响文件为 `rules.yml`；该变更进入 M09 配置变更确认流程，按规则变更风险等级默认 high。
- **依据**：M01 v3.13 5.5/5.6 规则编辑边界；M09 v1.32 3.3/3.4/6.2；用户确认「规则内容创作在 M01，组织交付在 M09」。
- **影响范围**：M09 PRD 3.3（配置生成）、3.4（变更确认）、4.4（ConfigDraft change_items 源对象枚举）、6.2（配置包结构）、原型 ConfigPreviewPage。

#### 决策 30：`alertmanager.yml` 由 M08 直写，不进入 M09 配置产物与审批

- **问题**：M08 管理的通知路由、接收人、静默/抑制配置是否应随 M09 配置包下发？
- **结论**：
  1. **M08 独立管理 `alertmanager.yml`**：接收人（Receiver）、路由（Route）、静默（Silence）、抑制（InhibitionRule）在 M08 编辑，保存后由 M08 直接写文件/调用 Alertmanager reload，不经过 M09 配置变更确认流程。
  2. **M09 配置产物删除 `alertmanager.yml`**：中心管理域配置目录与边缘 zip 配置包均不再包含 `alertmanager.yml`；M09 配置变更确认的对象限定为 `prometheus.yml` / `targets/*.json` / `rules.yml` / `blackbox.yml`。
  3. **变更对象解耦**：`alertmanager.yml` 变化不在 M09 变更单中体现；M09 的 Change Log 中不再把 alertmanager.yml 列为受影响文件。
  4. **MVP 阶段单域管理**：M08 在 MVP 只支持中心管理域的 Alertmanager；边缘域告警收敛（边缘 alertmanager）v0.4+ 另行设计。
- **依据**：M08 v1.3 定位收缩为「告警收敛与通知管理」；M09 v1.32 3.4 审批分级策略；用户确认「alertmanager.yml 高频低风险，走 M08 直写，不审批」。
- **影响范围**：M08 PRD 3.1/3.2/3.3/5.1/6.2；M09 PRD 3.4/6.2/6.3/Change Log；M01 PRD 3.3/5.6（规则编辑不耦合通知路由）。

- **触发原因**：用户确认① module-09 原型 Header 上的「单/多网域模式」开关会造成全局认知断裂，应从 banner 移除；②「网域管理」入口可常驻，但单域无 Agent 时 Token / Agent 状态等字段/页面对用户无意义，需条件化；③企业级场景下，同一网域内也可能因规模/HA/拨测探针位置等原因部署分布式 vmagent / blackbox 采集节点，下发通道不应再按「域类型」划分，而应按采集节点位置划分。
- **关联模块**：Module_06（租户级多域能力开关）、Module_09、Module_01（采集策略）、Module_07（资源管理）。

### 关键决策

#### 决策 31：网域入口数据驱动 + banner 模式开关移除

- **问题**：module-09 原型在全局 Header 放置 `multi_site_enabled` 单/多网域切换开关，但其他模块没有该控件，用户易误以为它是全局概念；同时单域场景下若直接常驻全部入口会产生无意义空态。
- **结论**：
  1. **Header 模式开关移除**：`Tenant.multi_site_enabled` 退化为 M06 租户级「是否允许多网域」的行政能力开关，不再作为 module-09 页面内的运行时切换器；UI 中不存在全局顶栏网域/模式切换控件，避免认知断裂（与决策 25 第 7 条一致）。
  2. **网域管理入口常驻**：无论单/多网域，`NetworkDomain` 列表页始终可访问（`default` 域预置且存在），用于查看纳管状态、下发通道等；未纳管网域引导用户完成纳管。
  3. **字段按下发通道条件展示**：网域列表/编辑表单中的 Token、最后心跳、Agent 类型、安装指引等字段，仅在「下发通道 = agent_pull」时展示；「下发通道 = local」的网域（如默认 `default`）不生成/展示 Token，也不展示运行态心跳字段。
  4. **Agent 状态入口渐进呈现**：「Agent 状态」菜单/页面不依赖「多网域模式」开关，而依赖「是否存在 EdgeAgent 实例」；实例数为零时隐藏入口或显示空态引导（提示用户先完成网域纳管并接入 Agent）。
- **依据**：用户确认原型 Header 开关不合理；决策 25 已禁止全局顶栏弱提示；`default` 域始终存在，网域管理页不应被隐藏；空态页面常驻会增加用户认知负担。
- **影响范围**：M09 PRD 3.1 / 3.2 / 3.11 / 4.1 / 4.6；原型 MainLayout（移除 banner Switch）、NetworkDomainsPage（字段条件化）、EdgeAgentsPage（入口渐进呈现）。

#### 决策 32：下发通道按「采集节点位置」而非「域类型」分层

- **问题**：原方案按 `domain_type`（management/edge）决定下发产物形态：管理域 = 本地文件集 + `/-/reload`，边缘域 = zip 包 + Agent 拉取。但用户指出企业级单网域场景也可能需要分布式采集节点（vmagent 分片、HA、blackbox 多探测点），此时节点虽在同一网域，中心却无法直接写盘 / SIGHUP，必须走 Agent 拉取通道。
- **结论**：
  1. **分层轴改为「采集节点位置/通道类型」**：下发通道绑定到**采集节点位置**，而非绑定到**网域类型**；概念模型为每个网域包含 1..N 个采集节点，每个节点对应 `local`（与中心同机/同 Pod，中心可写盘 + reload）或 `agent_pull`（远端节点，由 Edge Sync Agent 心跳拉包）之一。
  2. **域级通道作为 MVP 简化**：MVP 阶段通道在 `NetworkDomain` 级别配置（字段 `channel`：`local` / `agent_pull`），`default` 域固定 `local`、其他网域固定 `agent_pull`（见决策 33）；v0.4+ 才演进为节点级通道与混合通道。
  3. **统一产物与链路**：无论 `local` 还是 `agent_pull`，配置产物均先生成 `ConfigVersion`；`local` 通道由平台将产物写中心 Prometheus 配置目录并 reload；`agent_pull` 通道由 Edge Sync Agent 拉取 zip 包并校验。`ConfigDeployment.channel` 同步改为 `local` / `agent_pull`，`alertmanager.yml` 仍由 M08 直写，不参与本模块下发。
- **依据**：VictoriaMetrics/vmagent 官方推荐按集群/可用区分片采集；blackbox 探测结果强依赖探针物理位置；同一网域内存在多个采集节点是常见企业级拓扑；决策 6 的「域类型分层」无法表达这种同域异构部署。
- **影响范围**：M09 PRD 1.0（核心职责 6/7）、3.1、3.4、3.5、3.8.1、3.9、3.11、4.1、4.6；原型 ConfigPreviewPage / DeploymentsPage（发布通道标注由「管理域/边缘域」改为「local/agent_pull」）。

#### 决策 33：MVP 不支持混合通道与通道切换（v0.4+ 演化边界）

- **问题**：「同一网域内出现多个采集节点 / 混合通道（local + agent_pull 并存）」「引导用户从 local 切换 agent_pull」是否需要在 MVP 支持？
- **结论（用户确认）**：
  1. **MVP 不支持同一网域内混合通道**：一个网域同一时刻只有一种下发通道、对应一个逻辑采集组；混合通道属过度设计，推迟到 v0.4+ 结合实际需求再评审。
  2. **MVP 不提供通道切换**：`channel` 在纳管时按网域确定（`default` 管理域固定 `local`，其他网域固定 `agent_pull`），编辑表单不提供通道切换入口；「default 域改走 agent_pull」无 MVP 场景，推迟到 v0.4+。
  3. **单网域分布式采集（vmagent 分片 / HA / blackbox 多探测点）整体推迟到 v0.4+**：届时一并评审「节点级通道 + 混合通道 + 通道切换」。
- **依据**：MVP 侧用户未提出同域多节点需求；切换通道缺乏真实场景；提前支持会引入下列 v0.4+ 影响面，属于过度设计。
- **影响范围**：M09 PRD 1.0 / 3.1 / 3.9 / 3.11 / 4.1 / 4.2 / 9.x / 10（移除 MVP 阶段通道切换与混合通道表述）。

### v0.4+ 演化影响备忘（供将来版本评审检索）

> 若 v0.4+ 引入「同一网域多采集节点 / 混合通道 / 通道切换」，以下三个面必须同步重新设计，当前 MVP 文档与实现均**未覆盖**：

1. **M09 配置下发粒度**：配置生成仍是网域级（`ConfigDraft` / `ConfigVersion` 按网域），但 `ConfigDeployment` 需从网域粒度细化到**节点粒度**（哪个节点拉到了哪个版本）；心跳、WAL 积压、`config_sync_status` 需按节点聚合；混合通道时同一份 `ConfigVersion` 需同时走「写中心盘 + 打包给 Agent」两条路径，需明确一致性策略；UI 保持网域筛选 + 节点下钻。
2. **M01 采集 Job 与规则**：同一网域多个 `agent_pull` 节点默认会重复执行同一 Job，产生重复序列；必须引入**节点级分片**（`hashmod` / 目标拆分）或 **Job→节点绑定** 或 **HA 主备去重**；规则编辑仍是中心统一管理（`scope=central` 不受影响），但 `scope=edge` 规则下发到多节点时需决定逐节点求值还是选主求值。
3. **external_labels 标签规范**：仅靠 `network_domain` 无法区分同域不同节点产生的数据——分片场景需要 `shard`/`node` 标签下钻定位，HA 场景需要 `replica`/`cluster` 标签供中心去重，排障需要节点来源标签；`network_domain` 维度的查询/权限/聚合保持不变。
4. **通道切换**：`local` ↔ `agent_pull` 切换需定义历史 `ConfigVersion` / `ConfigDeployment` 处理策略（是否保留原通道记录、是否强制重新纳管），以及切换期间的在途变更处理方式。

## 补充决策（2026-08-16：网域纳管页列收敛 + 采集节点状态页改节点平铺表）

- **触发原因**：用户评审 Module_09 原型（v1.24）发现两个 UX 问题──① 网域纳管页列数过多（zone_type / center_endpoint / remote_write_url / agent_type / description 等配置字段与日常巡检字段混排），用户感知杂乱；② 采集节点状态页的「网域聚合 + 展开式子表」结构导致筛选功能失效（展开行嵌套子表与筛选器无法联动），且三个进程（Edge Sync Agent / vmagent / blackbox exporter）的关系在 UI 上未自解释。
- **关联模块**：Module_09（PRD + 原型）、Module_01（采集 Job 配置动线）。

### 关键决策

#### 决策 36-1：网域纳管页列收敛 + 详情抽屉

- **问题**：网域纳管列表当前展示 10+ 列（id / 名称 / 域类型 / 网络区域类型 / 纳管状态 / 下发通道 / Token / Agent 类型 / Remote Write URL / 中心接入地址 / 状态 / 最后心跳 / 描述 / 操作），其中 center_endpoint、remote_write_url、agent_type、description 是「配一次就不动」的配置字段，日常运维不需要每天扫一眼；列多是把不同查看频率的信息摊在了同一层。
- **结论（用户确认，{v1.36 原型修正}）**：**列表主列按 7 列**，其余字段进「查看详情」右侧抽屉；zone_type 从抽屉提升为列表主列：
  1. **网域**（名称 + ID 两行合并一列，如 `政务云 A 区\ngov-cloud-a`）
  2. **网络区域类型**（zone_type，Tag 展示；政务云场景：互联网区/政务外网区/专线区；公有云场景：region 标识——用户扫列表第一眼认的是 zone_type，网域名称反而是辅助）
  3. **纳管状态**（created / monitored）
  4. **下发通道**（local / agent_pull，Tag 展示）
  5. **运行状态**（状态 + 最后心跳合并，如 `在线 · 5 分钟前`；仅 agent_pull 展示，local 展示 `-`）
  6. **凭据**（仅 agent_pull 行：脱敏 Token + 复制图标，窄列；local 行展示 `-`）
  7. **操作**（纳管 / 编辑 / 更多[重置 Token]）
- **抽屉内字段**（修正后，仅剩低频配置字段）：中心接入地址（center_endpoint）、Remote Write URL、Agent 类型、描述、组件运行状态概览。
- **{v1.36 操作列修正}**：操作列改为**三槽位固定结构**——`主操作 · 详情 · 更多`，所有按钮统一为文本链接样式（蓝色），消除实心按钮的视觉断裂感：
  - **主操作**：随行状态变化——未纳管行显示「**纳管**」（首次填监控参数+签发 Token，触发安装指引高亮），已纳管行显示「**编辑**」（参数维护，不改变纳管状态）；两者打开同一张表单但传递不同状态信号。
  - **详情**：常驻按钮，打开右侧详情 Drawer；决策 36 将大量字段收进抽屉后，详情成为最高频的读操作，不再藏在「更多」里。
  - **更多**：折叠低频/高危操作——仅 `agent_pull` 已纳管行出现「重置 Token」（二次确认弹窗），`local` 通道行和未纳管行整栏隐藏。
  - **依据**：「纳管」与「编辑」打开的虽是同一张表单，但向用户传递的**状态信号**不同——看到「纳管」立刻知道该网域未接入监控，看到「编辑」知道已在运行，这个信号有价值，不应合并。重置 Token 低频且有破坏性（旧 Token 立即失效，边缘 Agent 需重新部署），留在「更多」+ 二次确认更合适。详情是决策 36 列收敛后最高频的读操作，应独立显示。
- **渐进披露模式**：与 M01/M07 的 Drawer 模式一致；列表聚焦高频巡检信息，配置字段下沉到详情抽屉，排障或核对方可查看。
- **依据**：① zone_type 不是「配一次就不动」的运维参数，而是**网域身份的并列识别维度**——政务云场景按网络区域（互联网区/政务外网区/专线区）部署，一个区域一个节点；公有云场景按 region 部署，region 就是网域身份标识。zone_type 与决策 34 定位一致（NetworkDomain 是隔离边界实体，zone_type 是它的位置/行政身份属性）。② 真正低频的是 center_endpoint、remote_write_url、agent_type、description——这些才是「配一次基本不动」的配置字段，进抽屉合适。③ 7 列在常规屏宽下仍可完整展示，不撑爆。④ 兜底方案：可复用 M07 已有的「列显隐配置」模式（P1），让不同部署形态自选列，但默认主列按 7 列，不靠用户自己配出来。
- **影响范围**：M09 PRD 3.1（网域纳管列表字段表）、原型 NetworkDomainsPage（列收敛 + 详情 Drawer，zone_type 提升为第 2 列）。

#### 决策 36-2：采集节点状态页改节点平铺表 + 组件抽屉 + 组件关系说明

- **问题**：① 当前「网域聚合 + 展开行组件子表」结构导致筛选失效（展开行内的组件类型与筛选器无法联动）；② 用户心智中「采集节点」是实际安装的机器（一个主机名/IP 对应一个节点），但页面以网域为主对象，不符合用户直觉；③ 三个进程（Edge Sync Agent / vmagent / blackbox）的关系页面未自解释——用户困惑「是否同一进程」「vmagent 挂了 Agent 挂不挂」「我装的到底是什么」。
- **结论（用户确认）**：**改为一层平铺表 + 组件详情抽屉**，彻底解决三个问题：
  1. **主对象改为「采集节点」**（用户的心智单元：在哪个机器上装了什么东西），一行一个节点：
     - **节点**（主机名 / IP）、**网域**、**整体状态**（聚合三档：正常 / 部分异常 / 离线——规则：Agent 离线→离线；必装组件异常→部分异常）、**采集器状态**、**拨测器状态**、**配置同步**（含引导按钮）、**WAL 积压**、**最后心跳**。
  2. **组件明细进「查看」抽屉**（不再用展开行嵌套子表）：抽屉内按组件分区（edge-sync-agent / vmagent / blackbox-exporter 各一块），每块一行核心字段：组件类型 Tag、状态、版本、配置版本；实例名等长字段允许截断 + Tooltip 悬停看全；**「最近错误」不再全文展示**——抽屉内仅显示最近一条错误的一句话摘要 + 时间（截断约 80 字符），旁边一个「查看错误详情」按钮，点开用 **Modal 弹窗**（而非嵌套抽屉）展示完整错误文本（等宽字体、可复制）、发生时间、所属组件、关联配置版本；抽屉内配一句话组件关系说明：「Agent 是管理进程，负责拉取配置和守护另外两个进程。某个进程异常会被自动重启并在此处展示。」
  3. **筛选全部作用于平铺列**：网域、整体状态、采集器状态、拨测器状态、配置同步——折叠行被干掉后筛选自然恢复可用。
  4. **页面顶部加组件关系说明**（讲人话）：「一次安装 = 三个进程：Edge Sync Agent（管理进程）+ 采集器 vmagent（采集指标）+ 拨测器 blackbox（可选）。Edge Sync Agent 负责拉取配置并守护另外两个进程，某个进程异常会被自动重启并在此处展示。」
- **三个进程的架构关系（技术确认）**：
  - Edge Sync Agent：我们自己开发的管理进程（Go 二进制），负责向中心心跳/拉配置包、守护 vmagent 和 blackbox_exporter 进程（启动、健康检查、异常自动重启、配置更新后 reload）。
  - vmagent：VictoriaMetrics 官方二进制，干活的采集器。
  - blackbox_exporter：Prometheus 官方二进制，拨测器（可选，该网域有拨测 Job 才装）。
  - 三者是**独立进程**，不是同一个进程。vmagent 挂了，Edge Sync Agent 不会跟着挂（Agent 自己活着的证据是心跳本身；进程死了心跳停，中心超时后标 offline）。
  - 监控 vmagent/blackbox 技术上完全可行（Agent 与它们同机，通过进程存活 + 本地健康端点采集状态，随心跳上报）。
  - 故障语义：vmagent 挂 → Agent 健康检查发现 → 自动重启 → 心跳上报 collector_status=stopped→running。页面展示「节点在线，但采集器异常」——这是最有价值的信息分层：管理面活着、数据面有问题。
- **依据**：用户反馈「筛选器不好用」根因是展开行嵌套子表导致筛选无法联动覆盖子表列；用户心智的「节点」是物理安装单位而非逻辑网域；三个进程关系在 UI 上不自解释导致认知成本；去掉折叠行后筛选器自然恢复作用。
