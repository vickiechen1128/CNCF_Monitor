## 1. 结论摘要

| # | 议题 | 结论 |
|---|------|------|
| 1 | 中心推送安装 | **不做**。安全性上与市场既有决策 5（否决 Agent 持 SSH 凭据）同源且爆破半径更大；网络上前提出不成立（中心到边缘无入站端口） |
| 2 | 真正的待解问题 | 不是「推 vs 下载」，而是「**装完之后怎么升级**」（见 §3） |
| 3 | Agent 自升级 | **建议恢复评估**：M11 PRD §3.3 现为「**不做**（风险保守原则）」，与本文建议冲突，为显式待重新审视项（见 §3.4、§8-D3） |
| 4 | 三区中心选址 | 中心放**政务云互联网区**（唯一与另两区都有通道的枢纽区）；政务外网区 + 腾讯云区各部署一个采集节点（`agent_pull`）；边缘区**不加**二级汇聚代理（见 §4） |
| 5 | 代理服务器的性质 | 网闸穿越**不需要**代理（Agent 已支持 `HTTPS_PROXY`）；中心侧**建议**加反向代理；边缘区中继设备**只在必要时**引入，且必须是应用层反代 + 存储转发（见 §4.4、§5.3） |
| 6 | 方案 A′/B 决策 | **推荐 A′ = 中心留政务云互联网区 + UI 控制台外移腾讯云**；**不建议**为运维便利把中心搬到腾讯云（详见 §5） |
| 7 | Edge Agent 的拓扑无关性 | **成立，且不需要改 Agent 代码**。差异只落在网域表 `center_endpoint` / `remote_write_url` 两个字段填什么（见 §5.4） |
| 8 | 阻断级缺口 | 中心侧 **remote_write 接收端缺失**（`--web.enable-remote-write-receiver` 未开、`platform/` 无 ingest 实现）→ 边缘指标目前无处可写，A/A′/B 全部依赖此项（见 §7-G1） |

### 1.1 三轮讨论的因果链

```
① 怎么装？  ──→  装的形态不是瓶颈，"装完之后怎么升级"才是（人工重装 N 节点不可持续）
                        │
② 三区怎么放？──→  由连接的**方向性**决定：边缘主动出站 ⇒ 中心必须落在"人人可达"的枢纽区
                        │
③ 能不能把中心放腾讯云？──→  真正在意的是**访问面**（运维办公网），不是数据面
                        │
                        └──→  解耦：控制面+数据面留政务云，只把 UI 搬到你方便的地方
```

## 2. 背景

### 2.1 用户真实拓扑与约束（第二轮、第三轮输入）

| 区域 | 简称 | 网络约束 | 运维可达性 |
|------|------|---------|-----------|
| 政务云·政务外网区 | G1 | ↔ G2 走**双向网闸**，**来回映射地址不同**；↔ T 不可达 | 需申请**云桌面**访问，不便 |
| 政务云·互联网区 | G2 | ↔ G1 经网闸；↔ T 经物理防火墙 + 云防火墙，**开策略可通**；出口有物理防火墙 | 需 **VPN + 堡垒机**进入 |
| 腾讯云·公有云区 | T | ↔ G2 开通策略后可通 | **零信任**直达 |

**运维日常工作位置：普通互联网办公网。**

中心（管理域 `default` / `local` 通道）只能有一个；其余两区为采集节点域（`agent_pull`）。

### 2.2 三条已落版的硬约束（不可绕过）

| # | 约束 | 出处 |
|---|------|------|
| 1 | **中心无入站端口**：心跳 / 拉包 / remote_write 全部由边缘主动出站，中心无需开放任何防火墙入站规则 | M11 §6.1；`module-09/design-decisions.md` 决策 9 |
| 2 | **不提供 `curl\|bash` 一键脚本**（政务网 / 金融专网普遍禁用）；交付形态为离线二进制包 + systemd 一体化包 | M11 §3.3「交付形态」 |
| 3 | **`force_restart` 不做**：中心远程重启边缘进程的指令通道不做，维持 outbound-only 安全边界 | M11 §1.2 边界声明 |

> 约束 1 是选址问题的**决定性**前提：一旦接受「只有出站」，中心的物理位置就必须满足"所有采集节点域都能主动连到它"。

## 3. Agent 升级策略（第一轮）

### 3.1 问题重述

原问题是「能否由中心推送安装」。结论是**不能**，理由有二：

- **网络层不成立**：中心→边缘方向本来就无入站通道（约束 1），推送需要额外的可达性工程。
- **安全模型冲突**：既有决策 5 已否决「Agent 持 SSH 凭据为下游节点装 exporter」（5 条风险：凭据暴露面、供应链篡改、敏感配置注入、审计缺口、与人工确认流程冲突，见 `module-09/design-decisions.md`）。**中心推送是同一问题的更严重版本**——爆破半径从单个网域放大为整个平台（中心需持有所有网域的主机凭据）。

### 3.2 真正的瓶颈：安装是低频的，升级是高频的

`platform/edge-sync-agent/packaging/README.md`（feat 工作树）明确写死：二进制升级需**人工替换 + `systemctl restart`**。由此推导：

> 每发布一次边缘包，就要对**每一个**采集节点执行一次「下载 → 摆渡 → 覆盖安装 → 重启」。节点数 N × 升级次数 M 的人工成本线性增长，而 version bump / 安全补丁属于常态需求。

若 go-no-go 条件成熟再评估推送，门槛是：**中心→边缘有可控入站通道 + 客户书面授权主机凭据托管（KMS/Vault 短期凭据）+ 网域数规模化 + 具备安装回执与回滚审计**。即使满足，推荐形态也是**「可编排交付」**（平台出幂等产物与脚本，由客户侧 Ansible / Salt 执行，凭据留在客户侧），而非平台内置 SSH——后者是下策。

### 3.3 建议的四层路径模型

| 层 | 机制 | 方向 | 自动化程度 | 现状 |
|----|------|------|-----------|------|
| 首次安装 | 下载一体化离线包 + 人工三步 | 人从中心拉取 | 人工 | ✅ 已覆盖（§3.3 下载入口） |
| 凭据注入 | 网域 Token（完全脱敏 + 复制） | 一次性 | 人工 | ✅ 已覆盖（§3.1 纳管取凭据） |
| 配置下发 | 心跳拉包 | 边缘 → 中心出站 | 自动 | ✅ 已覆盖（§6.2 / §6.3） |
| **Agent / 组件升级** | **心跳带版本 → 中心返回 latest + URL → 拉签名包 → 校验 → 原子替换 → systemd 重启** | 边缘 → 中心出站 | **建议新增，默认关** | ❌ PRD 现为「不做」 |

自升级**不扩大信任半径**（无入站、无主机凭据），复用既有拉包链路。

### 3.4 ⚠️ 与既有 PRD 决策的冲突声明（必读）

**M11 PRD §3.3 现文明示：`Agent 自升级 | 不做（风险保守原则）`**（另有决策 86 记录 `module-09/design-decisions.md` L2352「Agent 不做自升级」；`Modules/README.md` L74 v1.79 条目同）。

本文**不满足于绕开该决策**，而是正式提出：**以 {v0.3} 拉模式自升级为目标重新审视**。理由与边界：

| 维度 | 主张 |
|------|------|
| 为什么不推翻而是"重新审视" | 「风险保守」在小规模（节点数 ≤ 5、年升级 1~2 次）时**是正确的**；成本问题在规模化后才尖锐。应把它设为带门槛的能力，而非无条件禁用 |
| 触发重评的条件（建议） | 采集节点数 ≥ 10 **或** 年升级次数 ≥ 3 时，默认走自升级；低于该规模维持人工引导升级（§4.4 流程） |
| 护栏（缺一不可） | ① **必须 ed25519 签名**，不能只靠 checksum——checksum 只防传输损坏，防不住供应链篡改，而供应链正是决策 5 否决推送的第 2 条理由；② 默认 `auto_update=false`、升级窗口可配；③ 保留上一版二进制，启动失败原子回滚；④ 按网域灰度；⑤ 升级结果与错误进心跳上报 |

> **待拍板 §8-D3**。若维持「不做」，则本文 §3.3 第四层不成立，但 §4 / §5 的拓扑结论不受影响。

### 3.5 一条实现侧文案缺陷（次要）

生产前端 `ui-custom/web/src/pages/config-center/nodes/EdgeAgentsPage.tsx`（feat 工作树）空态文案为「按**页面顶部**「安装指引」…」，但按 PRD §11.3，安装指引 / 下载区块位于**网域纳管页**顶部，采集节点状态页并无该区域 → 文案指向本页不存在的元素。建议改为「前往网域纳管页查看安装指引」。（属 `dev-feedback` 层，非本文主线）

## 4. 三区拓扑选址（第二轮）

### 4.1 为什么中心必须在 G2（政务云互联网区）

`agent_pull` 的全部流量方向为「采集节点 → 中心」（§6.1），因此**中心必须被另外两个采集节点域都能主动访问到**：

| 候选位置 | 结论 | 理由 |
|---------|------|------|
| G1 政务外网区 | ✗ | T 的 Agent 到不了（需穿网闸再出公网，两跳）；且「公有云主动访问政务外网区」在合规上几乎不可能批 |
| T 腾讯云公有云区 | ✗ | G1 出不去；且**政务指标出域**到公有云，数据合规风险最高（这是 §5 中方案 B 的核心代价） |
| **G2 政务云互联网区** | ✅ | G1 经网闸可达、T 经防火墙策略可达；且 G1 + G2 指标**全部留在政务云内**，只有 T 指标**回传进入**政务云（入方向，比出方向好批） |

代价是 G2 暴露面相对较大，用三件事收敛：**来源 IP 白名单**（网闸映射 IP + 腾讯云 NAT 出口 IP）、**每网域独立 Token**（退纳管即废止）、**UI 不向边缘暴露**。

### 4.2 分区配置建议

| 区域 | 网域 | `channel` | `zone_type` | `center_endpoint`（该区视角） |
|------|------|-----------|-------------|------------------------------|
| G2 互联网区 | `default`（管理域） | `local` | internet | 无（同区直连） |
| G1 政务外网区 | 待定 | `agent_pull` | extranet | **网闸映射后的中心地址** |
| T 腾讯云公有云区 | 待定 | `agent_pull` | public | 中心公网地址 |

> 用户提到「来回通道的映射地址不同」——这正是 `center_endpoint` / `remote_write_url` 设计为**网域级**字段、语义为「**该网域视角的可达地址**」的原因（§5.1）。（核对：旧 M09 PRD 曾表述为「网闸映射后地址」；M11 v0.2 §5.1 表述为「转发场景填转发侧可达地址」，语义一致且覆盖更广——**已包含中继转发场景**。）
>
> **两个边缘网域必须填各自视角的地址，不可复用同一个。**

### 4.3 边缘区是否需要二级汇聚代理：不建议

「网闸映射地址稀缺」的问题已被 PRD 的单节点口径解决——**一个网域只需装一个采集节点**（§3.1「单网域只需一台常开机器部署一个采集节点」），因此 G1 全网域只需 **1 条**映射，无需给每台业务机器开映射。

只有该区规模大到单 Agent 扛不住时才需要区内汇聚，而这属于 {v0.4+} 同域多节点演化的范围，MVP / v0.2 不展开。

### 4.4 代理三问

| 问题 | 结论 |
|------|------|
| 网闸穿越需要代理吗 | **默认不需要**。若网闸只放行 HTTP 代理协议，Agent **零改动已支持**：`platform/edge-sync-agent/internal/client/client.go:45` 使用 `&http.Client{Timeout: …}`（Transport 为 nil → `http.DefaultTransport` → `Proxy: http.ProxyFromEnvironment`），配 `HTTPS_PROXY` 环境变量即可走 CONNECT 隧道。**待验证**：vmagent 的 remote_write 是否同样可走代理（VictoriaMetrics 提供 `-remoteWrite.proxyURL`） |
| 中心侧需要反向代理吗 | **建议加**（Nginx / Envoy，不自研）。四个作用：统一地址服务多个边缘网域（省网闸映射资源）、IP 白名单与 TLS 终结、agent 接口与 UI 分流、**承载指标写入接收**（见 §7-G1） |
| 边缘区需要中继吗 | **仅在 G1↔G2 网闸实测不穿透时**引入，且形态有硬性要求，见 §5.3 |

## 5. 访问面解耦与方案 A′/B 决策（第三轮）

### 5.1 核心洞察：把三个面分开看

用户提出「中心能否放腾讯云」的真实动因是**运维在互联网办公、进政务云要 VPN+堡垒机不方便**。这是**访问面**问题，不是数据面问题。

| 面 | 内容 | 选址依据 | 能否搬走 |
|---|------|---------|---------|
| **数据面** | TSDB 落地、指标查询回源 | 枢纽位置 + **数据合规** | 不宜搬 |
| **控制面** | 心跳 / 纳管 / 配置下发 | 必须全局唯一，且须被所有采集节点域可达 | 不宜搬 |
| **访问面** | UI 控制台、告警通知出口 | **跟着运维办公网走** | ✅ **可以搬** |

按 §1.2 边界，既有 PRD 的 §11 前端契约隐含「UI 与中心同址」假设；这里建议把它显式拆出来。

### 5.2 三个方案对比

| | 方案 A：中心在 G2 | 方案 B：中心在 T + G2 跳板机 | **方案 A′：中心在 G2 + UI 外移 T** |
|---|---|---|---|
| G1 部署 | 采集节点（出站至 G2） | 采集节点（出站至 G2 跳板） | 采集节点（出站至 G2） |
| G2 部署 | **监控中心**（控制面+数据面+UI） | **relay 缓冲转发**（运维成本≈半个中心） | **监控中心**（仅开放受限接口） |
| T 部署 | 采集节点 | **监控中心** | 采集节点 + **UI 控制台（静态资源）** |
| 运维入口 | VPN + 堡垒机（不便） | 零信任直达 | **零信任直达** |
| 数据流向 | 全部留政务云 | **政务数据落到公有云** | **全部留政务云** |

### 5.3 为什么不建议把跳板机做成"转发管道"

用户的设想（G2 放一台机器让 G1 remote write 过去）技术上可行，但**不能是 L4 / 纯端口转发**：

| # | 理由 |
|---|------|
| 1 | `remote_write` 是持续 HTTPS 流 + snappy/protobuf，网闸与公网会切断空闲长连接 → **直接丢数据**；这正是 PRD §3.1「网闸按标准 HTTPS 可穿透设计、**待客户环境实测**」所列的待验证项 |
| 2 | 因 G1↔T 不可达，G1 的**心跳 / 拉配置也必须过这台机器**（不只是数据面）→ 它必须是**应用层反向代理**，不是 `iptables` / `stream` 转发 |
| 3 | L4 转发做不了网域身份透传，远端中心认不出是哪个网域的数据 → `network_domain` 标签丢失或必须每网域一条独立通道 |
| 4 | 一台机器成为**整个 G1 的单一故障域** |

若必须引入，正确形态应是**「互联网区监控专用缓冲 / 转发网关」**：

- **管理面**（心跳 / 拉包 / 升级包下载）：Nginx / Envoy 应用层反代；
- **数据面**（remote_write）：带持久化队列的存储转发组件（如 vmagent + `-remoteWrite.tmpDataPath`，断网自动续传），**不要**用纯 Prometheus receiver 裸跑，也不要用 TCP 转发；
- relay 尽量**无状态**（除缓冲队列），可快速重建。

### 5.4 Edge Agent 对拓扑无关：A / A′ / B 都满足，且无需改代码

| # | 依据 | 位置 |
|---|------|------|
| 1 | `center_endpoint` / `remote_write_url` 为**网域级**字段，语义「转发场景填转发侧可达地址」 | M11 §5.1；代码 `platform/models/network_domain.go:78/79` |
| 2 | 明确的方向约束「**全部为上行（采集节点 → 中心）**，中心不主动入站」 | M11 §6.1 |
| 3 | HTTP client 走 `http.DefaultTransport`（`Proxy: http.ProxyFromEnvironment`）→ 支持 `HTTPS_PROXY` CONNECT 隧道 | `platform/edge-sync-agent/internal/client/client.go:45` |
| 4 | 每网域独立 Token 鉴权，中继两侧可用不同凭据 | M11 §3.5 |

> **结论**：Agent 对"目标是中心还是 relay"**完全无感**。中心选址与中继与否，差异只落在**网域表两个地址字段填什么**——这是产品可交付能力，不是代码变更。

补一条有利证据：`contract.HeartbeatRequest` 已带 `wal_backlog_bytes` / `remote_write_queue_size`（对齐 §5.3 EdgeHeartbeat 模型），多一跳后若堆积积压**是可观测的**。

### 5.5 推荐方案 A′ 的落地要点与代价

落地只需三件事：

1. UI 静态资源部署在腾讯云（零信任网内），构建期注入 `VITE_API_BASE_URL` 回指 G2 的 `/api/v2/platform` —— **前端已原生支持**：`ui-custom/web/src/api/client.ts:6` `const BASE_URL = import.meta.env.VITE_API_BASE_URL || ''`；
2. G2 侧反向代理公开后端 API，限定来源 IP = 腾讯云 UI 出口 IP；
3. UI 与 agent 接口分流，UI 不向边缘映射地址暴露。

**为什么合规上优于方案 B**：认证链路方向是「腾讯云 UI → 政务云互联网区 API」，属**入方向**访问。**指标一条都没有离开政务云**；而 G2 本就是对外服务区，T 主动访问它与"互联网用户访问该区"差别不大，只需 1 条防火墙策略。

**代价（须如实告知）**：

- UI → API 跨区，**PromQL 查询代理（M02）/ 告警代理（M08）的响应数据要走这条链路**，大时间窗查询延迟可能上升（数十至数百毫秒），需实测；
- 腾讯云侧多一台静态资源机（轻量、无状态、可多副本）；
- **零号备选（建议优先尝试）**：相当多堡垒机 / 零信任产品自带 Web 应用反向发布能力，可直接把 G2 的 UI 发布到运维办公网，连腾讯云这台机器都省了。

### 5.6 何时才真的该用方案 B

需**同时**满足：

1. 监管书面允许政务数据出入公有云；
2. 腾讯云侧已有统一可观测平台要做收敛；
3. 政务云侧确实拿不到资源。

仅为了「运维少拨一次 VPN」而把控制面与数据面搬去公有云，是**拿数据合规换操作便利**——这笔账不划算。把 UI 搬走就够了。
