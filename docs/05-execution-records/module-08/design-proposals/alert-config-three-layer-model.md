## 1. 背景：两个关联议题

### 1.1 议题一：三层配置模型（配置内容从哪来）

2026-10-02 用户提出一套三层配置模型，并附带 SSOT / 禁用疑问：

> **三层模型**
> 1. **预设标准 alertmanager 配置文件（标准模板库）**：给「完全不会用平台」的用户——产品方/运维在后台帮他配好一套可用的标准配置。
> 2. **平台派生配置**：用户一旦自行修改了路由/通知渠道/通知模板，平台派生出一份「平台生产的配置文件」。
> 3. **高级用户自己挂载配置文件**：保留给熟练产品的高级用户一个手写挂载入口。
>
> **SSOT / 禁用疑问**：是否要考虑单一事实来源？用户一旦想自己编辑配置文件，平台上已有的路由/渠道/模板，他是否需要逐项选择「禁用」？

### 1.2 议题二：告警配置页信息架构（用户怎么操作这些内容）

同日用户就 `/alert-config` 页提出：

> 既然现在路由规则功能也开发完全了，是否可以把「挂载新配置」降级，优先引导用户去配置 UI 层面的控制而不是直接编辑配置文件？当前「写配置前必读：三块必写 + 两块豁免」、「当前生效配置」、「派生预览：平台将写入的接收人」这些子功能造成**信息杂乱无章，没有逻辑性**；尤其「当前生效配置」中「默认兜底接收人」、「路由规则作者模式」两个按钮**为什么不是全局按钮，是否应该提级到全局按钮**，UI 术语也过于技术化。

### 1.3 两议题为何必须合并落档

**它们是同一件事的投影：议题一决定「配置内容从哪来」，议题二决定「用户以为配置从哪来」。UI 必须忠实反映能力分层，否则能力已落地而 UI 仍在教用户手写 YAML。**

逐层对应关系：

| 三层模型（议题一） | 该态下用户真正的动作 | UI 应有的层级（议题二） |
|---|---|---|
| ① 预置种子（标准模板库） | 打开就有可用配置，**不需要做任何动作** | 页头**不得**挂「上传文件」主按钮；首屏须明示「平台已为你准备基础配置」 |
| ② 平台派生（改渠道/路由即生效） | 在 UI 里点选，文件是**产物** | 派生预览从「主流程卡」降为「高级只读」；UI 控件提级为页面级策略 |
| ③ 手写逃生舱（永久保留） | 上传/粘贴整份 YAML | 降为高级区入口，**不删除**（§11.6） |

**现状正是错配的**：路由 UI 化已落地（v0.3-a/b，T08-F10/F11），接收人 UI 化已落地（决策 74），但 `AlertConfigPage.tsx` 的信息架构仍停留在「文件挂载中心」形态。`alert-config-scope-and-notification-bridge.md` §3.2.4 早已预言「三块 UI 化后，文件挂载页退化为『只读视图 + 高级编辑逃生门』」——**该预言已成真，页面却未跟上**。故两议题必须同批拍板、同批落地，否则会出现「能力已落地 / UI 仍教手写」的产品自相矛盾。

## 4. SSOT 与「禁用」分析（议题一核心问题）

### 4.1 用户担忧的本质

「禁用」疑问的本质是怕：开启手写后，平台上已有的路由/渠道/模板还在文件里「打架」。这是一种**逐实体的、事后打补丁式**的 SSOT 治理思路。

### 4.2 已决策 SSOT = 段级所有权 + 模式开关（不是逐实体禁用）

PRD §4.1.1 早已给出 SSOT 答案，且粒度是**「段」**而非**「实体」**：

- `route` 段：要么托管（平台派生），要么手写（用户全权），**模式开关是互斥单作者**；
- `receivers` 段：按命名空间双作者（平台槽位 vs 用户自有实名 receiver），**冲突即报错、不静默覆盖**；
- 模板/静默时段：`templates`/`mute_time_intervals` 归用户；`inhibit_rules` 平台 + 用户可追加。

**结论**：SSOT 已由「段级所有权 + 模式开关」承载，**不需要再引入逐实体的「禁用」开关**。

### 4.3 为什么「逐实体禁用」是反模式（若强行加）

| 风险 | 说明 |
|------|------|
| 双重语义 | 「禁用但仍在文件里」造成「到底生不生效」的歧义，比不禁用更难排查 |
| 幽灵配置 | 禁用的实体若被别处引用（route→receiver、inhibit→target），产生悬空引用 / 静默失效（dead config），与 v0.3-a「消解死接收人」立身点相冲 |
| 击穿逃生舱 | 模式开关的本意是「开手写 = 平台把这段完全让给你」；逐实体禁用又reintroduce 了「平台半管控」，与 §11.6 逃生舱语义冲突 |
| N 个开关爆炸 | 路由/渠道/模板/静默/抑制各加禁用，UI 与状态机复杂度线性膨胀，且互相组合语义不可穷举 |

## 6. 议题二：告警配置页现状诊断

### 6.1 当前结构（五段式，`AlertConfigPage.tsx`）

| 顺序 | 区块 | 行号 | 定位 |
|---|---|---|---|
| ① | 页头卡 + 主按钮「挂载新配置」+ 两行定位说明 | `:398-417` | **页面主操作 = 上传整份文件** |
| ② | 折叠栏「写配置前必读：三块必写 + 两块豁免」+ 最小骨架 | `:421-497` | 手写时代的说明书 |
| ③ | 「当前生效配置」卡：内含**两个策略控件** + 版本元数据 + 完整 YAML | `:538-646` | 控件埋进元数据卡（`:553-585`） |
| ④ | 「派生预览：平台将写入的接收人」 | `:672-720` | 只读 + 每渠道 YAML 片段 |
| ⑤ | 配置版本历史（表格） | `:722-744` | 「重新挂载」是主要操作之一 |

### 6.2 三个结构性问题

**问题一：主操作与能力分层倒置。**
「挂载新配置」是 `type="primary"` 页头按钮，但议题一的三层模型里它是**第三层**（逃生舱）。而第一层（预置）在页面上完全不可见——用户打开页面看到的是「请上传文件」，而不是「平台已为你准备好基础配置」。

**问题二：策略控件被埋进版本元数据卡，且两个控件语义关系未被显式化。**
「默认兜底接收人」（Select）与「路由规则作者模式」（Switch）被平铺为两个并列控件（`:553-585`），但它们在模型上**不是平级关系**（详见 §6.3）。UI 未表达这层关系 → 用户只能读 `:609-614` 那段三行诚实口径才能理解。

**问题三：术语全实现视角，且 YAML 全文散落四处。**
「派生预览」「兜底」「作者模式」「必写/豁免」「收敛（告警抑制）」「route / routes」——同时散落：折叠栏骨架、完整配置、派生预览片段、插入示例。全文出现 4 处 YAML，用户无法判断哪一处才是「现在生效的那份」。

### 6.3 关键证据：手写模式下，平台**仍然**会改文件

这是本议题最重要的发现，也是「两个控件不该平级」的实证：

| 工序 | 门禁条件 | 是否受 mode约束 | 证据 |
|---|---|---|---|
| 根兜底接管（#31） | `in.Enabled && in.DefaultReceiver != ""` | **❌ 不受** | `notify_route_skeleton.go:79`；`draft/service.go:319-321` 亦只判`DefaultReceiverChannelID == nil`，`EffectiveDefaultReceiver`（`alertmanager_route_setting.go:54-64`）同样不判 mode |
| 完整预置示例（#33） | `setting.Mode == managed` | ✅ 受约束 | `draft/service.go:385` |

**结论**：手写模式 ≠ 平台完全零写入。用户选定了「默认兜底接收人」后，**即便手写模式，平台每次生成配置仍会替换根 `route.receiver` 单键**（这正是决策 113 口径 C 的设计意图：手写模式下骨架经平台拥有片段注入）。而 UI 上唯一的提示只是 `:565` 一个 `平台接管中` 绿 Tag。

⇒ 因此「默认兜底接收人」**不是**「版本元数据」，**也不是**「路由模式的下游项」，而是**独立于模式之外的第三个开关**。这是 UI 误呈为平级两项的根因，也是模式控件不应是 Switch（而应是显式二选一）的根因。

### 7.4 「写配置前必读」不删除，改为条件化（P7 护栏）

全仓核对结论：抑制规则**无独立 UI**。`ui-custom/web/src/` 下 `inhibit` 仅命中 `types/alertmanager.ts:180,186,200`（通知状态四态 `inhibited`），**无任何抑制规则配置页**。故该折叠区**不得整体删除**：

| 模式 | 折叠区内容 |
|---|---|

## 8. 破除用户心智模型的三条误设

1. **模板不进文件（P3）**：三层模型把「模板」与「路由/渠道」并列。实际上模板存 DB、由桥渲染，**改模板不会派生/挂载任何 `alertmanager.yml` 段**。真正映射到文件的只有「渠道（→ receivers）」和「路由（→ route）」；模板是**动线卡上的平行入口**。
2. **预置是全局单例（P4）**：「标准模板库」不是每网域一份，而是中心 Alertmanager 的**一份全局预置**；v0.4+ 边缘按域分派时再谈按域覆盖。**并据此否决 §7.1 方案 B（全局设置）**。
3. **手写 ≠ 平台零写入（§6.3）**：手写模式下平台仍会替换根 `route.receiver` 单键（决策 113口径 C 的设计意图）。这是 UI 必须显式化的**第三条**语义，不是一条边角说明。

### 12A.1 关键判据：为什么是「列」而不是「再搬一个面板」

「平台自动生成的接收人」的数据源是 `getReceiverSnippet(channelId)`，与本页**行内「接收人配置」抽屉完全同源**
（`ReceiverSnippetDrawer.tsx:55`）。若原样搬一个只读面板过来，同一页就出现两份同一个接口的结果——从「跨页同源」
升级为「页内同源」。故改为表格列：

- **列内只给结论**：接收人名（`Text code`）+ 模板绑定 + 可用性 tag；
- **片段 YAML 与复制仍只由抽屉承载**（单一来源），抽屉本身就是列的下钻；
- 停用渠道显示「停用后不再生成」（`useDerivedReceivers` 只取 `enabled`，口径一致）。

### 12A.2 文案去重原则：每个事实只在一处说

| 事实 | 原先说了 N 次的地方 | 去重后唯一落点 |
|---|---|---|
| 路由规则由谁维护 | 策略卡 + `policySummary` + 手写说明引导句 | 策略卡 / `policySummary` |
| 已启用渠道的接收人由平台自动写入 | 手写说明引导句 + 接收人块 desc + 骨架注释 + 抽屉说明 + 渠道页页头 | 手写说明引导句（渠道页另有一次在说明区，**分属两页**可接受） |
| 抑制规则平台已为边缘站点离线场景生成 | 抑制块 desc + 托管模式引导句 | 托管模式引导句 |
| 「请用下方的手写说明」（自指） | 托管模式引导句 | 删除（它就写在手写说明内部） |

例外容留：可被**单独复制/单独打开**的制品必须自解释——`ALERTMANAGER_MIN_SKELETON` 的 YAML 注释、
`AlertConfigDrawer` 的骨架说明、`ReceiverSnippetDrawer` 的副标题，这三处的重复是**有意的**。

### 12A.3 `PageIntro` 组件契约（`ui-custom/web/src/components/PageIntro.tsx`）

统一样式：标题（`Typography.Title level={4}`）+ 一行副标（只做定位，不解释机制）+ 右侧 `extra` 操作位

2. 每条 `points` 只说一个事实，跨页重复的事实只在本页说一次（其余页链过来）；

### 12.1 落地过程中的两处实现修正（超出原提案，属实现缺陷修复）

1. **嵌套 Collapse 的点击冒泡**：高级区（外层 `Collapse`）内嵌了「手写配置说明 / 平台自动生成的接收人」两个内层 `Collapse`。
   antd `Collapse` 的 header 是 `role="button"` 的容器，点击内层标题会冒泡到外层 header → **整个高级区被收起**，表现为「点开内层后内容立刻消失」。
   修法：在**内层 `Collapse` 之外**加一层 `<div onClick={stopPropagation}>` 包裹。
   ⚠️ 不可把 `stopPropagation` 挂在内层 `label` 上——那会连内层自己的 header 事件一起拦掉，导致内层永远展不开（本轮实际踩过）。
2. **「配置版本历史」曾被误放进「平台自动生成的接收人」折叠面板内**（收窄折叠层时顺带挪错了父级）。
   版本历史与「平台自动生成的接收人」无关，已提回为高级区的直接子项。
