### 1.2 告警处理全链路（问题定位的总框架）

整条告警链路由**四段连续能力**构成，三个问题的落点分别在不同段：

| 段 | 能力 | 回答的问题 | 产物 / 载体 | 当前归属与状态 |
|----|------|-----------|-------------|----------------|
| 1 | 采集策略 | 抓什么 | `prometheus.yml` / scrape jobs | M01，已实现 |
| 2 | **规则求值** | **什么算异常** | `rules.yml`（expr / for / labels / annotations） | M01 规则编辑，已实现 → **Q1 争议点** |
| 3 | **路由收敛** | **发给谁、怎么聚合、怎么降噪** | `alertmanager.yml`（receivers / route / inhibit_rules） | M08，已实现 → **Q2 澄清点** |
| 4 | **通知渲染** | **通知长什么样** | webhook 渲染模板（飞书卡片 JSON 等） | **无产品化载体** → **Q3 缺口** |

> 第 4 段是 Alertmanager 的**天然空白**：AM 原生只吐通用告警 JSON，飞书/钉钉/企业微信机器人要的是各自的卡片 JSON，官方无 `feishu_configs` / `dingtalk_configs` 接收器类型，社区惯例是接一个 PrometheusAlert 中转——用户自建脚本正是在补这一段。

| 环节 | 脚本做法 | 平台化后可收敛的问题 |
|------|----------|----------------------|
| 接收 | HTTP Server 监听 `:18081`，收 AM `webhook_configs` 投递的告警 JSON | — |
| 渲染 | 硬编码字段（`alertname`/`instance`/`zone`/`severity`/`summary`/`description`）拼飞书 `interactive` 卡片 | 字段与卡片结构写死在代码里，改样式必须改代码、无法审计 |

| 可观测 | 仅 stdout print 计数，无留痕、无版本、无审计 | 发送成功/失败不可查、无变更留痕 |

### 1.4 关键判断（方案取舍）

| 判断 | 结论 |
|------|------|
| 用户自造脚本说明什么 | PRD 把第 4 段（通知渲染）排到 v1.0，形成**真实真空**——这是最容易出工、最该先补的一环，而非可延后的锦上添花 |
| 是否做「托管用户脚本的沙箱平台」 | **不做**。沙箱执行任意代码 = 安全 / 生命周期 / 可观测 / 升级四个无底洞，ROI 极低；且与「未来 AI 写配置、UI 仅辅助」的产品方向**背道而驰**（AI 擅长产出可校验的标准文本，不是丢进沙箱跑的任意脚本） |
| 正确抽象 | 把「渲染」收编为**可校验、可留痕、可版本化**的标准**模板**，由平台内置一个**通知渠道桥**端点承载渲染与转投；用户从「写脚本」降级为「写/选模板」 |

## 3. 详细设计

### 3.1 PL-1：规则编辑归组（Q1）

#### 3.1.1 判断：归属不迁移，只修心智

`MonitoringRule`（expr / for / labels / annotations）的本质是**判据定义**——回答「什么是异常」。它的创作上下文全部锚在 M01：

- expr 引用的指标来自采集 Job，PromQL 校验、指标预览、默认采集配置联动**全部依赖 M01 的指标库与监控对象类型**；
- 技术链路上，`rules.yml` 与 `prometheus.yml` 是**同一个 Prometheus 进程的两份配置**，统一由 M09 按域生成下发（M01 = 内容 Owner，M09 = 管道 Owner）。

把规则编辑物理搬进 M08，会让 M08 反向依赖指标库 / Job / 资源清单并重构 `rules.yml` 下发管线——**该绕的都绕不开，还会破坏 M08「只处理告警产生之后」的聚焦**。

**chenrt 补充的更强理由（2026-09-28）**：**指标库（MetricLibrary）在 M01「采集策略」下**。规则编辑的核心上下文——「有哪些指标可选、指标属于哪个监控对象类型、PromQL 校验的指标存在性」——全部依赖指标库。若把规则编辑整体迁到 M08，**指标库要么跟着搬（则 M08 反向吞掉 M01 半个模块），要么留在 M01（则规则编辑与指标库跨模块割裂、用户写规则时查不到指标）**。两者都不可接受。

> 结论：**分界线是「判据域（M01）vs 处置域（M08）」**。用户的困惑是**找不到**，不是**放错了**。因此只做信息架构收敛，**不动代码归属、不动导航归属**。

#### 3.1.2 动作 ①：告警工作台「去写规则」联动入口

| 落点 | 内容 |
|------|------|
| 告警状态页（`/alert-status`）空态 | 当「Prometheus 当前触发告警」为空时，空态引导补一条「还没有告警规则？去写规则 →」（跳 `/rules`），与 M09 生成巡检的空态引导同构 |
| 告警配置页（`/alert-config`） | 配置说明卡内加一条指向 `/rules` 的说明链接：「告警规则（什么情况下告警）在『规则编辑』维护，本页只管『告警发给谁、怎么收敛』」 |
| 历史告警页（`/alert-history`）空态 | 同上，复用同一引导组件 |

实现落点：[RulesPage.tsx](file:///Users/chenrt/S-03Python/03%20AIopsAgent-study/CNCF_Monitor-worktree/ui-custom/web/src/pages/strategy/RulesPage.tsx) 路由不变；仅在 M08 三个页面新增跨模块链接，**不新增接口**。

#### 3.1.3 动作 ②：导航归属——**已决定不做迁移**（chenrt 2026-09-28）

原评估的三个方案及结论：

| 方案 | 做法 | 判定 |
|------|------|------|
| 甲 | `/rules` 迁移到「告警收敛与通知管理」模块下，移除「采集策略」入口 | **否决**。会切断规则编辑与**指标库**（在 M01 采集策略下）的同域上下文：用户写规则时需要查指标库，二者一旦分处不同一级模块，动线断裂 |
| 乙 | 双入口保留 | **否决**。同一路由两个入口，高亮归属与用户预期易混 |
| **丙** | **导航完全不动，只做动作 ①（联动入口）** | **✅ 采纳** |

> **决定**：「规则编辑」**保持在「采集策略」一级模块下**，路由 `/rules`、页面文件、M01 后端接口、`MonitoringRule` 归属**全部零变更**。跨模块的"找不到"问题由 §3.1.2 的联动入口解决，不通过移动导航位置解决。

#### 3.1.4 动作 ③：命名议题（待定，附替代建议）

chenrt 提出：是否把「规则编辑」改名为「**告警采集规则编辑**」，以使告警用户更易发现。

**提案方评估：不建议该命名**，理由三条：

| # | 问题 | 说明 |
|---|------|------|
| 1 | **语义越界** | **规则不是"采集"的**——采集 = 抓指标（scrape），规则 = 对指标做求值判断。名字里嵌入"采集"会把**采集域与判据域搅在一起**，恰好破坏 §3.1.1 要守住的边界，反而加重混淆 |
| 2 | **漏掉记录规则** | `MonitoringRule` 同时承载**告警规则**与**记录规则**（记录规则的 labels 只是新时间序列的附加维度，**不参与告警路由**）。叫"告警…"会让记录规则用户找不到入口，属功能覆盖缺口 |
| 3 | **收益已被动作 ① 覆盖** | 既然导航不动、由 M08 工作台的「去写规则」联动入口解决发现性问题，此时再引入一个带歧义的新名字，等于**用新的歧义换旧的不便** |

**替代建议（二选一，待 chenrt 裁决）**：

- **建议 A（推荐，零成本）**：**保持「规则编辑」**，仅在菜单项补**副标题/标签**「含告警规则、记录规则」，并在规则编辑页顶部增加一句定位文案——信息量增加、歧义不增加。
- **建议 B**：改名为「**监控规则**」（覆盖告警 + 记录两类，且隐含"规则属于监控策略域"），比"告警采集规则编辑"更准、更短。
- ~~「告警采集规则编辑」~~：不建议（见上表）。
- ~~「告警规则」~~：可用，但会把记录规则弱化为"附带能力"，需接受该取舍。

### 3.2 PL-2：告警配置口径澄清（Q2）

#### 3.2.1 「告警配置」是什么

`alertmanager.yml` 的产品化定义：**「告警分派与收敛引擎」的配置**。它决定「**谁收到、怎么聚合、如何静默抑制**」，但**不含「通知长什么样」**（第 4 段由 PL-3 承载）。

#### 3.2.2 用户当前在「告警配置」页需要写什么（本提案要显式化的口径）

**需要用户写的三块**：

| # | 块 | `alertmanager.yml` 字段 | 回答 | 备注 |
|---|----|------------------------|------|------|
| 1 | **接收人 / 渠道** | `receivers` | 告警发给**哪个端**（飞书群机器人、钉钉群、邮件组……） | MVP 经 webhook URL 承载；**建议指向 PL-3 平台内置端点**（见 §3.3.5） |
| 2 | **路由** | `route` / `routes` | 按什么标签**分发给谁**、怎么**分组**、多久**重复** | 支持 `severity` / `team` / `network_domain` 匹配、`group_by` / `group_wait` / `group_interval` / `repeat_interval` |
| 3 | **收敛（告警抑制）** | `inhibit_rules` | 根因告警存在时**自动抑制次生告警**，降噪 | 平台对网域离线场景**已自动生成**（`EdgeSiteOffline` → `inhibitable=true`），用户只需按需增补 |

**不需要用户写的两块（明确豁免）**：

| # | 块 | 为什么不用写 |
|---|----|--------------|
| 4 | **静默（silences）** | **平台已实现**——静默是 Alertmanager 运行时 API 状态，M08 已提供创建/列表/删除 UI（v2 API 直调即时生效），文件挂载本来就承载不了 |
| 5 | **通知模板内容（templates）** | 由 **PL-3「通知模板」** 独立承载并经平台生成引用，用户不再手写模板文件（见 §3.3.5） |

**`global` 段**：MVP 阶段只需最简（如 `resolve_timeout`）；仅当使用**邮件**渠道时才需 `smtp_smarthost` 等。属「按需最简」，不列为必写块。

### 3.3 PL-3：通知渲染桥（Q3，核心）

#### 3.3.1 链路定位

```
M01 规则编辑              M08 告警配置                M08 通知模板 + 渠道桥
（severity/labels/        （route 决定发给谁、        （平台内置端点按模板
  annotations）      →     抑制决定降不降噪）     →     渲染成飞书卡片并转投）
        ↓                        ↓                          ↓
   rules.yml            alertmanager.yml            /api/v1/webhooks/notify
```

三者是**一条双向契约链**：

- M01 决定「**告警携带哪些信息**」——脚本能渲染出的所有字段（`summary`/`description`/`severity`/`instance`…）都来自规则里定义的 annotation / label；
- M08 告警配置决定「**发给谁**」——receiver 的 `webhook_configs.url`；
- **通知模板决定「这些信息怎么呈现」**——本提案新增的载体。

#### 3.3.2 数据模型（新增）

**NotifyChannel（通知渠道）**

| 字段 | 类型 | 必填 | UI 展示名 | 说明 |
|------|------|------|-----------|------|
| id | string | 必填 | 渠道 ID | 平台内唯一标识；**AM 侧只引用 ID，不暴露目标地址** |
| name | string | 必填 | 渠道名称 | 如「SRE 飞书群」「数据库团队群」 |
| type | enum | 必填 | 渠道类型 | `feishu` / `dingtalk` / `wecom` |
| webhook_url | string | 必填 | 机器人 Webhook | 目标机器人地址（含 token）；**仅在平台侧存储** |
| secret | string | 选填 | 签名密钥 | 钉钉/飞书加签密钥（启用加签时必填） |
| enabled | bool | 选填 | 启用状态 | 是否启用 |

**NotifyTemplate（通知模板，版本化留痕）**

| 字段 | 类型 | 必填 | UI 展示名 | 说明 |
|------|------|------|-----------|------|
| id | string | 必填 | 模板 ID | 唯一标识 |
| name | string | 必填 | 模板名称 | 如「飞书卡片-默认」 |
| channel_type | enum | 必填 | 适用渠道类型 | 与渠道类型匹配后才可组合 |
| content | text | 必填 | 模板内容 | **Alertmanager 标准 Go template** 文本（不是脚本） |
| is_builtin | bool | 选填 | 内置模板 | 平台内置默认模板（随版本升级） |
| checksum | string | 选填 | 校验和 | `sha256`（复用 `AlertmanagerConfigChecksum` 口径） |
| status | enum | 选填 | 状态 | 仅 `applied`（照抄决策 59/60「校验失败不落库」纪律） |

> **与 `AlertmanagerConfigVersion` 的纪律一致**：模板先校验、通过才落库留痕，失败只回行级错误、不落库；版本历史支持回看与回滚。

#### 3.3.3 内置渲染端点

| 项 | 设计 |
|----|------|
| 端点 | `POST /api/v1/webhooks/notify` |
| 调用方 | 中心 Alertmanager（同机部署，`http://127.0.0.1:8080/api/v1/webhooks/notify`） |
| 入参 | ① AM 原生 webhook JSON body（`{version, groupKey, status, alerts[], groupLabels, commonLabels, commonAnnotations, externalURL}`）；② 定址参数 `channel`（NotifyChannel ID）+ `template`（NotifyTemplate ID，省略则用渠道类型的内置默认模板） |
| 处理 | 解码 AM 告警 → 按模板渲染 → 组目标渠道卡片 JSON → POST 到 `channel.webhook_url`（加签时带签名字段）→ 返回 `{success, fail}` |
| 鉴权 | 内网调用令牌（`env/env.sh` 注入，随 `alertmanager.yml` 生成时写入 URL）；未带令牌直接 401 |
| 幂等 | 端点为无状态渲染转发，不落告警业务表；仅记发送结果日志（供可观测） |

**关键安全设计——ID 定向，杜绝 SSRF**：

> 与用户脚本 `?fsurl=<任意地址>` 的**开放中继**做法不同，本端点**只接受平台内已登记的 `channel` ID**，目标地址由服务端从 DB 解析。任何情况下都**不接受请求方传入的目标 URL**——这一条直接消除了用户脚本中「任何能访问该端口的人都能让它向任意地址 POST」的隐患（对齐 AGENTS.md §9 的 SSRF 防护要求）。

#### 3.3.4 模板形态：Go template，不是脚本

- 用户粘贴的是 **Alertmanager 标准 Go template**（如 `{{ define "feishu.card" }}…{{ end }}`），与 AM 官方 `templates` 机制同源；
- **校验**：`amtool check-config` 等价校验（含模板解析）——与现有 `alertmanager.yml` 校验工序**复用同一套**（[validate.go](file:///Users/chenrt/S-03Python/03%20AIopsAgent-study/CNCF_Monitor-worktree/platform/alertmanager/config/validate.go)）；
- **AI 友好**：AI 擅长产出可校验的标准模板文本，天然可留痕、可 diff、可版本化——与「未来 AI 写配置、UI 辅助」的产品方向一致；
- **平台内置默认模板**：至少内置「飞书卡片-默认」（对齐用户脚本当前的字段与红绿配色语义：`status` 决定 header 模板色、含 `alertname`/`instance`/`zone`/`severity`/`summary`/`description`/开始与恢复时间），用户零模板即可完成接入。

#### 3.3.5 与 `alertmanager.yml` 的接线

平台在生成 / 校验 `alertmanager.yml` 时：

1. receiver 的 webhook 指向平台桥并携带 ID：

```yaml
receivers:
  - name: 'sre-critical'
    webhook_configs:
      - url: 'http://127.0.0.1:8080/api/v1/webhooks/notify?channel=ch-feishu-sre&template=tpl-feishu-default&token=xxx'
        send_resolved: true
```

2. 若用户使用自定义模板文件语义，平台在 `alertmanager.yml` 的 `templates:` 段生成对平台托管路径的引用（用户不再手写模板文件）；
3. `edge`（v0.4+）场景的本地 AM 引用 **edge 侧登记的渠道 ID**（后续版本，本提案不实现）。

#### 3.3.6 平台内置收编的「通用坑」

| 脚本里的坑 | 平台内置处理 |
|-----------|-------------|
| UTC → 东八区固定偏移硬编码 | 平台统一时区渲染（可配置显示时区），模板内提供已本地化的时间字段 |
| 依赖 `certifi` 兜底系统 CA 库缺失 | 平台 HTTP 客户端统一 CA 配置，出站 HTTPS 一处收敛 |
| 发送失败只 print、不可查 | 发送结果结构化日志（渠道 / 模板 / 成功失败 / 失败原因），可在 M08 侧查看 |
| 字段与卡片结构写死 | 模板可改、可留痕、可回滚；默认模板覆盖主流动线 |

#### 3.3.7 逃生门（明确不托管）

对确有高级定制需求的用户：receiver 的 `webhook_configs.url` **始终可以直接填外部地址**（用户自有的 PrometheusAlert / 自建脚本）。平台只负责**配置与校验**，**不承诺托管运行、不承诺其可用性**。

> 责任边界：平台保证「自己生成的分派配置合法可校验」；外接中继的可用性归用户。这是对 ROI 最诚实的态度——能力开放、边界明确。

#### 3.3.8 需要 NEW 的接口契约汇总

| 端点 | 方法 | 说明 | 鉴权 |
|------|------|------|------|
| `/api/v2/platform/alertmanager/notify-channels` | GET / POST | 通知渠道列表 / 创建 | 认证 |
| `/api/v2/platform/alertmanager/notify-channels/{id}` | PUT / DELETE | 通知渠道更新 / 删除 | 认证 |
| `/api/v2/platform/alertmanager/notify-templates` | GET / POST | 通知模板列表 / 提交（校验通过才落库） | 认证 |
| `/api/v2/platform/alertmanager/notify-templates/{id}/remount` | POST | 模板回滚（重新提交历史版本） | 认证 |
| `/api/v1/webhooks/notify` | POST | **平台内置渲染桥**（AM 调用，不入认证态） | 内网令牌 |
