## 0. 给产品经理的一页摘要（先读这段）

**今天的问题，一句话**：告警从「触发」到「发到你的飞书」，中间有一步叫「路由」——决定**这条告警该发给谁、按什么条件分、怎么攒一批一起发、多久重发一次**。这一步在今天的产品里**没有界面**，只能打开 `alertmanager.yml` 手写。而它恰恰是**最需要调、最容易写错**的一步。

**我们要做的三件事**：

1. **看得懂** —— 把文件里的路由配成一张**树**，一眼看出「critical 的告警走哪条、为什么这条排在上面」。
2. **改得动** —— 用表单改：**分给谁**（接收人下拉）、**按什么条件分**（标签匹配器）、**怎么分组**（分组键）、**多久发一次**（三个时间）。不用碰 YAML。
3. **不打架** —— 解决「平台自动填的」和「你手写的」在同一份文件里**互相覆盖 / 互相误判**的问题（这正是现场变更单校验失败的根因）。

**关键取舍（最重要的一条）**：Alertmanager 的路由是一棵**有序的树**——「先匹配到的先生效」。**一棵有序的树不适合两个作者各写一半**。所以我们推荐的边界策略不是「平台写一半、你写一半」，而是：

> **`route` 整段只有一个作者，二选一**：要么你继续手写（逃生门，保持现状），要么交给平台表单管理（界面里点一下切换，首次切换会把你现在手写的路由**导入成表单初始值**）。
> `receivers` 段则是**天然的双作者**（平台写平台自己的接收人槽位、你写你自己的），靠命名空间区分——这一条第一步（L2）已在做。

**已拍板的 4 件事（2026-09-30 经 chenrt 确认，均取推荐项；结论见 §7.2.1）**：

| # | 待拍板 | 推荐结论 |
|---|---|---|
| P1 | route 段的默认作者 | **a. 保持手写（默认，零影响）** |
| P2 | 是否本期就做「从手写导入表单」 | **a. 做（否则存量用户迁移成本高）** |
| P3 | 兜底接收人（根路由 receiver）怎么来 | **a. 平台提供一个「默认接收人」配置项** |
| P4 | v0.3-a（只读渲染）是否与第一步止血同批上线 | **a. 同批（零风险、高感知）** |

## 1. 背景与问题

### 1.1 告警在这条链路上「断」在哪

一条告警从产生到送达，链路是：

```
M01 规则求值（Prometheus / vmalert）
      ↓  产生告警（带标签：severity / network_domain / resource_id …）
M08 Alertmanager route   ← ★ 本次要前台化的那一步
      ↓  按标签匹配 → 选接收人 → 分组 → 定时
M08 receiver（平台通知渲染桥）
      ↓  渲染成飞书卡片 / 钉钉 / 邮件
飞书 / 钉钉 / 邮件
```

- 上游（规则内容、表达式、标签）由 **M01** 前台化；
- 下游（接收人定义、通知模板、渲染桥）由 **M08 PL-3** 前台化（已落地）；
- **中间这一步 route，是全链路上唯一还得打开 YAML 手写的环节。**

### 1.2 三个用户可感知的痛点

| # | 痛点（用户语言） | 现场证据 |
|---|---|---|
| 1 | **「我不知道该写什么」** | 平台自动生成了接收人（`notify-1`），但它**没有任何路由指向**→ 从不投递；用户不知道「还差一步」。见 dev-feedback #26。 |
| 2 | **「我改完不知道谁生效了」** | 手写路由与平台生成的接收人混在一份文件里，平台**认不出哪条是自己的产物**→ 把自己上次写的说成「你手写的重名」。见 M09 F-36。 |
| 3 | **「顺序错了，但文件里看不出来」** | 路由是**有序树，先匹配先生效**。线上文件里用户自己写了长段注释告诫：「本条必须排在 `severity="critical"` 之前，否则会被 critical 路由吃掉（1h 一次），10s 设置失效」。**顺序语义只能靠注释传承**——这就是缺 UI 的直接代价。 |

### 1.4 为什么是现在

1. **上行已通、下行已通，只剩中间**：M01 规则前台化 + M08 PL-3 接收人/模板/渲染桥已落地 → 缺口唯一。
2. **原型的 IA 已经验过**：`RoutesPage.tsx` 把「路由树 + 四维字段」的信息架构画完了，**主要成本在接线（生成 YAML、校验、走变更单），不在从零设计**。
3. **第一步止血正在做**：#28 的 L1/L2/L3 会把「平台产物 vs 用户产物」的判据与文案划清；**本提案的边界策略正是 L2 判据的上位规则**——先定边界，L2 的判据才有依据（这也是 #28.3 建议「L2 等本草案定稿后一并实现」的原因）。
4. **顺序语义已经在产生真实损失**：见 1.2 痛点 3，用户只能靠注释传承顺序，且线上还存在 `group_interval: 10s` 兼作通知管道 timeout、飞书限频 100 次/分钟等**属于「调参」而非「写 YAML」的知识**，散落在注释里无法沉淀。

## 3. 信息架构：route 可视化编辑器

### 3.1 四个问题 = 一条链路的四段

设计完全围绕**用户脑子里的四个问题**组织，而不是照抄 YAML 字段：

| 用户的问题 | 对应语义 | Alertmanager 字段 | UI 位置 |
|---|---|---|---|
| **① 什么告警？** | 匹配条件 | `matchers`（列表，AND 关系） | 编辑表单第 2 段 |
| **② 发给谁？** | 接收人 | `receiver` | 编辑表单第 1 段 |
| **③ 怎么分组？** | 攒批的键 | `group_by` | 编辑表单第 3 段 |
| **④ 多久发 / 多久重复？** | 三个时间 + 是否继续匹配 | `group_wait` / `group_interval` / `repeat_interval` / `continue` | 编辑表单第 3 段 |

列表态则回答第 5 个问题：**⑤ 谁先谁后？**（顺序 + 层级）。

### 3.2 页面骨架（列表态）

入口：菜单「告警收敛与通知管理 / **路由规则**」（与「告警配置 / 静默管理」并列，作为 Sider 二级）。原型 `RoutesPage.tsx` 已按此布局，复用为主。

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 路由规则                                                                  │
│ 按告警标签决定通知到哪个接收人、如何分组、何时重复                          │
├──────────────────────────────────────────────────────────────────────────┤
│ ⓘ 路由顺序 = 生效顺序：先匹配到的先生效。拖拽或上下移动可调整。             │
│   [ 由此页面管理的路由 ]  ← 模式徽标（手写接管 / 平台管理）                │
├──────────────────────────────────────────────────────────────────────────┤
│ [＋ 新建路由规则]        [ 从当前配置导入 ]        共 5 条路由              │
├──────────────────────────────────────────────────────────────────────────┤
│  # 路由名称           匹配条件          接收人     分组键   发送节奏 继续 启用 │
│ ────────────────────────────────────────────────────────────────────────  │
│  1 📌根路由（兜底）     （所有告警）      飞书        …      30s/5m/4h  —   ● │
│  2 └─ 主机宕机专用      alertname=~"…"   飞书        …      15s/10s/10s 否  ● │
│  3 └─ P0 严重告警       severity="crit…" 飞书        …      15s/3m/1h   否  ● │
│  4 └─ P1 告警           severity="warn…" 飞书        …      30s/5m/2h   否  ● │
│  5 └─ P2 告警           severity="info"  飞书        …      30s/10m/4h  否  ● │
└──────────────────────────────────────────────────────────────────────────┘
```

**与原型的差异（必须改）**：

| 原型（`RoutesPage.tsx`） | 本草案 |
|---|---|
| 「排序」是一个数字输入框 `order` | **拖拽 / 上移下移**（顺序是本功能的第一类语义，数字框不可接受） |
| 列「启用」是 `Switch`，切换即弹「演示」 | 沿用 Switch，但**明确落盘语义**：`enabled=false` 的规则在生成 YAML 时**整条剔除**（AM 无此字段，见 §3.5） |
| 顺序靠 `order` 数字 + `Sort` | 顺序靠**数组位置**（AM 的 `routes[]` 顺序即优先级），`order` 仅作编辑态辅助 |
| 无「根路由」概念（根也当普通行） | **根路由单独置顶并锁定**（它对应 AM 的 `route:` 本体，不可删、不可移动） |

### 3.3 路由树为什么必须是「树 + 有序」

**这是本功能最重要的设计判断**，理由是 Alertmanager 的原生语义：

1. **单根**：AM 的 `route` 是**唯一一棵树**，只有一个根（`route:` 本体）。根必须有 `receiver`（兜底接收人）。
2. **有序**：子路由按 YAML 数组顺序**依次匹配**；一旦命中，是否继续匹配下一层由 `continue` 决定（**默认 `false`**，即命中即停）。
3. **因此顺序即优先级**，且是**全局**的：一条子路由往上挪一格，可能改变所有告警的走向。

线上文件的用户注释是这个判断的最好证据：

> 「位置说明：子路由 continue 默认 false，先匹配先生效。**本条必须排在 `severity="critical"` 之前**，否则会被 critical 路由吃掉（1h 一次），10s 设置失效。」

⇒ **UI 必须把「顺序」做成第一等公民**（显式展示、可直接调整、调整时有解释），否则等于把最难的语义留给了 YAML。

### 3.4 编辑态：三段式表单

新建/编辑用 **Drawer（抽屉）**，而非原型里的 Modal——理由：字段有 12 个，且要放「发送节奏」的辅助说明与预校验提示，Modal 高度不够。

```
┌─ 编辑路由规则 ─────────────────────────────────── ✕ ┐
│                                                      │
│ ① 这条规则管什么                                      │
│   路由名称  [ 主机宕机专用________________ ]           │
│   父路由    [ 根路由（兜底）            ▾ ]           │
│                                                      │
│ ② 匹配什么告警（多个条件为「且」）                     │
│   标签名        值            正则   操作              │
│   [ alertname ] [ HostDown|… ] ☑正则  🗑              │
│   [＋ 添加匹配条件]                                    │
│   ⓘ 留空 = 匹配所有告警（等同根路由的兜底行为）         │
│                                                      │
│ ③ 发给谁、怎么发                                      │
│   接收人    [ 飞书 · 腾讯云边缘域       ▾ ]  ⓘ 见下   │
│   分组键    [ instance ✕ ][ alertname ✕ ]  + 输入回车 │
│             ⓘ 留空 = 不分组（所有告警一条通知）        │
│   ┌ 发送节奏 ──────────────────────────────────┐      │
│   │ 初次等待   [ 15s ]  告警攒多久再发第一条     │      │
│   │ 分组间隔   [ 10s ]  ⚠ 必须能整除「重复间隔」│      │
│   │ 重复间隔   [ 10s ]  同一告警多久重发一次     │      │
│   └────────────────────────────────────────────┘      │
│   ☐ 继续匹配（命中后仍继续匹配下一级路由）              │
│   ● 启用                                              │
│                                                      │
│              [ 取消 ]   [ 保存并提交变更 ]             │
└──────────────────────────────────────────────────────┘
```

**关键交互规则**：

| 规则 | 说明 |
|---|---|
| 「接收人」下拉只列**已启用**接收人 | 空值不可保存（AM 要求 `receiver` 必填）；若渠道被禁用导致引用悬空，列表态标「未定义」红字（原型已有，保留） |
| 「匹配条件」支持**正则开关** | 映射到 AM 新式 matcher 的 `isRegex`；值为正则时才建议打开（UI 可做正则合法性预校验） |
| 「分组键」用 **Tags 输入** | 与 AM `group_by` 数组同构；提供标签名联想（复用 M08 §4.2.1 静默页的**四层并集键联想**能力，避免重复造） |
| **`group_interval` 整除校验** | AM 官方：`group_interval` 必须能整除 `repeat_interval`，否则**向上取整**。UI 在两者不整除时给**警告级**提示（不阻断，因为 AM 自身会兜底） |
| **`group_interval` 兼作通知管道 timeout** | AM 官方：单次发送耗时超过 `group_interval` 会被取消 → 漏发。UI 给**说明性 Tooltip**（本项目实际踩过：线上文件注释记录 `group_interval: 10s` 与飞书脚本 `timeout=10` 贴边） |
| **`continue` 默认关闭且有解释** | 用 Tooltip 写明「关闭 = 命中即停；打开 = 继续匹配下一级（可能收多条通知）」 |
| 保存动作 = **提交 M09 变更单**，不即时生效 | 与「告警配置」页同构：校验 → 落草稿 → 人工确认 → 下发 reload（决策 59/60） |

### 3.5 字段清单与控件选型（PRD §5.2 全覆盖）

> ★ = **编辑态字段，落盘时必须剔除或转换**，这是最容易出错的地方。

| PRD §5.2 字段 | UI 展示名 | 控件 | 落盘处理 |
|---|---|---|---|
| `id` | 路由 ID | 不可见 | ★ 平台内部 ID，**不落盘** |
| `parent_id` | 父路由 | Select（路由树选项） | ★ 转为 YAML **嵌套位置**（`routes:` 下的层级），不落盘 |
| `name` | 路由名称 | Input | ★ **不落盘**（AM 无 name 字段）→ **用注释落盘**：`# 路由名称: 主机宕机专用` 置于该节点上方，保住可读性 |
| `matchers` | 匹配条件 | Form.List（标签名 / 值 / 正则）+ 标签联想 | 落盘为 AM 0.34 新式：`matchers: [ {name, value, isRegex} ]` 或字符串简写 `- severity="critical"` |
| `receiver_id` | 接收人 | Select（仅已启用） | 落盘为 `receiver: '<name>'`（取 `ReceiverName()`） |
| `group_by` | 分组键 | Select Tags | 落盘 `group_by: [...]`；留空则不输出该键 |
| `group_wait` | 初次等待 | Input（时长）+ 常用值快选 | 直落 |
| `group_interval` | 分组间隔 | Input（时长）+ 整除校验 + Tooltip | 直落 |
| `repeat_interval` | 重复间隔 | Input（时长） | 直落 |
| `continue` | 继续匹配 | Switch | 直落（`true` 才输出，避免噪音） |
| `order` | 排序 | **拖拽**（列表态） | ★ 不落盘；由数组位置表达 |
| `enabled` | 启用 | Switch | ★ **不落盘**——`false` 的规则生成时**整条剔除**（含其子树） |

**落盘产物示例**（平台管理模式下，由上面那张列表生成）：

```yaml

  group_wait: 30s

  repeat_interval: 4h

    # 路由名称: 主机宕机专用

        - alertname=~"HostDown|NodeExporterDown"

      group_wait: 15s
      group_interval: 10s
      repeat_interval: 10s
    # 路由名称: P0 严重告警

        - severity="critical"
      receiver: 'feishu'
      group_wait: 15s
      group_interval: 3m
      repeat_interval: 1h
```

> **注意**：上面的输出与线上现网文件（`config-output/alertmanager.yml:71-100`）**结构逐字一致**——因为列表态就是照着它做的。这为「导入」能力（P2）提供了可行性证明：**解析现有 route 段 → 填表 → 再生成**是往返无损的（`name` 通过注释还原）。

## 4. 与手写 YAML 的边界策略（核心章节）

### 4.1 问题本质：一份文件，两个作者

`alertmanager.yml` 是**一份文件**，但今天有**两个作者**：

| 作者 | 写什么 | 怎么认自己的东西 |
|---|---|---|
| **平台** | `receivers:` 里为每个启用渠道追加一个 receiver | 靠「**名字 + URL 全等**」——**URL 一变就认不出**（M09 F-36 根因） |
| **用户** | 手写 `route:` 整棵 + 自有 `receivers:` | 无标记，全靠人脑记 |

三个后果（即 §1.2 三个痛点）：认不出 → 误报重名；不知道归属 → 以为不用写 route；顺序无载体 → 靠注释传承。

### 4.2 三个候选策略与对比

| | **A 只读镜像** | **B route 段单一作者 + 模式开关**（推荐） | **C 分区受管（平台子树 + 用户子树并存）** |
|---|---|---|---|
| **做法** | 前台只**读**文件里的 route，渲染成只读树；编辑仍走文件挂载 | route 段**只有一个作者**：要么用户全手写，要么平台全生成；界面提供切换 | 平台生成「平台管辖的子树」，用户手写其余；用注释锚点划界 |
| **解决痛点 1（看不懂）** | ✅ 解决 | ✅ 解决 | ✅ 解决 |
| **解决痛点 2（改不动）** | ❌ 不解决（还是手写） | ✅ 解决 | ✅ 解决 |
| **解决痛点 3（顺序）** | ⚠️ 只能展示，不能调 | ✅ 可调 | ❌ **反而更糟**（两个作者 + 一棵有序树） |
| **实现成本** | 低（解析 + 渲染） | 中（表单 + 生成 + 导入 + 模式开关） | **高**（合并算法 + 冲突仲裁 + 顺序仲裁） |
| **用户心智** | 简单 | 简单（「这段归谁管」一句话说清） | **复杂**（「为什么我的规则不生效」会成为常客） |
| **风险** | 治标不治本 | 迁移期需要「导入」向导 | Alertmanager **有序单根**语义与「分区」根本冲突 |

> **为什么 C 被否**：Alertmanager 的 route 是**有序、单根、语义全局**的结构。`continue: false` 时「先匹配先生效」意味着**一条子路由的位置由它所有兄弟共同决定**。两个作者各写一半时，**谁排在谁前面**无法用「分区」表达——用户加一条规则可能悄悄改变平台规则的优先级，反之亦然。YAML 层面能拼出来，**用户心智层面拼不出来**。

### 4.3 推荐：route 段「单一作者 + 模式开关」

**核心约定**：

```
                 ┌──────────────────────────────────────────────┐
alertmanager.yml │                                              │
                 │  global:   …………… 平台生成（现状不变）         │
                 │                                              │
                 │  route:    ★ 单一作者，二选一                 │
                 │     ├─ 手写模式（默认）：文件挂载写，UI 只读   │
                 │     └─ 平台模式：表单编辑，平台生成整棵        │
                 │                                              │
                 │  receivers: ◆ 天然双作者（靠命名空间区分）     │
                 │     ├─ 平台槽位：name ∈ 平台 ReceiverName 集合 │
                 │     └─ 用户自有：其余                          │
                 │                                              │
                 │  inhibit_rules: ……… 平台自动生成（现状不变）   │
                 └──────────────────────────────────────────────┘
```

- **模式开关**落点为「**告警配置**」页（该页已是文件挂载与版本历史的落点）：一个显式开关「**路由规则由平台管理**」。
  - **默认关闭**（=保持今天的行为，对存量用户零影响）。
  - 打开时弹二次确认，说明「此后路由规则在『路由规则』页用表单管理；你原来手写的 route 段将被接管，可随时切回」。
  - 打开后**首次进入**「路由规则」页时，若检测到文件里已有手写 route，提供「**从当前配置导入**」按钮，一键解析成表单初始值（可行性见 §3.5 的往返无损论证）。
  - **随时可切回手写**：关闭开关 → 平台把最后一次生成的 route 段**原样留在文件里**（不删除），用户从此可自由手写；**已生成的内容不丢**。

### 4.4 权威规则表（建议同步进契约快照 §11.6）

| 段 | 作者 | 平台行为 | 用户行为 | 冲突处理 |
|---|---|---|---|---|
| `global` | 平台 | 生成 | 只读 | 用户手改 → 平台下次生成覆盖（**仅限平台拥有的键**） |
| `route` | **单一作者** | 平台模式：整棵生成<br>手写模式：不触碰 | 手写模式：整棵手写<br>平台模式：只读 | 由模式决定，**不存在同时写** |
| `receivers` | **双作者** | 追加/更新**平台槽位**（name ∈ 平台 `ReceiverName()` 集合） | 手写自有 receiver | 平台槽位：**原地更新**（地址演进不算冲突，= L2）；**非平台槽位同名 → 报错，绝不静默覆盖**（决策 74 语义不变） |
| `inhibit_rules` | 平台 | 自动生成（网域离线场景） | 可手写追加 | 现状不变 |
| `templates` / `mute_time_intervals` | 用户 | 不触碰 | 手写 | — |

**关键性质**：这张表把「**平台自动填的**」和「**你手写的**」从「靠 URL 猜」升级为「**靠规则判定**」：`route` 靠**模式**判定，`receivers` 靠**命名空间**判定。两者都不再依赖易变的 URL。（L2 就是 `receivers` 这一列的实现。）`route` 的「根兜底 receiver」可由平台骨架注入（见 §4.9），不改变「单一作者」判定。

### 4.5 冲突与异常处理规则

| 场景 | 判定 | 用户看到 |
|---|---|---|
| 平台模式 + `route` 段被外部改动（如有人直接用文件挂载覆盖） | 下次生成时**以表单为准**，但**不静默** | 变更单变更项里明示「route 段被平台重建」，并在告警配置页提示「文件曾被外部修改」 |
| 平台模式 + 用户手写 receiver 与平台槽位**同名**，且 URL **不是**平台桥地址形态 | **真重名** | `failed + user_config` + 行级错误（现有行为，保持不变） |
| 平台模式 + 平台槽位 URL 变了（桥地址演进） | **不是冲突** | 变更项写「平台接收人地址更新」（= L2 目标行为，**不再误报重名**） |
| 表单里选了已被禁用的接收人 | 悬空引用 | 列表态标「未定义」（红字），保存时阻断并提示先启用或换一个 |
| 删除一条有子路由的规则 | 级联 | 二次确认明示「将同时删除 N 条子路由」 |
| 手写模式下切 UI 编辑 | 不允许 | 「路由规则」页顶部模式徽标提示「当前为手写管理，如需在此编辑请先在『告警配置』开启平台管理」 |

### 4.6 产物流转：仍走 M09 变更确认，不改管道

- 保存 = `POST` 一份**新版本的 alertmanager.yml 内容**（route 段由表单生成，receivers 段由平台物化 + 用户手写合并）。
- 之后**完全复用** M08 已有链路：`amtool check-config` 校验 → 落 `AlertmanagerConfigVersion` → 触发 M09 变更检测 → `ConfigDraft` → **人工确认** → M09 写盘 + AM reload。
- **好处**：本次前台化**零管道改动**，风险集中在「表单 → YAML 生成器」这一处纯函数，可单测锁定。
- 与「告警配置」页的关系：**两者操作同一份内容**，因此「路由规则」页保存后，告警配置页的版本历史会多一条记录——语义自洽。

### 4.7 与第一步 / 第三步的衔接

| 步骤 | 关系 |
|---|---|
| **第一步 · 止血（#28）** | **L1**（桥地址持久化）与本提案无关但为其前提之一（地址稳定才好比对）；**L3**（明确 route 由用户写）是**过渡态文案**，本提案落地后应改写为「route 可由用户手写，也可交给平台管理」；**L2**（物化判据认命名空间）**应在本草案定稿后实现**——因为 §4.4 正是 L2 判据的上位规则。 |
| **第三步 · v0.3+（#26 备选）** | 即「平台连 route 一起物化」——**本提案的平台管理模式就是它的实现**（route 段单一作者已解决合并问题，剩下的是 receivers 的双作者，由 L2 解决）。⇒ 本提案可视为**把第三步提前到第二步做**，因为「不先解决归属，操作 UI 只是把 YAML 的坑搬到表单里」。 |

### 4.8 逃生门保留承诺

> **无论哪个版本，「整份 `alertmanager.yml` 文件挂载」入口永久保留。**

理由：告警路由是**产品的高级逃生门**（用户原话）。平台提供表单是为了覆盖 80% 的常规调整，**绝不剥夺 20% 的高级能力**。平台管理模式只是把 route 段的**默认作者**从用户换成平台，且**随时可切回**。

### 4.9 最小运行骨架自动布缆（Step 2/3 增量前置，2026-09-30 用户拍板纳入）

**问题**：第一步 L3 文案明确「route 由用户手写维护」，但平台物化的 receiver 一旦没有 route 引用就是死配置（#26）。用户每建一个渠道都要手动在 `route` 里加一条指向 `notify-<id>` 的规则，否则永远收不到告警——这正是「用了平台渠道模版却还要人手改配置文件才生效」的断裂。

**目标**：让平台托管的 receiver **开箱即响**——生成配置时自动带上一条「最小运行骨架」route，把根路由指向平台默认接收人；按级别/标签/网域的分流是 opt-in，由用户在路由页手写或开启平台模式接管，而非「不写就不响」。

**机制（与 §4.3 / §4.4 单一作者规则不冲突）**：

```
alertmanager.yml（用户手写 或 平台模式生成）
  route:
    receiver: <用户自选兜底 / 平台默认接收人>   # 根兜底
    routes:                                    # 具体分流（带 matchers），先匹配先生效
      - 用户手写的规则 …
      # 平台骨架不写进这里

── 平台拥有的片段（route_files 合并 / 平台模式生成）──
  route.receiver（根兜底）= <平台默认接收人>      # 仅当无具体匹配时回落
```

- **平台只拥有「根 `route.receiver` 兜底指针」**，且**无 `matchers`**——它只在「没有任何具体路由匹配」时生效（AM 原生语义：具体规则先匹配，否则回落根默认）。
- **用户拥有具体分流**（`route.routes[]`，带 `matchers`）。两者不构成「两个作者各写半棵」：根兜底是平台给的 floor，用户规则是 ceiling，优先级由 AM 原生语义表达，**无顺序歧义**。
- **绝不写进用户手改的根 `route:`**（否则重开 L2 类「谁拥有这个节点」歧义）。骨架落在**平台拥有片段**：
  - 平台模式：骨架 = 生成的整棵 route 树的初始态（`route: { receiver: <默认接收人> }`，用户尚未加任何 `routes[]` 时）；
  - 手写模式：经 `route_files:` 合并一个平台片段（仅含根兜底 receiver），不碰用户文件里的 `route:` 正文。

**两道护栏（否决朴素写法）**：

| 朴素写法 | 问题 | 本方案 |
|---|---|---|
| 骨架写进用户手改的根 `route:` | 重开 L2 类「谁拥有该节点」歧义；用户改 root receiver 与平台兜底打架 | 落平台拥有片段（route_files / 平台模式生成），根兜底由平台注入 |
| 仅默认模版自动布缆、自定义模版仍要手写 | 「默认渠道能响、自定义渠道哑火」且无原因可解释——UX 陷阱 | 适用维度 = **receiver 是否由平台托管**（与模版来源无关）；所有平台托管 receiver 一律给骨架 |

**L3 文案改写**（#26 / `ReceiverSnippetDrawer.tsx` / `AlertConfigPage.tsx`）：

> 旧：「平台自动写入的是 `receivers` 定义；要让通知真正生效，需在 `route`/`routes` 中把 `receiver` 指向它。」
> 新：「已为你生成**最小 route 骨架**：根路由 → `notify-<id>`（默认接收人），新建渠道开箱即响。如需按级别/标签/网域分流，请在『路由规则』页编辑（或开启平台管理）。」

> 该文案仅在该 receiver **尚无具体分流**时出现；既诚实（不制造「全自动」错觉）又低摩擦，且不掩盖「平台骨架可被你的具体规则覆盖」这一事实。

**默认接收人来源**：P3 已决——取「已启用渠道里第一个」或用户显式指定一个（在「告警配置」页补「默认接收人」选择项）；骨架的根兜底即该默认接收人。

**与 §4.4 权威规则表的关系**：§4.4 的 `route` 行「单一作者」判定**不变**。本节的「根兜底 receiver」是**平台模式生成的初始态 / 手写模式经 `route_files` 注入的 floor**，它不新增第二个 `route` 作者，只是给根兜底一个平台默认值，故不破坏单一作者规则。

#### 4.9.1 回填清单（本节落地时同步）

> **建议**：把 **v0.3-a 与第一步止血（#28）同批上线**——它零风险，且立刻把「平台 receiver 是死配置」这件事**在界面上显性化**（列表里能看到没有任何路由指向它）。另：§4.9 的「最小运行骨架」生成器侧改动可更早独立上线（零 UI），作为止血后消除「死 receiver」的首道产品化收口。

## 6. 验收标准

| # | 验收项 | 通过判据 |
|---|---|---|
| 1 | 只读渲染 | 平台上载一份含 5 条路由的 `alertmanager.yml`，「路由规则」页能还原出**层级 + 顺序 + 四维字段**，与文件逐条一致 |
| 2 | 生成往返无损 | 「从当前配置导入」→ 不改任何字段 → 保存生成 → 与导入源**结构等价**（`name` 经注释还原） |
| 3 | 顺序即优先级 | 列表拖拽调整后保存，生成的 YAML 中 `routes[]` 顺序与界面一致 |
| 4 | 编辑态字段不落盘 | 生成的 route 段**不含** `id` / `parent_id` / `name` / `order` / `enabled` 字段；`enabled=false` 的规则及其子树**整条消失** |
| 5 | matcher 语法正确 | 生成物通过 `amtool check-config`；正则条件落 `isRegex: true` |
| 6 | 时间校验 | `group_interval` 不整除 `repeat_interval` 时界面给出警告（且仍可保存，与 AM 行为一致） |
| 7 | 双作者不打架 | 平台管理模式保存后，用户手写 receiver **原样保留**；平台槽位地址变化**不报重名**（= L2 验收） |
| 8 | 逃生门可用 | 关闭模式开关 → 用户可在告警配置页整份手写 route 并正常下发 |
| 9 | 管道不变 | 保存后进入 M09 变更单，人工确认后才写盘 reload（决策 59/60 不破） |

## 7. 风险与未决项

### 7.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 生成器与 AM 语义漂移（如 matcher 语法版本差异） | 生成物校验失败 | 生成物**必须**过 `amtool check-config`（已有能力）；单测覆盖 matchers / 时长 / 嵌套三组 |
| 「顺序」被用户忽略 | 规则不按预期生效（同今天的困境） | 列表态**常驻**顺序说明；保存时若存在「一条路由的条件被上方兄弟完全覆盖」的**可检测死规则**，给出提示（v0.3-c 候选） |
| 模式切换误操作 | 用户手写 route 被接管 | 二次确认 + **切换时不删已有内容** + 版本历史可回滚（已有能力） |
| 双作者仍存于 `receivers` | 与 L2 强耦合 | **L2 必须先落**（这是 #28.3 的执行顺序结论） |

### 7.2 决策结论（P1–P4 已拍板 · P5–P7 已定案）

> 说明：P1–P7 共 7 项。**P1–P4 为产品取舍，2026-09-30 经 chenrt 拍板（均取推荐项）**；**P5–P7 为工程/范围判断，直接定案**。

#### 7.2.1 P1–P4 产品拍板结论（2026-09-30 已决）

| # | 问题 | 选项 | **结论** | 理由 | 影响 |
|---|---|---|---|---|---|
| **P1** | route 段**默认**作者 | a. 手写（默认）<br>b. 平台管理 | **a. 手写（默认）** | 存量部署（含现网）已是手写 route，默认切到「平台管理」会在用户不知情时接管其手写配置，违背「零影响」原则。新用户由「首次进路由页」的引导切入平台模式，迁移是**显式**动作而非隐式。 | 现网/存量用户**无感**；平台模式为可选入口，不自动接管。 |
| **P2** | 是否做「从当前配置导入」 | a. 做<br>b. 不做 | **a. 做** | 不做则存量用户要重新在表单里敲一遍，迁移成本高到没人会用，「平台模式」形同虚设。§3.5 已论证「解析现有 route 段 → 填表 → 再生成」往返无损（`name` 经注释还原），技术可行、代价可控。**但可降级**：v0.3-b 首发可只做「导入 + 手动校正」，不追求全自动无损。 | 平台模式可被存量用户**真正采用**；v0.3-b 实现须含解析器。 |
| **P3** | 根路由兜底接收人来源 | a. 平台提供「默认接收人」配置项<br>b. 强制先建接收人再启用平台模式 | **a. 平台提供默认接收人** | AM 的根 `route:` 必须有 `receiver`（否则 `amtool` 校验失败），若无兜底，用户启用平台模式的第一步就卡住。平台已物化 receiver，取「已启用渠道里的第一个（或用户显式指定一个）作为默认」最顺滑，且与 PRD §1「管理域 default 不扇出」的兜底语义一致。 | 启用平台模式**零门槛**；需在「告警配置页」补一个「默认接收人」选择项（回填项 §8.1/§11.6）。 |
| **P4** | v0.3-a（只读渲染）是否与第一步止血同批上线 | a. 同批<br>b. 等 v0.3-b | **a. 同批** | 只读渲染零生成逻辑、零模式开关、零风险，能立刻把「平台 receiver 是死配置（无 route 引用）」在界面上显性化——这正是止血后用户最想看到的第一件事。 | 路由页**先于可写表单**上线只读态；与第一步止血（#28）同批发布。 |

#### 7.2.2 工程/范围判断（P5–P7，可定案）

| # | 问题 | **结论** | 理由 |
|---|---|---|---|
| **P5** | route 编辑是否复用挂载端点（不新增端点） | **复用，不新增** | route 编辑本质是「提交一份新的 alertmanager.yml 内容」，与文件挂载完全同构，只是「内容由表单生成」而非「用户粘贴」。复用 `POST /api/v2/platform/alertmanager/config` 即可走通「校验 → 落库 → M09 变更确认 → 下发」全链路，**零后端契约扩张**，风险最低。真正需要新增的只有「只读渲染」可能需要的**读取**端点（见 §8.2 待回填），**那个**单独评估、不影响本结论。 |
| **P6** | `mute_time_intervals`（免打扰时段）是否纳入 v1.0 | **本期不做，纳入 v1.0 候选（不承诺）** | AM 0.34 已支持，但它引入「时段」这一全新维度（时区、周期性时间窗、与 route 的关联），会显著摊大表单与生成器。告警通知的「免打扰」是真实诉求，但优先级低于「先让 route 能改对」。**留待 v1.0 阶段再评估**，不在 v0.3 承诺。 |
| **P7** | 「死规则检测」（条件被上方兄弟完全覆盖）是否做 | **本期不做，列为 v0.3-c 候选** | 完整的子集/覆盖判定需要解析 matcher 语义（含正则的包含关系），是**难而少见**的能力；而「顺序靠注释传承」的即时痛点已由 v0.3-a 的「顺序可视化 + 拖拽」解决。先上「顺序可视化 + 拖拽」这个高杠杆项，死规则检测作为增强项单独排。 |
